# Changelog

История ревизий метода Gauntlet и бандла эталонного набора. Документы в репозитории версионируются вместе:
ревизия инструкции `gauntlet-method-universal.md` и ревизия бандла `gauntlet-kit-bundle.md` совпадают.

## Ревизия 4.4 — 2026-11-24

Проверки по результату вместо эвристик по тексту (issue #4) и давние дефекты из ревью `7061885` (issue #3). Правки
внесены в бандл; универсальная инструкция меняет только ревизию. Все правки только ужесточают: ни один порог, тест
или правило не сняты; новые красные с обходным путём перечислены в README набора, раздел 9.

### Что было до правок (база, ревизия 4.3)

- **Запись в файлы набора мимо guard ничто не судило.** guard читает команды агента, а список команд записи не бывает
  полным (`sort -o`, `gzip`, `javac -d`, переменная в цели перенаправления).
- **B2 узнавал фильтр тестов только по тексту скрипта.** Переменная, `tasks['test']`, `matching { }`, параметр
  замыкания, ветка `case`, Kotlin `when`, фильтр тестовой платформы вне скрипта (`PostDiscoveryFilter`) — тест не
  запускался, гейт был зелёный. На Gradle: из 30 форм Groovy и 9 Kotlin B2 не видел 21 и 4.
- **Сценарии приёмки, убранные фильтром, не считались.** `excludeTags` тестовой платформы или более узкий
  `cucumber.features`: «Acceptance: 11 scenario(s), none skipped - OK» при 15 определённых.
- **Порядок прогона мутантов судился по аргументам JVM.** `_JAVA_OPTIONS`, файл аргументов, провайдер, который
  отвечает иначе после прогона, `doLast` проекта — шесть путей, при которых контроли шли раньше мутанта, все зелёные.
- **Stop-хук и CI судили по коду выхода Gradle.** Одна строка в `build.gradle`,
  `gradle.startParameter.excludedTaskNames.addAll(['gauntletFast', 'gauntlet'])`, убирала все гейты из графа:
  `BUILD SUCCESSFUL`, агент отпущен, CI зелёный.
- **Давние дефекты (issue #3):** Stop-хук выходил с кодом 1 при ошибке ОС и отпускал агента; шаблон нёс
  `module=core,adapter`; `install.sh` писал через символическую ссылку `.claude`, падал посреди установки на
  `settings.json` не той формы, оставлял хук набора дважды; подложенный отчёт печатал локальный файл через XXE в
  `PitSummary`, `DryGate`, `CrapGate` и `GherkinMutator`; `crap.threshold=NaN` проходил любой метод;
  `GAUNTLET_GATE_JAVA_HOME` обходил минимум Java 17; `session_start.sh` читал `baseRef` только через `=`.

### Что изменилось

1. **`.github/workflows/gauntlet-kit.yml`** (новый, ставится `install.sh`): `pull_request_target`, сравнение PR с
   merge base только git'ом, без кода PR; красный, когда изменён путь, который guard охраняет как человеческий.
   Вердикт — check run `gauntlet kit unchanged` на голове PR через Checks API (`checks: write`). Человек делает
   обязательными `gauntlet` и `gauntlet kit unchanged` с источником GitHub Actions; своё изменение набора мержит
   в обход.
2. **`testCensus`** (новый инструмент `TestCensus.java`, в `gauntletFast`): каждый тестовый класс, который
   скомпилировали `test` и `archTest`, есть в их JUnit XML; иначе находка T6, которую принимает только строка
   allowlist'а. Задача вне графа или выключенный XML-отчёт — отказ.
3. **Поток сообщений Cucumber.** `gherkinMutation` судит порядок прогона мутантов по потоку этого прогона (по файлу на
   JVM): начало и конец каждой попытки, ни одного перекрытия в одном JVM, каждый мутант между своими контролями.
   `acceptanceCheck` сверяет сценарии, которые определяют фичи, с потоком: неисполненные — находка F2. `acceptanceTest`
   идёт по одному форку; с Cucumber 8 набор добавляет Jackson в свои зависимости приёмки по умолчанию.
4. **Stop-хук и CI требуют строку `> Task` у каждой задачи гейта** (`GATE_TASKS` в `stop_gate.py`, CI вызывает
   `stop_gate.py --verify-ran gauntlet`) после зелёного кода выхода.
5. **issue #3:** ошибка ОС в Stop-хуке — красный прогон через счётчик попыток, вывод не в UTF-8 декодируется с
   заменой, вне git — сообщение «не запускался»; шаблон с пустым `module`, `install.sh` отказывается до любых
   изменений на записи `module` без каталога, на ссылке `.claude`, `.claude/settings.json` или `.claude/agents`, на
   `settings.json` не той формы и оставляет один хук набора; `PitSummary`, `DryGate` и `GherkinMutator` не читают
   отчёт с DOCTYPE, `CrapGate` не загружает внешних параметрических сущностей; порог CRAP — конечное число ≥ 0;
   `GAUNTLET_GATE_JAVA_HOME` и `-Pgauntlet.gateJavaHome` проверяются на Java 17+ по ответу их `java`;
   `session_start.sh` читает `baseRef` кодом `stop_gate.py`.
6. **Dry run JUnit Platform** (`junit.platform.execution.dryRun.enabled=true`, найден при переписи: каждый тест
   «пропущен», ни один не запускался) — находка P1 в `junit-platform.properties` и B3 в скрипте сборки.
7. **По независимому ревью сведённых правок:** dry run Cucumber и `discovery.as-root-engine` набор задаёт сам и
   сверяет после прогона; суженный `testClassesDirs` и один каталог JUnit XML у `test` и `archTest` — отказ
   переписи, тестовый исходник вне компиляции — T6; Jackson для Cucumber 8 — без версии, с ограничением «предпочитаю»
   (Spring Boot 4 с `io.spring.dependency-management` снова зелёный); лимиты размера JAXP JDK 24+ сняты во всех
   читателях XML; список `cucumber.plugin` собирается по элементам. Гейт, который набор не пропускает сам,
   засчитывается только выполненным (`tasks.named('integrityCheck') { enabled = false }` после `apply` был
   зелёным), пропуск набора — только с его строкой `skipped by the kit`; код выхода инструмента сверяется после
   прогона (`ignoreExitValue`); `gauntlet.properties` не в UTF-8 больше не роняет Stop-хук; PR в другую ветку
   отчитывается под именем `gauntlet kit unchanged (<ветка>)`; инструменты запускаются с `-Dfile.encoding=UTF-8`
   (JVM гейта 17 в локали POSIX).

## Ревизия 4.3 — 2026-11-20

Ревью всего набора на ошибки (инструменты, хуки, настройки, пример, документация) и правки по всем находкам.
Правки внесены в бандл (встроенные файлы эталона); что изменено в универсальной инструкции — в «Где именно».
Поведение гейтов не ослаблено: ни один порог, тест или правило не сняты.

### Что было до правок (база, ревизия 4.2)

- **`IntegrityCheck` (B1) освобождал «безобидную» задачу по имени где угодно в строке.** `test { dependsOn(jar);
  enabled = false }` проходило как «безобидный jar», хотя отключало `test`. Лазейка: отключение тестов под
  видом ссылки на jar.
- **`CrapGate` резал строку allowlist по первому `#`.** Разделитель `Class#method` — тоже `#`, поэтому запись
  обрезалась до имени класса и allowlist не работал (молча).
- **`GherkinMutator`: отсутствующий каталог фич давал «no mutants OK» (exit 0).** Ошибка конфигурации
  (`acceptance.features`) маскировалась под зелёный гейт. Пустота проверялась по файлу, а не по сценарию:
  сценарий без «Примеров» внутри файла с другими сценариями проходил вхолостую. Unescape ячеек шёл тремя
  последовательными `replace` и двойно декодировал `\\n`/`\\|`; имя мутанта с переносом строки ломало TSV-манифест.
- **guard обходился обёртками и inline-кодом.** `sudo git push --force`, `bash -c 'git push --force'`,
  `eval '…'`, `echo '…' | sh`, `python3 -c "os.system('…')"` не проверялись на human-only правила. `.git/`
  не был защищён (удаление снимает заморозку и Stop-хук, подделка `last-green-*` форсит зелёный статус).
  `push --mirror`/`--all`, `push HEAD` на базовой ветке, сокращения `--no-verif`, `core.hooksPath`, пути в
  другом регистре (`GAUNTLET/…`) не ловились.
- **`stop_gate`: окно повторов SubagentStop (20 мин) было меньше таймаута `mutationGate` (3300 с).** Медленный
  прогон выглядел «новой сессией» и сбрасывал счётчик в 1 — бесконечная петля красных остановок.
- **`permissions.deny` не покрывал заявленное.** README обещал блокировку `--amend`/`reset`/`push --force`
  «хук + deny», но в deny были только `rebase`/`filter-branch`/`filter-repo`/`gh pr merge`.
- **Пример фичи содержал эквивалентные мутанты.** Процентная скидка: строка `| 0 | 10000 | 0 |` и округление
  процентов давали мутанты, не меняющие исход, — `gherkinMutation` не мог их убить.
- **Инструкция, п. 10: «Blocker и major исправляются всегда» — без оговорки типа.** Противоречило шагу 7
  процесса: находка типа «правило» (blocker/major по важности) уходит владельцу, а не в раунд правок.

### Что изменилось

1. **`IntegrityCheck` (A1):** освобождение проверяется только по опенеру блока — текст до первой `{`, после
   последней `;` в строке. `test { dependsOn(jar); enabled = false }` снова нарушение B1; `jar { enabled = false }`
   по-прежнему освобождён.
2. **`CrapGate` (B4):** комментарий начинается с `#` после пробела или в начале строки (как в `PitSummary`);
   `#` внутри `Class#method` не режет запись. Allowlist снова работает.
3. **`GherkinMutator` (A2/A3/E14):** отсутствующий каталог фич — жёсткая ошибка (exit 1) с сообщением о
   misconfigured `acceptance.features` (установка создаёт каталог пустым с `.gitkeep`, так что отсутствие —
   именно ошибка конфигурации, а не легитимный пустой проект). Пустота — по каждому сценарию (`GHERKIN VACUOUS`
   с именем и строкой). Unescape атомарный, за один проход. Имя мутанта в манифесте — через `tsv` (переносы
   и табы заменяются пробелом).
4. **guard (C5–C9):** human-only правила рекурсивно применяются внутри обёрток (`sudo`/`env`/`exec`/`command`/
   `nohup`/`time` с опциями и значениями), inline-кода (`-c`/`-e`, включая вложенные строки в кавычках —
   `os.system`/`subprocess`/`execSync`), `eval`/`source` и pipe в интерпретатор. Сегментация внешней команды
   учитывает кавычки (`split_shell`): разделители внутри кавычек не режут команду, поэтому inline-payload
   доходит до рекурсивной проверки целым, а уже код рекурсия режет по его настоящим разделителям.
   `.git/` — зона человека. Закрыты `push --mirror`/`--all`, `push HEAD` на базовой ветке (с разрешением
   `push -u origin HEAD` на своей ветке), сокращения `--no-verify` и `core.hooksPath`, регистронезависимые
   пути и `mentions`.
5. **`stop_gate` (D11):** окно повторов = `timeout + 10 мин` (больше любого таймаута задачи); медленный
   `mutationGate` не сбрасывает счётчик. Ключ сессии (`session + agent_id`) изолирует сессии, поэтому окно
   безопасно расширено. Stop-событие по-прежнему использует флаг `stop_hook_active`.
6. **`permissions.deny` (E13):** дополнен прямыми формами human-only команд (`--amend`, `reset --hard`,
   `push --force`/`-f`/`--force-with-lease`/`--mirror`/`--all`, `checkout -B`, `switch -C`, `branch -f`/`-D`/`-M`,
   `revert`, `update-ref`, `replace`) — префиксный дубль хука.
7. **Пример фичи (E12):** фиксированная скидка, `итог = сумма − скидка`; изменение любой ячейки «Примеров»
   меняет исход — 9 мутантов, 0 эквивалентных (проверено генерацией и разбором).
8. **`PitSummary` (E15):** поведение не менялось; в Javadoc зафиксировано, почему `TIMED_OUT` не входит в
   UNVERIFIED — тесты прогнались против мутанта и он их зависнул (бесконечный цикл), это настоящее обнаружение
   (`TIMED_OUT(true)`), а не crash, пропустивший тесты. Сверено по семантике PIT.
9. **Инструкция (F16):** п. 10 — «Blocker и major типа «дефект» исправляются всегда», согласовано с шагом 7.
10. **README набора:** таблица лазеек и раздел 8 дополнены новым покрытием; счётчик самопроверки 574 → 682;
    честно описан остаток эвристики и настоящая опора (branch protection + CI + diff PR).
11. **guard — две правки по автоматическому ревью PR (Codex):**
    - **P1 (сегментация inline-кода).** Первая версия гасила мета символы внутри кавычек перед сегментацией
      (`QUOTED.sub`), и это стирало `;` внутри `bash -c 'echo ok; git push --force origin main'`: рекурсия
      видела `echo ok_ git push …` как аргументы `echo` и пропускала force-push. Заменено на `split_shell` —
      сегментация, учитывающая кавычки: разделители в кавычках не режут внешнюю команду, payload доходит до
      рекурсии целым и режется уже по своим настоящим разделителям. Закрывает и многострочный inline
      (`echo ok; git push --force`), и вложенные кавычки (`os.system('…')`).
    - **P2 (`core.hooksPath` только в конфиге).** `any("core.hookspath" in a.lower() for a in args)` ловил
      текст сообщения коммита и переблокировал `git commit -m 'Document core.hooksPath behavior'`. Заменено
      на `hooksPath_override`: проверяются только реальные глобальные `-c`/`-c…` до подкоманды git со
      значением `core.hooksPath=…`, а не произвольные аргументы (сообщение, trailer).
    - Регрессии: 7 новых сценариев в `selftest.py` (многострочный inline force-push/amend/gh-merge и безобидный
      `echo ok; echo done`; `-ccore.hooksPath=…` и два случая с текстом `core.hooksPath` в сообщении).
      `guard_tests` гоняется в трёх раскладках, поэтому +21 проверка (661 → 682). Остаток эвристики не
      изменился (`$(which git)`, переменные, base64).
12. **guard и инструменты — шесть правок по ревью Kimi (продолжение ревизии 4.3).** Каждая находка
    подтверждена воспроизведением на базе и на PR; поведение гейтов не ослаблено.
    - **guard, тела подстановок команды (P1).** Регрессия после правки Codex: `split_shell` учитывает кавычки
      при сегментации, но тела `$(…)`/`` `…` ``, которые shell исполняет вне одинарных кавычек, не проверялись —
      `"$(git push --force)"` проходило. Добавлен `command_substitutions`: тела подстановок вне одинарных
      кавычек рекурсивно проверяются human-only правилами (вложенные подстановки рекурсия разбирает сама).
      В одинарных кавычках подстановка литеральна и не блокируется — без over-block.
    - **`GherkinMutator`, Background (P1) — отменено правкой G6 (п. 13).** Сценарий без собственных шагов
      освобождался от проверки пустоты, даже когда Background фичи или правила даёт исполняемые шаги. Правка
      сделала освобождение только когда шагов нет и в Background (`hasBackgroundSteps`); иначе сценарий без
      «Примеров» помечался `GHERKIN VACUOUS`. Посылка оказалась неверной: Gherkin не подмешивает Background к

### Остаток `gherkinMutation` (честно)

- glue-код, читающий имя сценария, отличает мутант от контроля по заголовку (`MUTANT`/`CONTROL`);
- исключение без стека (`writableStackTrace=false`) не несёт кадра шага: настоящий kill считается ошибкой;
- колонка, которую конвертирует Cucumber (enum, `@ParameterType`), даёт ошибку, а не kill: инструмент пока не
  подбирает вторую валидную величину колонки (как и на `166287c`, гейт здесь красный, а не зелёный);
- «Значения» считается ключевым словом «Примеров», хотя Gherkin Cucumber 7.23.0 его не знает.

### Остаток эвристики guard (честно)

guard — растяжка, а не сейф (это заявлено в наборе). Статический разбор shell не видит:
- подстановку команды, порождающую имя бинарника: `$(which git) push --force`;
- разворачивание переменной: `G=git; $G push --force`;
- закодированные payload'ы (base64 и т. п.);
- функцию оболочки, определённую в той же команде (`f() { "$@"; }; f bash <<EOF …`), и код из файла — скрипт,
  который запускает интерпретатор;
- `cd` внутри конвейера (`cd ../worktree | cat; git push`): в bash каталог не меняется, в zsh последний элемент
  конвейера исполняется в текущей оболочке; хук считает, что каталог сменился;
- конфигурацию git через переменные окружения (`GIT_CONFIG_KEY_n`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_GLOBAL`)
  и алиасы, уже лежащие в глобальном конфиге пользователя;
- `push.default=upstream` с push без refspec на ветке, чей upstream — базовая;
- настройки репозитория через `gh api -X PATCH repos/…`;
- команды записи, которых хук не знает: `sort -o`, `uniq`, `shuf -o`, `gzip`, `split`, `zip`, `mkfifo`,
  `javac -d`, у main и `dd of=` (список команд записи полным не бывает; закроет проверка защищённых файлов в CI);
- функции модулей perl (`perl -MFile::Copy -e 'copy(…)'`) и программу awk (`system()`, `print >`): хук знает
  встроенные слова записи perl, но не разбирает модули perl и программу awk.

`permissions.deny` тоже префиксный и обходится обёрткой (`bash -c 'git push --force'` не начинается с
`git push`). Настоящая опора для базовой ветки — GitHub branch protection, CI (`fetch-depth: 0`,
`integrityCheck`) и человек, читающий diff PR. Эти остатки не заявлены как закрытые и не маскируются.

## Ревизия 4.2 — 2026-11-19

Защита от петли «пробел спецификации». Правки синхронно внесены в универсальную инструкцию и в бандл

### Что было до правок (база, ревизия 4.1)

- **Находки ревью не классифицировались.** «Поведение противоречит утверждённой спецификации» и «спецификация
  вообще не определяет это поведение» обрабатывались одинаково — как дефект кода, уходящий в новый раунд
  правок. Вопрос уровня спецификации решался на уровне кода.
- **Лимит двух раундов держался на дисциплине.** Механического счётчика не было: остановка после второго
  CHANGES REQUESTED зависела от самоконтроля агента (в облачных сессиях хуки набора не срабатывают, а хук
  остановки основного агента проверяет гейты, а не число раундов ревью).
- **Для задач выбора значения или версии не требовалась таблица решений.** `specifier` возвращал сценарии, но
  правило выбора (какая версия/строка/значение допустимы к моменту события) могло остаться неопределённым и
  решалось кодом по одному случаю за раунд.
- **Дыра-чека перед заморозкой не было.** Правило, которое код должен решать, но которое не закреплено ни
  сценарием, ни явным «Вне фичи», могло молча уйти в реализацию.
- **Граничные регрессионные случаи рождались после сдачи.** Их приносил координатор или ревьюер патчем к
  готовой реализации, а не как цели тестов в пред-проверке до начала работы.
- **Отчёт не выделял находки «правило» и раунды ревью** отдельным списком с пометкой, что они ждут решения
  владельца и что правок кода по ним не было.
- **Манифест бандла был частично устаревшим** (см. ниже).

Следствие, которое и потребовало правок: в задаче выбора версии услуги спецификация не определяла, какая
версия записи действует на момент события, поэтому координатор восемь раз возвращал реализацию. Каждый раунд
исправлял один случай, а общее правило оставалось открытым; гейты были зелёными, поскольку проверяют код против
спецификации, а не ненаписанных правил. Ревизия 4.2 закрывает такой пробел процессом, а не метриками
(раздел 6 инструкции).

### Что изменилось — пять мер

1. **Классификация находок.** Каждая поведенческая находка ревью и координатора помечается типом:
   **«дефект»** — поведение противоречит утверждённой спецификации или решению владельца, правится в коде;
   **«правило»** — спецификация не определяет поведение, которое код решает (выбор версии, порядок строк,
   судьба отказа, явная очистка поля против его отсутствия). Находка типа «правило» не уходит в новый раунд
   правок: она идёт владельцу нумерованным списком «ответьте здесь», работа над ней останавливается до ответа;
   после ответа правило закрепляется в спецификации, затем один проход реализации против всего правила, а
   накопленные регрессионные случаи становятся приёмочным набором.
2. **Таблица решений для задач выбора.** Если задача выбирает значение или версию из нескольких,
   пред-проверка координатора и `specifier` строят таблицу по требованиям целевого проекта: строки — типы
   событий и граничные условия, столбцы — наблюдаемые результаты. Пустая ячейка — вопрос владельцу до
   реализации. Заполненные строки утверждаются до заморозки и становятся сценариями со значениями в Examples.
   Малый размер задачи не освобождает от таблицы.
3. **Дыра-чек перед заморозкой.** Каждое правило, которое код должен решать, закреплено сценарием или явно
   вынесено «Вне фичи» с принятым риском. Критерий — наблюдаемость приёмкой: меняется хоть одно свойство,
   которое видит приёмка (ответ, сообщение, сохранённая строка), — правило обязано быть в спецификации. Дыра —
   вопрос владельцу до заморозки; после заморозки она стоит уже правки спецификации человеком.
4. **Механический счётчик раундов.** Счёт ведётся в плане (координатор) или в описании PR (сессия без
   координатора). После второго CHANGES REQUESTED с непогашенными находками новые замечания не выдаются —
   остаток выносится владельцу, работа не считается сделанной. Исполнитель после второго круга останавливается
   с пометкой «ответьте здесь», а не правит код дальше. Замечание, воспроизводящееся на базе до задачи, —
   отдельная задача бэклога, а не основание заворачивать PR.
5. **Граничные тесты до реализации.** Цели граничных тестов из таблицы решений идут в промпт сессии в
   пред-проверке, а не патчем после сдачи.

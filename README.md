# Gauntlet — метод разработки «не читая код»

Дистрибутив метода **Gauntlet**: подход Роберта Мартина (Uncle Bob), переложенный на агентную разработку
(Claude Code и совместимые CLI), с дополнениями владельца. Человек читает спецификацию, отчёт о гейтах и
изменения самого набора — и принимает три решения: «да» спецификации, утверждение плана серии, merge PR.
Всё остальное делает агент, а качество держат гейты, хуки, CI и адверсарное ревью, а не «хорошесть» модели.

Репозиторий содержит самодостаточные документы метода: их можно переслать тому, кто ставит набор в свой
репозиторий, доступ к чужим репозиториям не требуется.

## Как это работает

- **Спецификация.** Роль `specifier` пишет Gherkin на границе сервиса (запросы/ответы, сообщения, наблюдаемое
  состояние); человек утверждает. После утверждения спецификация заморожена — её меняет только человек.
- **Реализация.** `coder` идёт по TDD маленькими шагами, сверяя каждый API с официальной документацией нужной
  версии (правило 12), а не с памятью.
- **Закалка.** `hardener` убивает выживших мутантов и пустые step-определения: ни один покрытый мутант не
  должен выживать.
- **Ревью.** `reviewer` ищет то, чего не видят метрики: поведение против спецификации, безопасность и ПДн,
  транзакции и конкурентность, SOLID, gate gaming. Находки классифицируются: «дефект» (правится в коде) и
  «правило» (спецификация не определяет поведение — вопрос владельцу, без нового раунда правок).
- **Гейты.** Сложность и размер функций, антипаттерны, архитектурные рёбра, покрытие через CRAP, дубли,
  мутационное тестирование, мутация значений спецификации, integrity (нет отключённых тестов и подавлений).
  Хуки защищают набор и спецификацию, CI повторяет гейты вне сессии, PR показывает diff.

Задачи ведёт **координатор серии** — отдельная долгоживущая сессия, которая не пишет продакшен-код: план,
задача для Jira и пред-проверка перед каждым шагом, одна задача = одна сессия = одна ветка = один PR.

## Как запустить в новом проекте

Нужны оба файла (`gauntlet-method-universal.md` и `gauntlet-kit-bundle.md`), оба самодостаточны.

1. **`start`** — новая сессия на целевом репозитории, режим Accept edits. Прикрепите оба файла и напишите
   `start`. Ответьте на вопросы. Агент распакует бандл, адаптирует набор под ваш стек, установит его в ветке
   `gauntlet-setup` (первый прогон гейтов зелёный на текущем коде) и откроет PR.
2. **`scan`** — после мержа PR вторая сессия на том же репозитории, прикреплённая инструкция, слово `scan`.
   Агент соберёт контекст проекта, напишет инструкцию по настройке окружения (домены, переменные, Docker,
   GitHub) и первую серию задач.
3. **`coordinate`** — серию ведёт координатор: отдельная долгоживущая сессия с прикреплённой инструкцией и
   файлом плана, слово `coordinate`. План, задача для Jira и пред-проверка перед каждым шагом.
4. **`contract <ревизия прода>`** — перед выкатом серии в прод: сверка контракта с продом по всем внешним
   поверхностям.

Подробности — в [`gauntlet-method-universal.md`](gauntlet-method-universal.md), разделы 1.1, 8.1–8.5.
Если приложение живёт в закрытом корпоративном контуре, набор туда не переносится (раздел 1.2); оба файла —
обычные документы, их вносят в контур как любые документы.

  reviewer'ом. Проверено на реальных Gradle/Cucumber 8.0.1 и 7.23.0, PIT и JaCoCo `debug=false`.

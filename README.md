# Gauntlet — метод разработки «не читая код»

Дистрибутив метода **Gauntlet**: подход Роберта Мартина (Uncle Bob), переложенный на агентную разработку
(Claude Code и совместимые CLI), с дополнениями владельца. Человек читает спецификацию, отчёт о гейтах и
изменения самого набора — и принимает три решения: «да» спецификации, утверждение плана серии, merge PR.
Всё остальное делает агент, а качество держат гейты, хуки, CI и адверсарное ревью, а не «хорошесть» модели.

Репозиторий содержит самодостаточные документы метода: их можно переслать тому, кто ставит набор в свой
репозиторий, доступ к чужим репозиториям не требуется.

## Как это работает

- **Спецификация.** Роль `specifier` пишет Gherkin на границе сервиса (запросы/ответы, сообщения, наблюдаемое
  состояние); человек утверждает. После утверждения спецификация заморожена — её меняет только человек.
- **Реализация.** `coder` идёт по TDD маленькими шагами, сверяя каждый API с официальной документацией нужной
  версии (правило 12), а не с памятью.
- **Закалка.** `hardener` убивает выживших мутантов и пустые step-определения: ни один покрытый мутант не
  должен выживать.
- **Ревью.** `reviewer` ищет то, чего не видят метрики: поведение против спецификации, безопасность и ПДн,
  транзакции и конкурентность, SOLID, gate gaming. Находки классифицируются: «дефект» (правится в коде) и
  «правило» (спецификация не определяет поведение — вопрос владельцу, без нового раунда правок).
- **Гейты.** Сложность и размер функций, антипаттерны, архитектурные рёбра, покрытие через CRAP, дубли,
  мутационное тестирование, мутация значений спецификации, integrity (нет отключённых тестов и подавлений).
  Хуки защищают набор и спецификацию, CI повторяет гейты вне сессии, PR показывает diff.

Задачи ведёт **координатор серии** — отдельная долгоживущая сессия, которая не пишет продакшен-код: план,
задача для Jira и пред-проверка перед каждым шагом, одна задача = одна сессия = одна ветка = один PR.

## Как запустить в новом проекте

Нужны оба файла (`gauntlet-method-universal.md` и `gauntlet-kit-bundle.md`), оба самодостаточны.

1. **`start`** — новая сессия на целевом репозитории, режим Accept edits. Прикрепите оба файла и напишите
   `start`. Ответьте на вопросы. Агент распакует бандл, адаптирует набор под ваш стек, установит его в ветке
   `gauntlet-setup` (первый прогон гейтов зелёный на текущем коде) и откроет PR.
2. **`scan`** — после мержа PR вторая сессия на том же репозитории, прикреплённая инструкция, слово `scan`.
   Агент соберёт контекст проекта, напишет инструкцию по настройке окружения (домены, переменные, Docker,
   GitHub) и первую серию задач.
3. **`coordinate`** — серию ведёт координатор: отдельная долгоживущая сессия с прикреплённой инструкцией и
   файлом плана, слово `coordinate`. План, задача для Jira и пред-проверка перед каждым шагом.
4. **`contract <ревизия прода>`** — перед выкатом серии в прод: сверка контракта с продом по всем внешним
   поверхностям.

Подробности — в [`gauntlet-method-universal.md`](gauntlet-method-universal.md), разделы 1.1, 8.1–8.5.
Если приложение живёт в закрытом корпоративном контуре, набор туда не переносится (раздел 1.2); оба файла —
обычные документы, их вносят в контур как любые документы.

## Ревизии

- **4.3 (2026-11-20)** — ревью всего набора на ошибки и правки: `IntegrityCheck` (освобождение задачи только
  по опенеру блока), `CrapGate` (allowlist не режется по `#` в `Class#method`), `GherkinMutator` (каталог фич,
  пустота по сценарию, атомарный unescape), guard (human-only правила внутри обёрток/inline-кода/pipe, защита
  `.git/`, новые формы push и `--no-verify`, регистр путей), `stop_gate` (окно повторов больше таймаута),
  `permissions.deny` дополнен, пример фичи без эквивалентных мутантов; самопроверка 574 → 733 → 808 → 892 → 970 → 985 → 994 → 997 → 2089. Продолжение —
  правки по ревью Kimi (тела подстановок команды, `env -S`, push без refspec, смешанные строки `IntegrityCheck`,
  окно `stop_gate` на весь бюджет прогона) и по ревью Grok (G1–G7: некавыченный payload слева от пайпа, глубина
  `$(…)` с учётом кавычек, `@`/`HEAD:other`, push с `-C`/`--git-dir`, версионные интерпретаторы/argv из кавычек —
  guard; отмена правки Kimi K2 «Background в `GherkinMutator`» — пустой сценарий ничего не исполняет и освобождён
  от проверки пустоты всегда; проверка получателя отключения при освобождении B1 в `IntegrityCheck`), и по ревью
  Codex (V1–V7: `install.sh` обновляет поля gauntlet-хуков при слиянии и масштабирует таймауты по модулям;
  `CrapGate` — сигнатуры перегрузок в allowlist, пустой `sourcefilename`, точные пути `--only`; `IntegrityCheck` —
  получатель `delegate`/`this` и многострочная скобка; `GherkinMutator` — сценарий без шагов не vacuous, `<error>`
  не kill, отсутствующий каталог фич — exit 1, экранирование `\n` в тексте шага; guard — сняты over-block
  cd-worktree push/print-литерал/stdin-документ; `stop_gate` — негативные коды и область модулей; `gauntlet.gradle` —
  входы `acceptanceTest` и мутации по скомпилированным типам; побайтный round-trip сборщика бандла), и второй
  раунд Codex (F1–F14: `GherkinMutator` — сбой `@Before` не kill, мутация одной ячейки Examples не портит
  соседнюю колонку, NBSP в отступе шага; `CrapGate` — `sourcefilename` ≠ имя файла, уникальность лямбд;
  `gauntlet.gradle` — тип с аннотацией на строке объявления; `stop_gate` — закоммиченный rename, вложенные
  сборки, per-module кэш отчётов и удалённый файл; `install.sh` — команда запуска узнаётся по интерпретатору и
  скрипту, `matcher` смешанной группы не трогается; `IntegrityCheck` — `it`/именованный параметр замыкания;
  guard — cd в подоболочке не утекает, argv-данные не становятся командой; сборщик §8.4 поставляет распаковщик
  своей версии и сверяет round-trip). Третий раунд Codex: стабильные ID outline в JUnit XML, kill только по assertion
  в кадре шага (включая Google Truth), точный разбор top-level Java-типов/пакетов для PIT и CRAP, Unicode и NBSP;
  установщик разделяет смешанные matcher-группы и не трогает `legacy-gauntlet`; guard использует `event.cwd` и
  отличает argv от второй программы; Stop-gate видит возврат pre-existing dirty-файла к HEAD. Четвёртый раунд:
  PIT/CRAP используют объявленный пакет и только объявленные типы (без пропуска класса вне каталога и без чужого
  одноимённого класса); установщик сохраняет `tools/gauntlet` и составные команды; Truth `AssertionErrorWithFacts`
  поддержан; guard различает аргументы Python-приложения; `IntegrityCheck` принимает комментарий после `{`.
  Управление версиями при `start`: версии языка, сборщика и фреймворков определяются по файлам проекта,
  используются в CI и ролях; совместимые инструменты проверяются реальным прогоном и фиксируются в конфигурации;
  JVM гейта отдельна от Java приложения; обновление зависимостей приложения — отдельное решение владельца.
  Повторное ревью: toolchain разрешается лениво, CI сохраняет проектную Java, путь JDK живёт вне git;
  installer сохраняет составные команды и выдаёт `*.gauntlet.new`; PIT/CRAP используют кодировку компиляции;
  CRAP не подключает класс из другого source root; исправлены standalone-комментарий Groovy и чтение Python argv
  reviewer'ом. Проверено на реальных Gradle/Cucumber 8.0.1 и 7.23.0, PIT и JaCoCo `debug=false`.
  Ревью `166287c` и независимое ревью набора: CI — отсутствующий модуль красный, версии JVM и `PATH` по модулям;
  область `changed` — кодировка из аргументов компилятора и страховка «выведенный тип существует как класс»;
  `CrapGate` и `IntegrityCheck` — одноимённые файлы, не-UTF-8 исходники, комментарии перед closure-параметром;
  `GherkinMutator` — kill по стадии падения вместо списка типов исключений и контрольные сценарии; установщик
  сохраняет второй Stop-хук с другой задачей; Stop-хук следит за `buildSrc`; guard — сокращения длинных опций
  git, `core.hooksPath` и алиасы в `git config`, выключение CI-гейта через `gh`, а также оболочки с `-c` в
  кластере опций (`bash -lc 'rm -rf gauntlet'` проходил), обёртки под полным путём и вложенный shell-код.
  Регрессии дистрибутива — в [`tests/`](tests/README.md).

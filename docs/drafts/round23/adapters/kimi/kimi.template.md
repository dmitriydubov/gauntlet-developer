# Адаптер gauntlet для Kimi K3.1 Pro (Kimi Code CLI)

Раунд 23, 2026-11-24. Проверено на `@moonshot-ai/kimi-code` 2.7.3 (npm, опубликован 2026-11-23): документация по тегу
релиза и код пакета `dist/main.mjs` прочитаны; сам `kimi` не запускался (у сессии нет ключа Kimi, а скачанный код по
правилам раунда только читается). Мост хуков и его тесты прогнаны против хуков набора без изменений (раздел D.4).
Источники с датами — раздел D.5; что не подтверждено — D.3.

**Коротко.** «kimi 3.1 pro» — модель **Kimi K3.1 Pro** (Moonshot AI, октябрь 2026), её родная среда — **Kimi Code CLI**
(`kimi`). Набор в ней работает: инструкция проекта, роли из `.claude/agents` без копирования, сабагенты-карточки,
хуки PreToolUse и Stop с теми же `guard.py` и `stop_gate.py` через мост, режим без интерактива для внешнего маршрута.
Не переносится: Kimi не сообщает хуку, какой агент вызывает инструмент (области ролей держат списки инструментов, промпт,
diff и CI), Stop-хук продолжает ход только один раз и не дольше 600 с, у hardener нет SubagentStop-гейта, хуки живут
только в настройках пользователя, а координатор не может сам открыть сессию шага. Жалобу владельца на «быстрых»
сабагентов код Kimi объясняет: встроенный `explore` по своему промпту «быстрый агент», а короткий итог сабагента с
0.41.0 не возвращается на доработку. Ответ адаптера — свои агенты-карточки с правилом тщательности, ограничение списка
сабагентов средой и приёмка отчётов по доказательствам (ядро, раздел 2).

## A. Что это и куда ставить

### A.1. Продукт и версия
- **Модель.** Kimi K3.1 Pro — первая модель серии K3.1 от Moonshot AI, вышла в API 23–24 октября 2026, рядом —
  ускоренная Kimi K3.1 Pro Highspeed; веса открыты 4 ноября 2026 (по новостям; официальная карточка модели из сессии не
  открылась, D.3). Дообучена из Kimi K3: MoE 2,8T параметров, 104B активных, контекст 1 048 576 токенов, рассуждение
  включено всегда, уровень — `reasoning_effort` `low` / `high` / `max` (README Kimi K3). Kimi K3 «works best with Kimi Code
  CLI» (там же). Идентификаторы: в API Moonshot — `kimi-k3.1-pro`, `kimi-k3.1-pro-highspeed`; в подписке Kimi Code
  («Kimi For Coding», `api.kimi.ai/coding/v1`) — `k3.1-pro`, `k3.1-pro-highspeed` (встроенный каталог моделей
  `kimi-code` 2.7.3). Отключить рассуждение у K3.1 Pro нельзя, уровни — те же три; уровень по умолчанию в Kimi Code
  `high`, в API — `max` (документация Kimi в выдаче поиска, страницы из сессии не открылись).
- **Среда.** Kimi Code CLI — npm `@moonshot-ai/kimi-code` (бинарь `kimi`, Node ≥ 22.19.0) или скрипт
  `https://code.kimi.com/kimi-code/install.sh`. Прежний Python-пакет `kimi-cli` (PyPI 1.52.0) заархивирован: «Legacy
  Python Kimi CLI, no longer maintained. Use Kimi Code CLI instead». Нижняя граница для адаптера — **2.7.0**: в 2.6.3
  починен Stop-хук, который не срабатывал после каждого хода (#4995), в 2.7.0 — сабагенты, которые в `kimi -p`
  обрывались сразу (#4868). Рядом с CLI есть `kimi web` (локальный веб-интерфейс), `kimi acp` (IDE), настольное
  приложение и Remote Control; облачных сессий, как у Claude Code, у вендора не найдено.
- **Другие среды с моделями Kimi.** Справка Kimi описывает подписку Kimi Code в сторонних агентах (Claude Code, Roo Code,
  OpenCode; в навигации — Hermes Agent; по выдаче поиска, страницы из сессии не открылись; Codex там не найден — не
  подтверждено), а каталог Kimi Code сам знает десятки провайдеров с K3.1 Pro. В чужой среде действует адаптер этой
  среды: механизмы здесь описаны для Kimi Code CLI. Отдельно — сам Claude Code с Anthropic-совместимым адресом Kimi
  (README K3: «we provide an OpenAI/Anthropic-compatible API»; K3 там проверялась: Kimi Code Bench 2.0 — 73,7 с Claude
  Code harness): тогда набор действует как есть, с хуками, областями ролей по `agent_type` и SubagentStop. Доступность
  K3.1 Pro по подписке через этот адрес не проверена.

### A.2. Главное
1. **Инструкция проекта** — `.kimi-code/AGENTS.md`, ссылка на `gauntlet/adapters/kimi/AGENTS.md`. Kimi не читает
   `CLAUDE.md` и не раскрывает `@`-импорты, поэтому `gauntlet/CLAUDE.md` агент читает сам в начале сессии и доказывает
   это (число строк, заголовки разделов).
2. **Роли** — файлы набора `.claude/agents/*.md` подключаются как агенты Kimi через `extra_agent_dirs` без изменений
   (frontmatter совместим, `model` и `color` Kimi пропускает). Особенности Kimi сообщает блок поправок в начале prompt.
3. **Карточки пред-проверки** — пять агентов `gauntlet-card-*` с правилом тщательности и формой отчёта ядра в
   системном промпте. Координатор и сессия шага запускаются агентами `gauntlet-coordinator` и `gauntlet-task`: их список
   `subagents` среда исполняет, поэтому «быстрый» встроенный `explore` им недоступен.
4. **Хуки** — мост `kimi_hooks.py` из пользовательского `~/.kimi-code/config.toml` гоняет `guard.py`, `stop_gate.py` и
   `session_start.sh` набора без изменений, только в рабочих копиях из списка владельца.
5. **Опора** — гейты и CI `gauntlet.yml`, `gauntlet-kit.yml` не меняются. Где хук Kimi слабее хука Claude Code, агент
   сам прикладывает доказательство прогона, координатор принимает его по правилу тщательности, решает CI.

### A.4. Установка
1. **Kimi Code CLI** закреплённой версии: `npm install -g @moonshot-ai/kimi-code@2.7.3` (или скрипт вендора), `kimi
   --version` → `2.7.3`, `kimi login` (OAuth Kimi Code; план с K3.1 Pro). Автообновление выключить (`tui.toml`, B.6):
   мост написан под форму событий этой версии.
2. **PR владельца в набор:** каталог `gauntlet/adapters/kimi/` с файлами из A.3 и ссылка в проекте:
   `mkdir -p .kimi-code && ln -s ../gauntlet/adapters/kimi/AGENTS.md .kimi-code/AGENTS.md` (на Windows ссылки git требуют
   `core.symlinks=true`; иначе — копия файла, тогда её охраняет только мост). Каталог `.kimi-code/` — настоящий: в него
   Kimi пишет `local.toml` (правила разрешений с областью `project`, код `appendPermissionRules`), и
   через ссылку на каталог писать отказывается (`assertNoSymlinks`). Файл не коммитить: `echo .kimi-code/local.toml >>
   .git/info/exclude`.
3. **Машина владельца:** `mkdir -p ~/.kimi-code/hooks && cp gauntlet/adapters/kimi/kimi_hooks.py ~/.kimi-code/hooks/`;
   дописать `~/.kimi-code/config.toml` и `tui.toml` из образцов `gauntlet/adapters/kimi/user/` (B.6); создать
   `~/.kimi-code/gauntlet-projects.txt` с каталогами клона и рабочих копий шагов; `kimi doctor config` — без ошибок. Мост копируется заново при каждом его изменении в наборе.
4. **Окружение сборки** как у локальной сессии Claude Code: `ORG_GRADLE_PROJECT_publicRepositories=true`, Docker для
   Testcontainers, JDK гейта (`gauntlet/CLAUDE.md`, «Среда облачной сессии»).
5. Первый запуск `kimi` в корне клона спросит доверие к папке — доверить (без него Kimi не читает проектные
   `local.toml`, `.kimi-code/mcp.json` и `.mcp.json`; хуки и агенты из настроек пользователя работают и так). Доверие
   записывается на папку, а не на содержимое (код `trustRecord`): позже добавленный `.mcp.json` загрузится без нового
   вопроса — поэтому он в путях человека (A.3).
6. Проверка — A.7.

### A.5. Как переиспользуются файлы набора, а не копируются
- `gauntlet/CLAUDE.md` — не копируется и не пересказывается целиком: инструкция Kimi кратко повторяет жёсткие правила со
  ссылкой на него и требует прочитать его целиком (B.1, раздел 0). Вариант «всегда в контексте» — A.8, п. 3.
- Роли — `.claude/agents/specifier.md`, `hardener.md`, `reviewer.md` загружаются Kimi как есть через `extra_agent_dirs`:
  их frontmatter разбирается как YAML, `tools: Read, Grep, Glob, Edit, Write, Bash` — те же имена инструментов Kimi,
  `model` и `color` Kimi пропускает (проверено разбором, D.4). Тексты ролей местами обещают хук («a hook enforces it»,
  SubagentStop у hardener) — в Kimi это не так, и блок поправок в начале prompt говорит это роли прямо (B.4).
- Хуки `guard.py`, `stop_gate.py`, `session_start.sh` — запускаются мостом из рабочей копии проекта, без правок: мост
  только переводит событие Kimi в форму, которую они читают, и добавляет пути Kimi к путям человека.
- Задачи Gradle, `gauntlet.properties`, CI, integrity — без изменений.
- Своё у адаптера: инструкция Kimi, пять карточек, два главных агента, мост, настройки пользователя.

### A.6. Как запускать
**Координатор** (в корне клона):
```
ORG_GRADLE_PROJECT_publicRepositories=true kimi --agent gauntlet-coordinator --add-dir <каталог плана>
```
Затем `/model` (K3.1 Pro) и `/effort max`, первым сообщением — `coordinate` и путь к плану.

**Сессия шага** — по команде и промпту, которые координатор выдаёт владельцу (B.2, раздел «Промпт сессии шага»):
`git worktree add ../<repo>-step-<N> -b <ветка> origin/<основная>`, затем в ней `kimi --agent gauntlet-task --yolo`,
`/model`, `/effort`, промпт первым сообщением. `/new` в такой сессии не использовать: новая сессия пойдёт с агентом по
умолчанию.

**Карточка сабагентом из другой среды** (черновик раздела 6 ядра, маршрут «CLI другого вендора»; например, координатор
в Claude Code отдаёт Kimi карточку только для чтения):
```
sha=$(git rev-parse origin/main)
wt=<каталог из gauntlet-projects.txt>/cards/<N>-<k> && git worktree add --detach "$wt" "$sha"
cd "$wt" && KIMI_MODEL_THINKING_EFFORT=max timeout 3600 kimi --agent gauntlet-card-mapper -m <алиас K3.1 Pro> \
    --output-format stream-json -p "$(cat <файл карточки>)" > <каталог плана>/card-<k>.jsonl 2> <каталог плана>/card-<k>.err
echo "exit $?"                                    # 0 — завершилась; 1 — ошибка; 4 — сессия занята; 124 — истёк timeout
jq -rs '[.[] | select(.role == "assistant" and (.content // "") != "" and ((.tool_calls // []) | length) == 0)]
        | last | .content // empty' <каталог плана>/card-<k>.jsonl > <каталог плана>/card-<k>.md
git -C "$wt" status --porcelain                   # пусто — карточка ничего не меняла
git worktree remove "$wt"
```
`-p` — последним, с текстом карточки: `-p, --prompt <prompt>` берёт следующее слово как текст (commander), и в форме
`kimi -p --agent …` из `reference/kimi-command.md` текстом стал бы `--agent`, а имя агента — неизвестной командой; верная
форма — как в `guides/print.md` (`kimi --agent reviewer -p "…"`). Отчёт — всё последнее сообщение целиком: `tail -n 1`
из примера вендора оставил бы от отчёта в четыре раздела одну последнюю строку. В `-p` нет подтверждений (режим Never
Ask), правила `deny` и хуки действуют; режима только чтения, которого ждёт черновик раздела 6 ядра, у Kimi нет: чтение
держат список инструментов агента (у `gauntlet-card-critic` нет shell) и проверка `git status` после карточки. Рабочую
копию карточки кладите под каталог из `gauntlet-projects.txt`, иначе мост в ней молчит. Алиас модели — из
`kimi provider list --json` (после `kimi login`
модели Kimi Code заводятся как `kimi-code/<id>`; для K3.1 Pro имя `kimi-code/k3.1-pro` выведено по аналогии с
`kimi-code/k3` из документации и не подтверждено). Отчёт принимается строже (черновик раздела 6 ядра, п. 5): назван
коммит, перепроверяются два утверждения, одно из них ключевое, и каждое «ничего не найдено»; ненулевой код выхода, пустой
или бесформенный отчёт — карточка не выполнена.

### A.7. Проверка установки
1. `kimi doctor config` — файл настроек разобран.
2. В корне клона: `python3 -I -B gauntlet/adapters/kimi/test_kimi_hooks.py . gauntlet/adapters/kimi/kimi_hooks.py` — 17
   тестов моста против хуков этого набора (нужны `git` и `python3`, для теста блокировки сборки — `java`);
   `python3 -B gauntlet/adapters/kimi/check_files.py gauntlet/adapters/kimi .` — форма настроек и агентов (нужен PyYAML).
3. В клоне `kimi --agent gauntlet-task`, первым сообщением: «Приведи строку статуса gauntlet и перечисли subagent_type,
   которые разрешает тебе инструмент Agent». Ожидается строка `[gauntlet] active - …; guard: on; stop hook: on; …` и
   ровно `specifier, hardener, reviewer, gauntlet-card-framework, gauntlet-card-refuter, gauntlet-card-repro`.
4. Там же: «Прочитай gauntlet/README.md инструментом Read и допиши в его конец пустую строку инструментом Write
   (`mode: append`)». Ожидается отказ среды с текстом `[gauntlet guard] … human-owned` или правилом `deny`. Без Read
   Write в существующий файл Kimi отклоняет сам («requires a prior Read», `reference/tools.md`) — такой отказ проверкой
   охраны не считается. Записалось — хуки или правила не подключены; не работать до исправления.
5. После обновления Kimi — снова п. 2–4 до начала работы.

### A.8. Решения владельца (ответ «1) да 2) …»)
1. Файлы адаптера — в наборе, `gauntlet/adapters/kimi/` (так их охраняют guard и CI без новых правил). Рекомендую: да.
2. Расширить `HUMAN_OWNED` в `guard.py` и список `owned` в `gauntlet-kit.yml` путями `AGENTS.md`, `agents.md`,
   `.kimi-code/`, `.agents/`, `.mcp.json` (сейчас их охраняет только мост в сессиях Kimi, CI — нет), а для CI — и
   вложенными `**/AGENTS.md`, `**/.kimi-code/**` (Kimi читает их в каталогах от корня до рабочего; мост их не видит,
   правила `deny` закрывают только Write/Edit). Рекомендую: да, отдельным PR набора.
3. Корневой `AGENTS.md` оставить свободным или нейтральным: его читают и другие среды (Codex), а Kimi читает его вместе с
   `.kimi-code/AGENTS.md`. Если в проекте нет других агентов, читающих `AGENTS.md`, можно сделать его ссылкой на
   `gauntlet/CLAUDE.md`: тогда полный текст правил всегда в системном промпте Kimi (сам файл ≈68 КБ, с инструкцией ≈93 КБ —
   выше рекомендации Kimi в 32 КБ: будет предупреждение и рост цены каждого запроса). Рекомендую: не делать, оставить чтение с
   доказательством.
4. Сессии шагов — в режиме Ask When Needed (`--yolo`): обычные правки без подтверждений, опасные команды — с
   подтверждением, `deny` и хуки действуют. Always Ask — подтверждать каждую правку и команду. Never Ask (`--auto`) для
   сессий шага — нет: агент не задаёт вопросов, а процесс требует остановки. Рекомендую: `--yolo`.
5. Отдельный каталог данных Kimi для работ gauntlet (`KIMI_CODE_HOME=~/.kimi-gauntlet`): хуки и правила не задевают
   другие проекты, но вход (`kimi login`) — отдельный. Рекомендую: по желанию.
6. Версию Kimi закрепить (2.7.3), автообновление выключить, обновлять осознанно с проверкой A.7. Рекомендую: да.
7. `[secondary_model]` для работ gauntlet не настраивать: без него сабагенты наследуют модель и уровень вызывающего; с ним
   — уровень `default_effort` или уровень модели по умолчанию, то есть тоньше. Рекомендую: не настраивать.
8. Внешний ревьюер PR при сессиях на Kimi — другой вендор (метод, 1.1 п. 19). Рекомендую: да.
9. Маршрут карточек — свои сабагенты Kimi; внешний — только по вашему решению на задачу. Рекомендую: свои.

## B. Промпты

### B.1. Инструкция проекта: `gauntlet/adapters/kimi/AGENTS.md` (Kimi читает её как `.kimi-code/AGENTS.md`)
Kimi собирает инструкции так: `~/.kimi-code/AGENTS.md`, первый непустой из `~/.agents/AGENTS.md`/`agents.md`, затем для
каждого каталога от корня репозитория до рабочего — `.kimi-code/AGENTS.md` и первый непустой `AGENTS.md`/`agents.md`;

### B.4. Роли specifier, hardener, reviewer
Новых файлов ролей нет: Kimi загружает `.claude/agents/*.md` набора через `extra_agent_dirs` (B.6). Что в текстах ролей в

| Роль | В тексте роли | В Kimi |
|---|---|---|
| specifier | «You may only write under … features … (a hook enforces it)» | хук не знает агента: заморозка после `spec:` исполняется, область «только фичи» — нет; фичи только через Write/Edit (Bash-запись в фичи guard отклоняет) |

## D. Пределы и источники

### D.1. Что не переносится
- **Права ролей.** В событиях хуков Kimi нет ни `agent_type`, ни id агента (код `runPreToolUse`, `runStop`), поэтому
  guard не может ограничить specifier фичами, hardener тестами, reviewer чтением. Держится: список инструментов агента
  (у критика нет записи вовсе), запись в фичи только инструментами Write/Edit и заморозка после `spec:` (их guard
  исполняет для всех), сверка `git status`/`git diff` основной сессией, integrity, CI и diff PR. Обратная сторона: до
  коммита `spec:` черновик фич через Write/Edit может записать любой агент, а не только specifier (мост считает такую
  запись записью specifier); «фичи пишет только specifier» здесь держит промпт, а не хук.
- **Stop-гейт.** Kimi продолжает ход по блоку Stop-хука один раз: следующий конец того же продолжения хук не проверяет
  (`stopHookContinuationUsed` выставляется и не сбрасывается), новая проверка — в конце следующего хода пользователя.
  Хук живёт не дольше 600 с; прогон `gauntletFast` дольше бюджета моста (560 с на все модули) — красный «TIMEOUT», а
  убитый по таймауту хук — пропуск без вердикта. Поэтому доказательство зелёного — собственный прогон агента.
- **Гейт hardener'а** (SubagentStop) — нет: событие только наблюдает.
- **Строка статуса** приходит не при старте сессии, а с первым сообщением владельца. Docker хук набора поднимает только в
  облаке Claude Code (`CLAUDE_CODE_REMOTE=true`); у Kimi облака нет, Docker — забота владельца.
- **Хуки — только у владельца.** Файла хуков в проекте Kimi не бывает: на машине без настроек B.6 защиты нет вовсе,
  остаются инструкция, CI и diff PR. Битый `config.toml` Kimi не останавливает: сессии идут на последних годных или
  встроенных значениях («sessions continue with default or last-known-good validated values», `configuration/config-files.md`,
  раздел `permission`) — признак: нет строки статуса в первом ответе (инструкция, раздел 0) и ошибка `kimi doctor config`.
- **Нет песочницы ОС.** «The environment is not a sandbox» — системный промпт Kimi. Карточки с Bash читают по промпту;
  нарушение видно по `git status` после карточки.
- **Координатор** не открывает сессии, не пишет в них и не подписан на PR — всё через владельца.
- **Атрибуция ходов** в мосте — по порядку событий TurnStarted/Stop (агента в них нет). Ошибается она в обе стороны.
  (1) Ход сабагента, который начала его законченная фоновая задача (`origin_kind: task`, без имени), — например,
  ход hardener'а после фонового `mutationGate`, — мост считает ходом главного агента: в конце такого хода идёт Stop-гейт
  всей рабочей копии (до 560 с), а при красном Kimi один раз продолжает ход сабагента сообщением «RED … fix the
  causes». Stop-сообщение моста велит сабагенту править только в пределах роли (карточки и reviewer — ничего);
  остальное держат промпт роли, сверка `git status`/`git diff` основной сессией и CI. Различать такие ходы по
  «начался внутри открытого хода» нельзя: когда фоновая задача главного агента заканчивается посреди его хода, Kimi
  завершает этот ход без Stop (`deferForRequest` → `turn.finish`, уведомление в очереди, `hasPendingRequests`) и
  начинает ход `task` — такая эвристика пропускала бы гейт главного агента. (2) Сабагентский ход с тем же номером,
  что у хода главного агента, оставшийся без Stop, может забрать себе Stop главного — пропуск одной проверки, её делает
  следующий ход.
- **Удалённые окружения Kimi** (`--environment`, `[environments] default`): инструменты агента идут на цели, а хуки —
  на локальной машине по локальному каталогу («never on the target», `customization/hooks.md`). Guard и Stop-гейт
  моста там проверяют не ту копию. Для работ gauntlet — только локальная сессия, без `[environments] default`.
- **Вложенные инструкции.** Kimi читает `AGENTS.md`/`agents.md` и `.kimi-code/AGENTS.md` в каждом каталоге от корня
  до рабочего, а его системный промпт велит смотреть `AGENTS.md` подкаталогов. Мост охраняет только корневые (guard
  сравнивает пути от корня), правила `deny` — вложенные для Write/Edit; запись вложенных через shell и CI не видят
  (A.8, п. 2).
- **Обновления Kimi** могут поменять форму событий: мост проверен на 2.7.3.

### D.2. Сбои Kimi Code и моделей K3, относящиеся к жалобе владельца
1. **Встроенный `explore` — «быстрый».** Профиль: «Fast codebase exploration with prompt-enforced read-only behavior»;
   его промпт: «You are meant to be a fast agent. Complete the search request efficiently»; глубину задаёт вызывающий
   («quick», «medium», «thorough»). Ответ: карточки — свои агенты; у главных агентов список `subagents` без `explore`.
2. **Короткий итог больше не возвращается.** 0.41.0 (#3459): «Subagent final messages are no longer bounced back for
   expansion when they are under 200 characters». Ответ: форма отчёта (`kimi_hooks.py report`) и возврат координатором.
3. **Сабагентов по умолчанию нет.** 2.3.2 (#4386): «Handle tasks directly by default instead of proactively launching
   subagents; request delegation explicitly in your message, AGENTS.md, a skill …». Описание инструмента `Agent`:
   «requests for depth, thoroughness, research, or investigation do not [authorize]; do that work yourself». Ответ:
   инструкция и главные агенты называют, кого и когда звать.
4. **«Не повторяй работу сабагента».** Описание `Agent`: «do not redo its searches or reads in parallel». Ответ:
   перепроверка после отчёта названа обязательной (ядро 2.2) в инструкции и промпте координатора.
5. **Обрыв сабагентов в `kimi -p`** до 2.7.0 (#4868: «Fix subagents timing out immediately in `kimi -p` …»). Ответ:
   версия не ниже 2.7.0.
6. **Stop-хук не срабатывал после каждого хода** до 2.6.3 (#4995). Ответ: версия не ниже 2.7.0.
7. **Среда торопит закончить ход.** Bash на переднем плане — 60 с по умолчанию, не больше 300 с, фоновые задачи — 600 с по умолчанию, `WaitFor` —
   до 90 с, со второго вызова за ход — совет «Stop calling WaitFor…» (сабагенту — «Stop waiting by reflex…»). Одинаковый
   вызов подряд: с 3-го — напоминание, с 5-го — выбор, где третий вариант «Conclude: deliver your best result», с 8-го —
   «Write your final response now», после 12-го ход обрывается (`toolDedupeService`: `REPEAT_REMINDER_2_START = 5`,
   `REPEAT_REMINDER_3_START = 8`, `REPEAT_FORCE_STOP_STREAK = 12`); сабагент, оборванный так, возвращается вызывающему
   со `status: completed`, `stop_reason: repeat_breaker` и пометкой «handoff, not a finished result», а при сбое
   сабагента среда советует вызывающему «take over the task yourself». Ответ: `bash_task_timeout_s = 0`, долгий Gradle —
   фоном, «прогон идёт» — не «готово», доказательство — строки `> Task`; вынужденный итог — с непокрытым в «Не
   проверено»; приёмка смотрит `status` и `stop_reason` (инструкция, раздел 6; координатор, «Ведение»).
8. **Неполный поиск.** Grep по умолчанию — имена файлов и `head_limit` 250, Glob — 100 путей, Read — страница до 100 000
   символов и ~25 000 оценочных токенов (не-ASCII — токен на символ). Ответ: в каждой карточке — `count_matches`,
   `head_limit: 0`, все страницы `Next Read`.
9. **Сводка после сжатия контекста.** Промпт Kimi: «Treat that summary as an accurate record: do not redo work it
   reports as done». Ответ: статус гейта — только новым прогоном, приёмка — по файлам отчётов на диске (инструкция,
   разделы 4 и 8).
10. **Цель «выполнена» по самооценке.** В goal mode завершение объявляет сама модель (`UpdateGoal`), а вендор в 0.23.1
    ужесточал подсказки, «so agents continue … instead of ending goals prematurely». Ответ: goal mode — инструмент
    владельца, «выполнено» — только с зелёным гейтом.
11. **Подгонка под проверяющего у K3.** По выдаче поиска со страницы Handshake о DeepSWE (сама страница не открывалась,
    второй поиск этой находки про K3 не нашёл, а аудит DeepSWE другие источники приписывают Datacurve): среди решений с

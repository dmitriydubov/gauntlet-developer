# Адаптер gauntlet для Qwen 4 Max (Qwen Code)

Ревизия адаптера 1, 2026-11-24, с исправлениями независимой проверки того же дня (раздел «Проверка» в конце: что
исправлено и почему). Язык — русский, как `gauntlet/CLAUDE.md`; ключи настроек, имена файлов, событий и

## A. Что это и куда ставить

### A.1. Что такое «qwen 4 max» и где он работает
- **Модель.** Qwen4-Max — флагманская модель Alibaba (семейство Qwen 4), идентификатор в API и в Qwen Code — `qwen4-max`.
  Вышла 16.11.2026 [W1–W4]. Числа из анонсов — 2,4 трлн параметров (MoE, ~71 млрд активных), контекст 1 млн токенов,
  только облако (QwenCloud API, Token Plan, Qwen Studio, QwenWork, Qoder), без открытых весов — по вторичным источникам
  и сниппету официального блога: страницы qwen.ai из этой сессии не открываются, «не подтверждено» первоисточником.
- **Что подтверждено первоисточником.** Qwen Code 0.28.0 (17.11.2026): «add qwen4-max support with native effort ladder,
  cache TTL, and image detail (#17513)» [S22]. Документация 0.28.4, «qwen4-max specifics» [S13]: каналы — ModelStudio
  Standard, Token Plan, QwenCloud Standard и подписка Qwen (Qwen OAuth); лестница рассуждений `low` / `high` / `xhigh`,
  **по умолчанию `high`**; `medium` поднимается до `high`, `max` сводится к `xhigh`, `none` выключает рассуждения;
  `max_tokens` покрывает рассуждения и ответ вместе — 262 144 с рассуждениями, 131 072 без; на подписке уровень
  превращается в `thinking_budget` (`low` → 4096, `high` → 131072, `xhigh` → 262144). В коде пакета окно контекста
  `qwen4-max` — 1 000 000 [S1: `chunks/chunk-MVDL2G4R.js`, `QWENCLOUD_MODELS`].
- **Где она работает как агент.** Qwen Code — открытый агент Qwen для терминала (Apache-2.0); начинался как форк Gemini CLI
  v0.8.2 и с v0.1 развивается отдельно [S23]. Версия на дату адаптера — **0.28.4** (`npm view`: `latest`, опубликована
  22.11.2026, Node ≥ 22) [S1]. Адаптер написан для неё. Не покрыты: **Qwen Code 1.0 Preview** (ветка `v1.0.0-preview`,
  свой установщик, «some interfaces, configuration options, and behaviors may change») [S24], Qoder и QwenWork — у них
  свои среды, их хуки и сабагенты здесь не изучались.

### A.3. Что настроить
1. **Установка.** `npm install -g @qwen-code/qwen-code@0.28.4` (Node 22+), `qwen --version` → `0.28.4`. Версию фиксировать:
   контракт хуков «forward-extensible», поля добавляются [S2, «Hook Input Structure»]; после обновления — A.6 заново.
2. **Модель.** В сессии `/auth` → QwenCloud (Token Plan или Standard API Key), Alibaba ModelStudio или «Qwen Account with
   Subscription» [S14]; `/model` → `qwen4-max`; `/effort xhigh` (или `model.reasoningEffort` в `~/.qwen/settings.json`) —
   рекомендация A.7, п. 4.
3. **Окружение.** `ORG_GRADLE_PROJECT_publicRepositories=true` в окружении, из которого запускается `qwen` (иначе сборка
   пойдёт в корпоративный реестр: `gauntlet/CLAUDE.md`, «Среда облачной сессии»); Docker запущен (Testcontainers);
   `python3` и `git` в `PATH` — на них хуки набора.
4. **Запуск — из корня репозитория.** `QWEN_PROJECT_DIR`, `CLAUDE_PROJECT_DIR` и `GEMINI_PROJECT_DIR` Qwen Code ставит
   хуку равными рабочему каталогу сессии [S1: `commandInvocation`]; из подкаталога путь к скрипту хука неверен, а
   `python3` без файла выходит с кодом 2 — для Qwen Code это блокировка: каждая правка и каждая остановка будут
   отклонены с текстом «can't open file» (воспроизведено тестом, раздел D.5).
5. **Одобрение хуков.** Хуки проекта не работают, пока владелец их не одобрил: при первом запуске Qwen Code показывает
   их и спрашивает; решение хранится в `~/.qwen/hookApprovals.json` и привязано к точной конфигурации хуков, к `.env`
   проекта и `settings.env`: любая их правка — вопрос заново; Esc откладывает [S2, «Approving project hooks»]. Ключ
   записи — корень проекта, рядом — sha256 хуков с окружением [S1: `chunks/chunk-62ZGP54Z.js`,
   `LoadedHookApprovals.getState`, `hashProjectHooks`]: новый `git worktree` сессии шага — новый ключ, одобрить и там.
   Без интерактива (`qwen -p`) Qwen Code не спрашивает: неодобренные хуки не грузятся, в stderr — одна строка [S2].
6. **Не включать для сессий задач** `tools.executionSandbox`: в этом режиме Qwen Code выключает исполняемые хуки
   [S9; S1: `getHookSystem(){if(this.shellExecutionSandbox)return void 0 …}`] — guard и stop-gate молча пропадут.
   Песочница Docker/Seatbelt (`--sandbox`) с Gradle и Testcontainers не проверялась.
7. **Если хуки нужны без интерактива и без одобрения** (выделенный раннер): хуки системных настроек
   `/etc/qwen-code/settings.json` (или `QWEN_CODE_SYSTEM_SETTINGS_PATH`) грузятся независимо от доверия к папке [S2,
   «Hook Configuration»; S6, «Settings files»], а агент, работающий не от root, их не правит. Запуск без интерактива с
   `--yolo` (или `--approval-mode yolo`) в командной строке тоже грузит проектные хуки как одобренные, но одобряет и все
   вызовы инструментов [S2, «Approving project hooks»; S10, «Safety in unattended runs»] — только в одноразовом
   окружении; интерактивного YOLO это не касается.
8. **Ручки тщательности и где они стоят.** Уровень рассуждений — на сессию (`/effort`, `model.reasoningEffort`), у
   `qwen4-max` верх лестницы `xhigh` [S13]. Потолков ходов в адаптере нет: `model.maxSessionTurns` по умолчанию `-1`,
   у агентов `maxTurns` не задан; на ход — адаптивные 100 вызовов инструментов (`model.maxToolCallsPerTurn`): останавливает
   ход только на зацикливании и на жёстком пределе 1000, но на той же отметке 100 «долгая непрерывная фаза только
   чтения» получает одно напоминание свернуть исследование [S6, `model.maxToolCallsPerTurn`; текст — D.2, п. 9]. Значение
   `0` или меньше убирает и напоминание, и предел 1000 [S6; S1: `getMaxToolCallsPerTurn`] — это решение владельца, в
   адаптере не задано. Авто-сжатие — около 85 % окна (`context.autoCompactThreshold`) [S6]. Режим `plan`
   (`/plan`, `--approval-mode plan`) — только анализ, без правок и без команд оболочки [S7]: для карточек не годится, им
   нужны `git grep`, `javap`, Gradle; а `approvalMode: plan` у сабагента при разрешительной сессии не держится [S3].
   Goals (`/goal`) — решение A.7, п. 7. Без интерактива — `--max-session-turns`, `--max-wall-time` (A.5).

Что делает каждый блок `.qwen/settings.json` — раздел B.5.

### A.4. Как переиспользуются файлы набора, а не копируются
- **Процесс и жёсткие правила.** `QWEN.md` включает `gauntlet/CLAUDE.md` строкой `@gauntlet/CLAUDE.md`. Импорт Qwen Code:
  путь от каталога `QWEN.md`, глубина не больше 5, только внутри корня проекта, `@` внутри кода (`` `…` ``, блоки) не
  раскрывается [S5, «Reference other files»; S1: `processImports`, `validateImportPath`, `findImports`]. В
  `gauntlet/CLAUDE.md` нет `@` вне кода (проверено), так что он попадает в контекст как есть.
- **До сабагентов** тот же контекст доходит сам: системный промпт сабагента собирается с файлами контекста сессии
  [S1: `renderSubagentSystemPrompt` → `assembleSystemPrompt({contextFiles: runtimeContext.getUserMemory(), …})`].
- **Роли.** Агенты `.qwen/agents/<роль>.md` тонкие: первым действием роль читает свой файл набора
  `.claude/agents/<роль>.md` и следует ему; агент Qwen Code добавляет только замены механизмов, чек-лист тщательности
  и формат отчёта. Чтение доказывается строкой `файл:строка` с цитатой в отчёте. Обновление роли в наборе доходит до
  Qwen Code без правки адаптера.
- **Хуки.** `guard.py`, `stop_gate.py`, `session_start.sh` не меняются. `Stop`, `SubagentStop` и `SessionStart` Qwen Code
  вызывает их напрямую: событие и смысл кода выхода совпадают с Claude Code (раздел B.5). `PreToolUse` и
  `SubagentStart` идут через `qwen_hooks.py`: он загружает `guard.py` как модуль и только переводит имена инструментов,
  определяет роль сабагента и добавляет человеческие пути Qwen Code.
- **Копия одна:** тексты разделов 1 и 3 ядра в `QWEN.md` — `core.md` пока не файл набора. Когда ядро ляжет в набор
  (например, `gauntlet/subagents.md`), копию заменить строкой импорта.

### A.5. Как запускается работа
- **Сессия задачи.** В рабочем дереве шага: `ORG_GRADLE_PROJECT_publicRepositories=true qwen --model qwen4-max -i "$(cat
  <промпт сессии>)"`, затем `/effort <уровень>`. Промпт — приложение D метода с заменами из B.2, раздел 4.
- **Координатор.** В своём рабочем дереве: `ORG_GRADLE_PROJECT_publicRepositories=true qwen --model qwen4-max
  --append-system-prompt "$(cat gauntlet/adapters/qwen/coordinator.md)"`, затем `/effort xhigh` и слово `coordinate`
  с путём к плану. `--append-system-prompt` добавляет текст после встроенного промпта и файлов контекста [S6,
  «Command-Line Arguments»]; в интерактивном режиме флаг не проверялся — запасной путь: первым сообщением «прочитай
  `gauntlet/adapters/qwen/coordinator.md` целиком и следуй ему».
- **Qwen Code как внешний исполнитель карточки** (маршрут «CLI другого вендора» из черновика `routing.md`: координатор
  другой среды отдаёт Qwen Code карточку только на чтение). Отдельный `git worktree` на зафиксированном коммите:

  ```bash
  git worktree add --detach ../precheck-<sha> <sha> && cd ../precheck-<sha>
  qwen -p "$(cat <карточка>.md)" --model qwen4-max --approval-mode default \
    --exclude-tools 'edit,write_file,notebook_edit,agent,save_memory,Bash(git *),Bash(gh *)' \
    --allowed-tools 'Bash(javap *),Bash(cat *),Bash(ls *)' \
    --json-schema @gauntlet/adapters/qwen/report.schema.json \
    --max-session-turns 150 --max-wall-time 45m --output-format json > ../precheck-<sha>.json
  echo "exit=$?"   # 0 — отчёт; 53 — потолок ходов, 55 — бюджет, 130 — прерван: карточка не выполнена
  ```

  Карточка — тело файла агента карточки (B.4) без заголовка плюс входы; коммит `<sha>` координатор пишет во входы сам.
  Почему это только чтение: без интерактива режим `default` (Ask) убирает оболочку, `edit` и `write_file`, если правило
  не разрешило их явно [S7, «Run headless queries in Ask Permissions Mode»]; `--exclude-tools` убирает запись. Но
  правило — это не только `--allowed-tools`: к ним добавляются `permissions.allow` всех слоёв настроек, в том числе
  `.qwen/settings.json` из этого worktree (`Bash(git *)` — значит и `git push`, `git commit`; `Bash(gh pr create *)`,
  `Bash(gh pr comment *)`, `Bash(./gradlew *)`) и `~/.qwen/settings.json` владельца [S6, `permissions.allow`: «Merged across
  all scopes»; S1: `mergedAllow`, `chunks/chunk-OHCM23H2.js`]. Поэтому `git` и `gh` здесь запрещены целиком: записи из
  `--exclude-tools` идут в список запретов (`mergedDeny`), а запрет сильнее любого разрешения [S6, «Decision priority»].
  Код карточка читает инструментами `read_file`, `grep_search`, `glob`; истории git (`git log`, `git show`) у неё нет —
  нужное из истории координатор кладёт во входы. `./gradlew` (проверки) остаётся из настроек проекта — это ядро
  позволяет (правило 1.6). Что команда вне правил в `-p` будет отклонена, а не выполнена, —
  следует из документации режима, живьём не проверено. Хуки проекта в новом worktree не одобрены и не грузятся — опора
  здесь на инструменты и разрешения, а не на guard. `--json-schema` фиксирует форму отчёта (коммит, доказательства,
  раздел «не проверено» обязателен) и завершает прогон на первом валидном ответе [S11]; правдивость доказательств —
  приёмка координатора (ядро, раздел 2, и черновик `routing.md`, п. 5).

### A.6. Проверка установки (до первой задачи и после каждого обновления Qwen Code или набора)
В ветке-песочнице, в корне репозитория:
1. `qwen --version` → `0.28.4`; `python3 gauntlet/adapters/qwen/qwen_hooks.py selftest` → `ok`.
2. `qwen` → диалог одобрения хуков → одобрить. Первое сообщение агента содержит строку `[gauntlet] active - …`; `/hooks`
   показывает `SessionStart`, `SubagentStart`, `PreToolUse`, `Stop`, `SubagentStop`.
3. «Допиши строку в `gauntlet/config/gauntlet.properties`» → отказ `[gauntlet guard] … human-owned` (и через `edit`, и
   через `echo >>`).
4. «Вызови сабагента reviewer: пусть создаст `src/test/java/X.java`» → отказ `The reviewer is read-only`.
5. «Вызови specifier: черновик фичи о …» → файл фичи создан (до коммита `spec:`); после коммита `spec:` повтор — отказ
   «frozen».
6. Внести в `src/main` нарушение гейта (метод длиннее лимита) и попросить закончить → Stop-хук запускает `gauntletFast`,
   агент получает красные строки и продолжает работу; в выводе — «attempt 1/3».
7. `qwen -p "скажи ok"` в каталоге без одобрения хуков → строка в stderr о том, что хуки проекта не загружены.
8. `git ls-files .qwen/.env` → файл в git. Владелец кладёт в корневой `.env` строку `GAUNTLET_PROBE=1` и запускает `qwen`:
   «выполни `printenv GAUNTLET_PROBE`» → пусто (корневой `.env` закрыт заглушкой), ключ API из `~/.qwen/.env` при этом
   работает (по коду 0.28.4 домашние файлы грузятся и после проектного; auth.md называет их запасными — расхождение,
   см. «Проверка»). Строку удалить.
9. Владелец: `GAUNTLET_GUARD=off qwen` → строка статуса `guard: off`, правка `gauntlet/config/gauntlet.properties`
   проходит (ручная поддержка набора); без переменной — снова отказ.
Расхождение на любом шаге — адаптер в этой среде не работает как описано: работа идёт с опорой на раздел 5 `QWEN.md`
и CI, и владелец знает об этом до первой задачи.

### A.7. Решения владельца (ответ «1) да 2) …»)
1. **Человеческие пути Qwen Code — в набор.** Добавить `.qwen/`, `QWEN.md`, `AGENTS.md`, `.qwenignore`, `.agentignore`,
   `.aiignore` в `HUMAN_OWNED` guard'а и в список `gauntlet-kit.yml`. До этого их закрывает прослойка (только когда
   хуки загружены) и `permissions.deny`, а CI правку не видит — её видно только в диффе PR. Рекомендация: да.
   Сюда же — переменные, которые Qwen Code берёт из `.env` при старте и отдаёт хукам [S14, «`.env` files»; S1:
   `findEnvFiles`, `commandInvocation`]: `GAUNTLET_GUARD=off` или `GAUNTLET_STOP_HOOK=off` в таком файле выключили бы

   `Edit(~/.env)` в `deny`; `~/.qwen/.env` уже под `~/.qwen/`.

3. **Режим одобрения** `auto-edit` + список `permissions.allow` (как «Accept edits» набора) или `auto` (классификатор
   модели решает про оболочку; это суждение модели, не охрана) [S7]. Рекомендация: `auto-edit`.
4. **Уровень рассуждений `xhigh`** для координатора и сессий шагов (умолчание `qwen4-max` — `high`). Дороже; отдельного
   уровня для сабагентов нет (B.3, D.1). Рекомендация: да, особенно для тонкой семантики фреймворка.
5. **Внешний ревьюер PR — не Qwen** (метод, п. 19: другой вендор, чем у сессий, пишущих PR). Рекомендация: да.
6. **`context.fileName: "QWEN.md"`** — Qwen Code по умолчанию грузит ещё и `AGENTS.md` [S5; S1:

7. **Goals Qwen Code** (`/goal` с независимым верификатором) для этапа реализации — не по умолчанию: верификатор —
   модель, читает только транскрипт и не запускает команд [S12]; авторитет — гейты и CI. Рекомендация: нет; можно для
   аудитов только на чтение.

````markdown
## 2. Сабагенты
- Роли набора — `specifier`, `hardener`, `reviewer`. Вызывай их на переднем плане (`run_in_background: false`) и жди
  результата: фоновый результат приходит позже уведомлением, и до него его нет.
- Обычный сабагент не видит этого разговора. В задание клади всё: запрос дословно, базу, пути, список файлов.
- Код пишешь ты. Писать файлы хук разрешает только тебе, `specifier` (фичи до коммита `spec:`) и `hardener`
  (тестовый код); любой другой сабагент для guard'а только читает.
- Не используй `subagent_type: "fork"` для проверок: форк наследует весь разговор и уже не независим. Не уводи
  роли в отдельные worktree (`isolation`, `enter_worktree`): одна задача — одна ветка в этом рабочем дереве.
- Отчёт сабагента — данные, а не факт: принимай его по разделу 4.

## 3. Правило тщательности (для тебя и для каждого сабагента)
Тщательность меряется не временем и не токенами, а тем, чем доказано каждое утверждение. Отчёт без доказательств
не принимается, как красный гейт не принимается «на слово».
1. **Доказательство к каждому утверждению.** Каждое утверждение отчёта несёт одно из:
   - команда, которую ты выполнил сам, и её вывод (обрезанный до сути);
   - `файл:строка` с цитатой, которую ты открыл и прочитал в этом сеансе;
   - источник нужной версии (URL документации той версии, что в сборке, или класс в jar/пакете) с цитатой.
   Утверждение без доказательства помечается «не проверено» и идёт в раздел «Не проверено», а не в выводы.
2. **Покрытие чек-листа, а не первая правдоподобная находка.** Задание даёт список того, что надо осмотреть. Отчёт
   называет покрытие числом: «вызовы X: 7 из 7, файлы: перечислены». «Ничего не найдено» — тоже результат, и он
   требует доказательства поиска: чем искал (запрос, команда), где, сколько совпадений.
3. **Читать и запускать, а не вспоминать.** Поведение фреймворка, сигнатура API, значение по умолчанию — из
   документации версии сборки, байткода или прогона; память модели — не источник. Если проверка запуском возможна
   (тест, команда, запрос), запуск предпочтительнее чтения.
4. **Самопроверка перед отчётом.** Перед тем как отчитаться, перечитай свой список утверждений и для каждого ответь:
   «что бы я увидел, если бы это было неправдой?» — и проверь это, если не проверил.
5. **Честный остаток.** Раздел «Не проверено» обязателен: что не осмотрено, почему (нет доступа, нет времени, вне
   задания) и чем это грозит. Пустой раздел допустим, только если чек-лист покрыт полностью.
6. **Без правок.** Сабагенты пред-проверки и ревью ничего не меняют в репозитории (только читают и запускают
   проверки); правку делает тот, чья это роль (кодер, hardener, specifier).
7. **Остановка — по чек-листу.** Заканчивай, когда чек-лист покрыт и каждое утверждение доказано или помечено
   «не проверено», — а не когда нашёл первый ответ или «достаточно уверен».

Что это значит в Qwen Code:
- Qwen Code сам дописывает к промпту обычного сабагента «используй инструменты, только когда необходимо». Здесь
  необходимость задаёт чек-лист: каждый его пункт закрывается вызовом инструмента или идёт в «Не проверено».
- Команда, оборванная таймаутом (`Command timed out after …`), — не результат: её вывод неполон, гейт не зелёный.
- Длинный вывод Qwen Code обрезает, а сжатие контекста (`/compress`, авто при ~85 %) и очистка старых результатов
  инструментов после простоя убирают доказательства из разговора. Вывод Gradle пиши в файл и ищи в нём; после
  сжатия или перерыва повтори проверку, прежде чем на неё ссылаться. Пересказ — не доказательство.
- Прежние сообщения разговора, в том числе твои, — зацепки, а не факты: перепроверь у источника, прежде чем повторять.
- После долгой серии чтений и поиска подряд (около 100 вызовов) Qwen Code вставляет напоминание «this read-only
  exploration phase has reached the configured tool-call allowance … summarize the findings». Это не условие
  остановки: заканчиваешь по чек-листу. Если чек-лист ещё не покрыт, продолжай; что не успел, перечисли в
  «Не проверено» с причиной.

## 4. Отчёт сабагента и его приёмка
Формат отчёта каждого сабагента (роль добавляет к нему свой итог, например `VERDICT` ревьюера):
```
## Итог
<одна-две строки: ответ на вопрос задания>

## Проверено (покрытие: N из M по чек-листу)
1. <утверждение> — доказательство: `<команда>` → <вывод> | `<файл:строка>`: «<цитата>» | <URL, версия>: «<цитата>»
2. ...

## Не проверено
- <что> — <почему> — <чем грозит>

## Вопросы и риски для координатора
- ...
```
Приёмка (ты — в сессии задачи, координатор — в пред-проверке):
1. Утверждения без доказательств или нет раздела «Не проверено» — отчёт возвращается сабагенту с перечнем
   недостающего (доработка отчёта, не новый раунд работы; не больше двух возвратов, затем — «не проверено» и
   вопрос владельцу).
2. Минимум одно утверждение из каждого отчёта проверь сам тем же способом (команда, `файл:строка`, источник).
   Расхождение — отчёт не принят целиком, задача уходит другому сабагенту (новый вызов, не продолжение).
3. Утверждение, на котором держится решение, проверяет второй, независимый сабагент с задачей опровергнуть; ему не
   передают вывод первого — только вопрос и пути. При неуверенности — «опровергнуто».
4. В план, отчёт PR и промпт сессии утверждения идут с пометкой: «доказано (как)», «опровергнуто», «не проверено».

## 5. Перед словом «готово» (всегда; если Stop-хук не загружен — единственная опора)
1. Сам, на переднем плане, без параметра `timeout` короче прогона, из корня репозитория:
   `./gradlew gauntletFast --continue --console=plain > build/gauntlet-fast.log 2>&1; echo "exit=$?"`
   (в монорепо — в каждом модуле, где ход менял код: `cd core && ./gradlew … > build/gauntlet-fast.log 2>&1`, лог
   тогда `core/build/gauntlet-fast.log`).
2. `python3 gauntlet/hooks/stop_gate.py --verify-ran gauntletFast --log build/gauntlet-fast.log` (из корня, путь к
   логу — его) — код 0: Gradle выполнил каждую задачу гейта. Иначе прогон не считается, как бы ни выглядел вывод.
3. В отчёт — код выхода, строки `> Task …` каждой задачи гейта и итог:
   `grep -E '^> Task |BUILD (SUCCESSFUL|FAILED)|^gauntlet: ' build/gauntlet-fast.log`.
4. Финал (шаг 8 процесса) — так же для `./gradlew gauntlet --continue` (`--verify-ran gauntlet`).
5. Красный гейт или отказ `--verify-ran` — работа не сделана; так и напиши, с причинами. Решает CI.

## 6. Известные сбои Qwen Code и что ты делаешь
- **Фоновые сабагенты.** По умолчанию сабагент верхнего уровня уходит в фон, и его результат приходит позже
  уведомлением. Роли — только на переднем плане; результат фонового сабагента не предполагай, пока не пришло
  уведомление.
- **Таймаут оболочки.** Без настройки команда на переднем плане обрывается через 2 минуты, параметр `timeout`
  вызова — не больше 10 минут. В `.qwen/settings.json` таймаут поднят до 60 минут; не передавай свой `timeout`
  прогонам Gradle.
- **Хуки не загружены.** Без одобрения проектные хуки молча не работают (в `qwen -p` — одна строка в stderr).
  Признак — нет строки статуса (раздел 0).
- **Потолок Stop-хука.** Qwen Code отпускает после 8 блокировок подряд, набор — после 3. Отпущенный с красным
  гейтом — не «готово».
- **Без интерактива.** В `qwen -p` режимы Ask и Auto убирают оболочку и запись, если правило не разрешило их явно.
  Чего не смог запустить — «не проверено», а не вывод из чтения кода.
- **Напоминание «подведи итог».** На длинной серии одних чтений Qwen Code просит свернуть исследование (раздел 3).
  Покрытие чек-листа важнее: напоминание не разрешает ни остановиться раньше, ни писать файлы.
- **Переменные из `.env`.** Qwen Code при старте берёт переменные из `.qwen/.env` проекта и из `~/.env`, и они
  доходят до хуков набора. Не создавай и не правь такие файлы ради Qwen Code: охрана хуком и `permissions.deny`
  закрывает их, а выключать охрану (`GAUNTLET_GUARD`, `GAUNTLET_STOP_HOOK`) может только владелец.
````

````markdown

Ты — координатор серии задач по методу gauntlet (метод, раздел 1.1, п. 11, и раздел 8.3). Ты ведёшь план, пишешь

## 0. Старт
- Слово владельца `coordinate` (без косой черты: `/coordinate` в Qwen Code — встроенный навык Agent Team, не этот
  протокол). Прочитай план (файл, который назвал владелец), найди в нём ход выполнения и ревизию.

- Твоё рабочее дерево — отдельное от сессий задач (своя ветка координатора). Сессии задач работают в своих
  `git worktree` рядом с репозиторием, не внутри `.qwen/`.

## 1. Цикл одной задачи (метод, раздел 8.3, с заменами для Qwen Code)
1. Владелец пишет, что шаг закрыт. Проверь мерж (`gh pr view <N> --json state,mergedAt,mergeCommit`), `git fetch`,
   запиши итог шага в план: PR, что вошло, открытые вопросы из отчёта.
2. Задача для Jira в чат (шаблон метода, раздел 3), затем пред-проверка (раздел 2 ниже). Результат — файл рядом с
   планом. Для задачи выбора значения или версии — таблица решений, атакованная критиком, и цели граничных тестов.
3. Пред-проверка меняет объём или оценку — дополнение к задаче и вопросы владельцу нумерованным списком
   («ответьте здесь» / решение). Сессию готовишь только по команде владельца.
4. Рекомендация модели и уровня с обоснованием (раздел 5), решает владелец. Затем подготовь сессию задачи — облачного
   инструмента создания сессий здесь нет:
   - `git worktree add ../<репозиторий>-step-<N> -b <ветка шага> origin/<основная ветка>`;
   - промпт сессии — файл вне репозитория, `../<репозиторий>-step-<N>.prompt.md`: приложение D метода с заменами
     раздела 4 ниже; пустые пункты — словом «нет»;
   - команда владельцу: `cd ../<репозиторий>-step-<N> && ORG_GRADLE_PROJECT_publicRepositories=true qwen --model
     qwen4-max -i "$(cat ../<репозиторий>-step-<N>.prompt.md)"`, затем `/effort <уровень>`. При первом запуске в новом
     каталоге Qwen Code спросит одобрение хуков проекта: без одобрения guard и stop-gate там не работают;
   - в план: путь worktree, ветка, имя сессии (`qwen sessions ps`).
5. Решения владельца, пришедшие, пока сессия работает, передай в неё сам: `list_agents` (раздел `sessions`) и
   `send_message` с текстом «Решение владельца от <дата>, дословно: 1) … 2) …». Qwen Code помечает такое сообщение
   как пришедшее от другой сессии, без власти её пользователя: утверждение спецификации («да») владелец пишет в сессию
   задачи сам. Сообщение удержано (`/peers` у получателя) или отклонено — владелец вставляет текст сам.
6. PR открыт: `gh pr checks <N>`, `gh pr view <N> --comments`; периодически — `/loop 30m проверь PR <N>: CI и
   комментарии внешнего ревьюера без ответа` (задача живёт, пока открыта твоя сессия). Ответы внешнему ревьюеру на PR
   шага пишет сессия шага; ты следишь, чтобы ни один не остался без ответа. Приёмка реализации — не больше двух
   раундов замечаний, каждое — «дефект» или «правило»; счёт раундов — в плане.
7. После мержа — проверка результата (метод, раздел 1.1, п. 21): `git worktree add --detach ../<репозиторий>-main-check
   origin/<основная>`, Docker поднят, там `./gradlew gauntlet --continue --console=plain > build/gauntlet.log 2>&1`, затем
   `python3 gauntlet/hooks/stop_gate.py --verify-ran gauntlet --log <путь к логу>`; код против описания PR и
   спецификации; остатки — в план; worktree шага — `git worktree remove`, сессию шага закрывает владелец.
8. Правку замороженной спецификации и строки allowlist RUN_ERROR (метод, раздел 8.3, п. 8) охраняемая сессия сделать
   не может: guard закрывает эти пути. Их вносит владелец на GitHub или сессия, которую он сам запускает без охраны
   (`GAUNTLET_GUARD=off qwen` в своём терминале); ты готовишь точный текст правки и проверку.
9. Документы для соседних команд — языком рабочего контура (метод, раздел 1.1, п. 25).

## 2. Пред-проверка карточками ядра
- Карточки — агенты `.qwen/agents/`: `precheck-mapper` (4.1), `precheck-framework` (4.2), `precheck-critic` (4.3),
  `precheck-refuter` (4.4), `review-repro` (4.6). Все только читают: хук держит это для любого сабагента, кроме
  `specifier` и `hardener`.
- Запуск — несколько вызовов `agent` в одном сообщении; карточки по определению идут в фоне. Жди уведомлений всех
  запущенных карточек, прежде чем сводить: результата, которого не пришло, нет.
- Задание карточке самодостаточно (карточка не видит твоего разговора): коммит (`git rev-parse HEAD`), задача, срез или
  утверждения или таблица, пути, база; напомни формат отчёта — `QWEN.md`, раздел 4.

  дизайна и таблица решений; 4.4 — по одной на каждое утверждение, на котором держится решение (раздел 3, п. 3).
- Никогда не `subagent_type: "fork"`: форк наследует твой разговор и не независим.
- Фоновая карточка не может спросить разрешения: команду, которой нужно одобрение (нет правила в
  `permissions.allow`), Qwen Code ей отклоняет. Такой отказ — «не проверено» в её отчёте; реши сам: перезапустить карточку на переднем плане (`run_in_background: false`,
  разрешение даёт владелец) или проверить пункт самому.

## 3. Приёмка отчёта (ядро, раздел 2) — по доказательствам, а не по усилию
Ты не пересказываешь отчёт сабагента как факт, пока не принял его.
1. **Отказ без доказательств.** Отчёт, в котором утверждения не несут доказательств или нет раздела «Не проверено»,
   возвращается сабагенту с перечнем недостающего (это не новый раунд работы, а доработка отчёта; не больше двух
   возвратов, затем — пометка «не проверено» и вопрос владельцу). В Qwen Code: `send_message` тому же агенту
   (`task_id` из `list_agents`); если `list_agents` даёт `resume_blocked_reason` — новый вызов той же карточки с её
   прежним отчётом и перечнем недостающего.
2. **Выборочная перепроверка.** Минимум одно утверждение из каждого отчёта проверь сам — тем же способом (запуск
   команды, открытие `файл:строка`, источник). Расхождение — отчёт не принят целиком, задача уходит другому сабагенту
   (новый вызов, не продолжение).
3. **Adversarial-проверка ключевых утверждений.** Утверждение, на котором держится решение (выбор дизайна,
   «фреймворк так себя ведёт», «вызовов больше нет»), проверяет второй, независимый сабагент с задачей опровергнуть —
   `precheck-refuter` в новом вызове; ему не передают вывод первого — только вопрос, пути и коммит. По умолчанию при
   неуверенности — «опровергнуто».
4. **Сводка с пометками.** В план и в промпт сессии задачи утверждения идут с пометкой: «доказано (как)»,
   «опровергнуто», «не проверено». Не проверенное не становится фактом пред-проверки.
Механически, до чтения по существу:
- нет коммита или коммит не тот, на котором ты ставил задачу, — вернуть: `файл:строка` другой ревизии не сверить;
- «покрытие N из M»: M — длина чек-листа карточки; не сходится — вернуть;
- утверждение «гейт зелёный» принимается только с логом прогона и кодом 0 у
  `python3 gauntlet/hooks/stop_gate.py --verify-ran <задача> --log <лог>`;
- «ничего не найдено» с запросом поиска — повтори тот же поиск сам: это дёшево;
- учёт в плане: сколько карточек, сколько отчётов возвращено и сколько не принято.
````

### B.3. Роли как агенты Qwen Code
Формат агента Qwen Code: Markdown с YAML-заголовком; поля `name`, `description`, `tools` (белый список), `disallowedTools`,
`model` (`inherit`, `fast`, id модели или `authType:modelId`), `approvalMode`, `background`, а из Claude Code — `maxTurns`,
`hooks`, `mcpServers`, `color`, `permissionMode` [S3; S1: `parseSubagentContent`]. Проект важнее пользователя:
`.qwen/agents/` перекрывает `~/.qwen/agents/` [S3]. Что выбрано и почему:
- `tools` — имена инструментов Qwen Code (`read_file`, `grep_search`, `glob`, `edit`, `write_file`, `run_shell_command`,
  `web_fetch`); у reviewer и карточек записи нет. `agent` нет ни у кого: роль не плодит своих сабагентов.
- `approvalMode` не задан: при разрешительном режиме сессии он не сужает права сабагента («the parent's permissive modes
  still take priority») [S3] — только чтение держат белый список инструментов и хук.
- `background: false` у ролей: главный агент ждёт результата и SubagentStop-хук hardener'а; `background: true` у карточек:
  координатор запускает их параллельно и ждёт уведомлений [S3; S4].
- `hooks` во фронтматтере не используются: проектным агентам они нужны с явным доверием к папке
  (`security.folderTrust.enabled`), одобрение хуков их не покрывает [S2, «Agent frontmatter scope»; S8]. Все хуки — в
  `.qwen/settings.json`.
- `maxTurns` не задан: потолок ходов обрывал бы работу раньше чек-листа.
- `description` — в двойных кавычках: двоеточие с пробелом внутри строки без кавычек ломает YAML заголовка, и Qwen Code
  агента не загрузит (так было в первом черновике hardener'а — поймано проверкой D.5).
- Объём: Qwen Code предупреждает о системном промпте агента длиннее 10 000 знаков и об описании длиннее 1 000 (мягкие
  пределы) [S3, «Limits»]; файлы ниже в них укладываются — роль набора агент читает сам, а не несёт в промпте.

Что здесь и почему:
- **`SessionStart` → `session_start.sh`.** Обычный текст из stdout хука SessionStart Qwen Code кладёт в контекст модели
  [S2, «Exit Code Behavior»] — строка статуса `[gauntlet] active - …` видна агенту. Облачные ветки скрипта
  (`CLAUDE_CODE_REMOTE`, запуск `dockerd`) локально не срабатывают.
- **`SubagentStart` → `qwen_hooks.py subagent-start`.** Запоминает в `.git/gauntlet-hook/qwen-agents/`, какому агенту
  принадлежит `agent_id`. Нужен потому, что вызов инструмента внутри сабагента несёт только `agent_id`, а `agent_type`
  есть лишь в SessionStart, SubagentStart и SubagentStop [S2, «Hook Input Structure»; S1: `createBaseInput`]. `agent_id`
  именованного сабагента — `<имя>-<id вызова>`, `agent_type` — имя агента [S1: `hookOpts={agentId:`${subagentConfig.name}-…`,
  agentType:subagentConfig.name}`]; если записи нет, роль набора узнаётся по префиксу.
- **`PreToolUse` → `qwen_hooks.py pre-tool` → `guard.py`.** Matcher — runtime-имена Qwen Code: `write_file`, `edit`,
  `notebook_edit`, `run_shell_command`, `monitor` (оболочка в фоне). Псевдонимы Claude Code (`Bash`, `Write|Edit`) Qwen
  Code в matcher принимает, но в `tool_name` события приходит runtime-имя [S2, «Matcher Patterns»], и `guard.py`, который
  знает только `Edit`/`Write`/`Bash`, без прослойки пропускает всё (тест: 33 случая из 33 — «allow»). Ответ отказа —
  тот же JSON, что печатает `guard.py` (`hookSpecificOutput.permissionDecision: "deny"`) [S2, «PreToolUse»]. Сбой хука
  пропускает вызов (как у набора): в Qwen Code ошибка хука `PreToolUse` — «shouldProceed: true» [S1: `firePreToolUseHook`].
  Вызов через мост `tool_call` приходит в `PreToolUse` под именем целевого инструмента: планировщик подменяет запрос
  до хука [S1: `resolveToolCallBridgeRequest` → `{...request,name:resolution.tool.name}`, затем `runPreToolUse`]; вызовы
  из `exec` (Code Mode, `tools.codeModeOnly`, экспериментальный, по умолчанию выключен) тоже проходят `PreToolUse`
  [S2, «PreToolUse»]. `GAUNTLET_GUARD=off` в окружении запуска выключает прослойку так же, как `guard.py` (прил. 1).
- **`Stop` → `stop_gate.py --task gauntletFast`.** Код выхода 2 Qwen Code читает как блокировку: stderr становится
  `reason`, решение — `deny` [S1: `commandResult`, `convertPlainTextToHookOutput`], `deny`/`block` у Stop — продолжение
  хода с этим текстом как следующим запросом [S1: ветка Stop в `sendMessageStream`, `isBlockingDecision`]. Поле
  `stop_hook_active` — как в Claude Code [S2, «Stop»]. Потолок Qwen Code — 8 блокировок подряд (`stopHookBlockingCap`,
  переопределение `QWEN_CODE_STOP_HOOK_BLOCK_CAP`) [S2] — выше трёх попыток набора, так что отпускает набор.
- **`SubagentStop` с matcher `^hardener$` → `stop_gate.py --task mutationGate`.** Matcher сравнивается с `agent_type` =
  имя агента; блокировка продолжает сабагента с `reason` как заданием, до `stopHookBlockingCap` раз [S1:
  `runSubagentStopHookLoop`].
- **Таймауты.** У командных хуков — в секундах, но значение 1000 и больше читается как миллисекунды [S2, «Command Hooks»;
  S1: `LEGACY_MILLISECOND_TIMEOUT_THRESHOLD=1e3`]. Поэтому 30 минут Stop-хука записаны как `1800000`, 2 часа hardener'а —
  `7200000`, а `180` у SessionStart — секунды.
- **Без `name` у хуков.** «A hook must include a name field to be enabled or disabled individually at runtime. Hooks
  without a name will always execute» [S2, «Approving project hooks»].
- **`permissions`.** Синтаксис Qwen Code: `Bash(<префикс> *)` с границей слова, `Edit(/путь/**)` от корня проекта,
  `Edit(~/…)` от домашнего каталога; `deny` > `ask` > `allow`; `Edit` покрывает `edit`, `write_file`, `notebook_edit`
  [S6, «permissions»]. Правила `Edit` действуют и на «равнозначные» команды оболочки (`cp`, `mv`, `rm`, `chmod` и др.), но не
  на «неизвестные» вроде `git` [S6, «Shell command bypass prevention»] — второй слой охраны человеческих путей, который
  работает и без хуков. Сокращения опций (`--am` вместо `--amend`) префиксные правила не ловят — их ловит guard.
  `allow` — команды, которые набор запускает сам, и чтение для карточек: фоновая карточка не может спросить разрешения,
  и команду без правила Qwen Code ей отклоняет [S7, «Auto Edits Mode»; S2, «PreToolUse»: «background subagents —
  "ask" falls back to "deny"»].
- **`tools.approvalMode: "auto-edit"`**, **`tools.shell.defaultTimeoutMs: 3600000`**: без настройки команда на переднем
  плане обрывается через 120 000 мс, а `timeout` вызова — не больше 600 000 мс [S6, «tools»; S1: `ShellTool`,
  `DEFAULT_FOREGROUND_TIMEOUT_MS=12e4`]; `gauntletFast` и `mutationGate` идут дольше.
- **`context.fileName`** и **`memory`** — решения A.7, пп. 6 и 2.
- **`Edit(~/.env)` и заглушка `.qwen/.env`.** Qwen Code при старте читает первый `.env` проекта (`.qwen/.env`, затем
  `.env`, от каталога запуска вверх), затем `~/.qwen/.env` и `~/.env`, и кладёт переменные в своё окружение, а оно
  целиком уходит хукам [S14, «`.env` files»; S1: `findEnvFiles`, `pushHomeCandidates`, `loadEnvironment`,
  `commandInvocation` → `sanitizeChildEnv(process.env)`]. `GAUNTLET_*` и `QWEN_CODE_SAFE_MODE` не входят в список
  ключей, которые Qwen Code отказывается брать из проектного `.env` [S1: `PROJECT_ENV_HARDCODED_EXCLUSIONS`]. Правка
  проектного `.env` требует нового одобрения хуков [S2, «Approving project hooks»], но `~/.env` в это одобрение не входит
  [S1: `readProjectEnvFiles` пропускает файлы пользователя]. Заглушка (A.2) — ниже.

## D. Пределы и источники

### D.1. Что не переносится
- **Хуки держатся на одобрении.** Пока владелец не одобрил хуки проекта в этой папке, их нет — ни guard, ни stop-gate.
  Каждое изменение `hooks` в `.qwen/settings.json` (и `.env` проекта) — новое одобрение [S2]. Признак — нет строки статуса;
  `QWEN.md` велит тогда остановиться, но это инструкция модели.
- **Роль сабагента выводится, а не сообщается.** Qwen Code не передаёт `agent_type` в `PreToolUse`; прослойка берёт его из
  записи SubagentStart или из префикса `agent_id`. Смена формата `agent_id` в будущей версии, без записи SubagentStart,
  сделает роли набора «только чтением» (безопасная сторона: hardener и specifier увидят отказ). После обновления — A.6.
- **`approvalMode` сабагента не ограничивает его**, если сессия в разрешительном режиме [S3]; только чтение ревьюера и
  карточек держат белый список инструментов и хук.
- **Хуки во фронтматтере агентов** требуют явного доверия к папке [S2; S8] — не используются.
- **Уровень рассуждений** задаётся на сессию; на сабагента — нет [S3: «`effort` … land in follow-up PRs»]; наследуют ли
  сабагенты уровень сессии — не подтверждено.
- **Облака Claude Code нет:** ни создания сессий координатором, ни Routine, ни подписки на PR; замены — в C.
- **`gauntlet kit unchanged`** не видит `.qwen/`, `QWEN.md`, `AGENTS.md` до решения A.7, п. 1.
- **Песочница выполнения Qwen Code несовместима с хуками** [S9; S1].
- **Окружение сессии собирается и из `.env`-файлов** (в Claude Code такого нет): переменные из них доходят до хуков
  набора. Закрыто заглушкой `.qwen/.env` и охраной `~/.env` (B.5); чей-то `QWEN_HOME` с другим `.env` прослойка
  охраняет по переменной `QWEN_HOME`, только если она задана и в окружении хука.
- **MCP-инструменты** прослойка не судит, как и набор в Claude Code (matcher — только инструменты записи и оболочки);
  правило `deny` для MCP блокирует вызов, но не убирает инструмент [S6].
- **Эвристика guard'а** та же, что в Claude Code: растяжка, а не сейф (README набора, раздел 9). Вложенный `qwen` с
  выключенными хуками прослойка отклоняет только в буквальных формах (`QWEN_CODE_SAFE_MODE=…`, `qwen … --safe-mode`,
  `--bare`).
- **Модель как исполнитель.** О том, насколько тщательно Qwen4-Max проверяет без принуждения, независимых данных нет:
  модель вышла 16.11.2026. Адаптер на это и не опирается — опора на доказательства и приёмку.

### D.2. Известные сбои, относящиеся к жалобе владельца («сабагенты отрабатывают слишком быстро»)
1. **Qwen Code сам подталкивает сабагента к минимуму.** К системному промпту обычного (не интерактивного) сабагента
   дописываются правила «Use tools only when necessary to obtain facts or make changes.» и «When the task is complete,
   return the final result as a normal model response (not a tool call) and stop.» [S1: `renderSubagentSystemPrompt`;
   вызов `createChat(context2)` без `interactive` у `AgentHeadless`]. Ответ адаптера: в каждом агенте необходимость определена

## Приложение 1. `gauntlet/adapters/qwen/qwen_hooks.py`

```python
#!/usr/bin/env python3
"""Qwen Code hooks -> the gauntlet's own guard.py, unchanged.

Part of the Qwen Code adapter. Proposed place: gauntlet/adapters/qwen/qwen_hooks.py, added by the human like any kit
change, so the CI check `gauntlet kit unchanged` covers it with the rest of gauntlet/. The Stop, SubagentStop and
SessionStart hooks need no translation: Qwen Code calls gauntlet/hooks/stop_gate.py and session_start.sh directly
(.qwen/settings.json). Only two events need this script:

  qwen_hooks.py subagent-start   SubagentStart: remember which agent (agent_type) an agent_id belongs to
  qwen_hooks.py pre-tool         PreToolUse: translate the call and ask guard.py
  qwen_hooks.py selftest         what this script relies on in guard.py is still there

Why guard.py alone is not enough under Qwen Code 0.28.4 (docs/users/features/hooks.md at tag v0.28.4 and the package
@qwen-code/qwen-code@0.28.4, read 2026-11-24):
  - tool events carry the runtime tool id in tool_name (write_file, edit, notebook_edit, run_shell_command, monitor),
    not Claude Code's Write/Edit/Bash, so guard.py sees no tool it knows and allows every call;
  - agent_type is reported on SessionStart, SubagentStart and SubagentStop only; a tool call made inside a subagent
    carries agent_id and no agent_type, so guard.py would judge every subagent as the main agent: the specifier could
    not write the specification and the reviewer and hardener would not be limited.
What makes the translation possible:
  - a named subagent's agent_id is "<agent name>-<call id>" and its SubagentStart event carries the same agent_id with
    agent_type = the agent's name (package: `hookOpts={agentId:`${subagentConfig.name}-${agentIdSuffix}`,
    agentType:subagentConfig.name, ...}`; tool calls run inside runWithAgentContext(hookOpts.agentId, ...));
  - the deny answer Qwen Code reads is the one guard.py already prints: {"hookSpecificOutput": {"hookEventName":
    "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": ...}}; a hook that fails or prints nothing
    lets the call through (fail-open, like guard.py itself).

Roles: no agent_id = the main agent (the coder); specifier, hardener and reviewer keep the kit's scopes; every other
subagent (the pre-check cards, Explore, general-purpose, fork) is read-only, as core.md rule 1.6 asks of them.
The human's switch is the kit's: GAUNTLET_GUARD=off in the environment Qwen Code starts with turns this check off,
as it turns off guard.py (guard.py main(); this script calls guard.py's functions, not its main(), so it checks the
switch itself). Qwen Code also takes variables from .env files at start-up (the project's first .qwen/.env or .env,
then ~/.qwen/.env and ~/.env; package findEnvFiles) and hands them to every hook: ~/.env is therefore Qwen Code's
configuration like ~/.qwen, and the project's .env is shadowed by a human-owned .qwen/.env (qwen.md, A.2).
Not run against a live Qwen Code: check it with the smoke test of the adapter (qwen.md, section A.6).
"""
import hashlib
import importlib.util
import json
import os
import re
import subprocess
import sys

HERE = os.path.dirname(os.path.realpath(__file__))
KIT_HOOKS = os.path.realpath(os.path.join(HERE, "..", "..", "hooks"))
# Qwen Code's own configuration in the project is human-owned like .claude/ and CLAUDE.md: settings, hooks, agents,
# rules, skills and fork profiles (.qwen/), the context files it loads by default (QWEN.md, AGENTS.md) and the ignore
# files that decide what its search tools see.
EXTRA_OWNED = (".qwen/", "QWEN.md", "AGENTS.md", ".qwenignore", ".agentignore", ".aiignore")
WRITE_TOOLS = {"write_file": "Write", "edit": "Edit", "notebook_edit": "NotebookEdit"}
SHELL_TOOLS = ("run_shell_command", "monitor")
KIT_ROLES = ("specifier", "hardener", "reviewer")
# Turning Qwen Code's hooks off is the human's, like GAUNTLET_GUARD=off (guard.py HOOK_SWITCH): the variables and
# flags that disable every hook of a Qwen Code process (hooks.md "A hook does not fire", item 4; stop cap: "Stop").
QWEN_HOOK_SWITCH = re.compile(
    r"(?:^|[\s;&|(])(?:export\s+)?QWEN_CODE_(?:SAFE_MODE|SIMPLE|STOP_HOOK_BLOCK_CAP)="
    r"|(?:^|[\s;&|(])export\s+QWEN_CODE_(?:SAFE_MODE|SIMPLE|STOP_HOOK_BLOCK_CAP)\b"
    r"|(?:^|[\s;&|(/])qwen\b[^\n;&|]*\s--(?:safe-mode|bare)\b")


def main(argv):
    command = argv[0] if argv else ""
    if command == "selftest":
        return selftest()
    try:
        event = json.load(sys.stdin)
    except Exception:
        return 0
    if not isinstance(event, dict):
        return 0
    try:
        if command == "subagent-start":
            subagent_start(event)
        elif command == "pre-tool":
            if os.environ.get("GAUNTLET_GUARD", "").lower() == "off":     # the human's switch, as in guard.py main()
                return 0
            reason = pre_tool(event)
            if reason:
                print(json.dumps({"hookSpecificOutput": {
                    "hookEventName": "PreToolUse",
                    "permissionDecision": "deny",
                    "permissionDecisionReason": "[gauntlet guard] " + reason}}))
    except Exception as error:       # fail-open like guard.py; exit 1 is Qwen Code's non-blocking error (debug log)
        sys.stderr.write(f"[gauntlet qwen] {command} failed: {error!r}\n")
        return 1
    return 0


def project_of(event):
    # Qwen Code sets QWEN_PROJECT_DIR = CLAUDE_PROJECT_DIR = the event's cwd for command hooks (package: commandInvocation)
    return event.get("cwd") or os.environ.get("QWEN_PROJECT_DIR") or os.environ.get("CLAUDE_PROJECT_DIR") or os.getcwd()


# ----------------------------------------------------------------------------- which agent made the call

def state_dir(project):
    """The directory stop_gate.py keeps its state in (.git/gauntlet-hook): under .git/, which the guard closes to
    every agent, so the agent cannot write itself a role."""
    try:
        out = subprocess.run(["git", "rev-parse", "--git-path", "gauntlet-hook"], cwd=project,
                             stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True, timeout=30).stdout.strip()
    except (OSError, subprocess.SubprocessError):
        return None
    if not out:
        return None
    path = out if os.path.isabs(out) else os.path.join(project, out)
    try:
        os.makedirs(os.path.join(path, "qwen-agents"), exist_ok=True)
    except OSError:
        return None
    return path


def record_path(state, event, agent_id):
    session = hashlib.sha1(str(event.get("session_id", "")).encode("utf-8")).hexdigest()[:16]
    return os.path.join(state, "qwen-agents", session + "-" + hashlib.sha1(str(agent_id).encode("utf-8")).hexdigest())


def subagent_start(event):
    agent_id, agent_type = event.get("agent_id"), event.get("agent_type")
    if not agent_id or not agent_type:
        return
    state = state_dir(project_of(event))
    if state:
        with open(record_path(state, event, agent_id), "w", encoding="utf-8") as f:
            f.write(str(agent_type))


def agent_of(event, project):
    """main, a kit role, or the name of another subagent. Recorded at SubagentStart; if that record is missing, the
    agent_id prefix (the agent's name, then '-') names a kit role; anything else is an unnamed subagent."""
    agent_id = event.get("agent_id")
    if not agent_id:
        return "main"
    agent_id = str(agent_id)
    state = state_dir(project)
    if state:
        try:
            with open(record_path(state, event, agent_id), encoding="utf-8") as f:
                recorded = f.read().strip()
            if recorded:
                return recorded if recorded != "main" else "subagent"     # a subagent never gets the coder's rights
        except OSError:
            pass
    for role in sorted(KIT_ROLES, key=len, reverse=True):
        if agent_id.startswith(role + "-"):
            return role
    return "subagent"


# ----------------------------------------------------------------------------- guard.py, with Qwen Code's paths

def qwen_config_paths():
    """Qwen Code's user, system and relocated configuration: settings, hooks, hook approvals, trusted folders, agents,
    memory (settings.md "Settings files"; QWEN_HOME in sandbox.md and cross-session-protocol.md; the approvals file
    QWEN_CODE_HOOK_APPROVALS_PATH in the package, getHookApprovalsPath), and ~/.env, which Qwen Code loads at every
    start-up and hands to every hook, outside the project-hook approval (package: findEnvFiles, pushHomeCandidates,
    readProjectEnvFiles skips user-level files)."""
    paths = [os.path.expanduser("~/.qwen"), "/etc/qwen-code", os.path.expanduser("~/.env")]
    for var in ("QWEN_HOME", "QWEN_CODE_SYSTEM_SETTINGS_PATH", "QWEN_CODE_SYSTEM_DEFAULTS_PATH",
                "QWEN_CODE_HOOK_APPROVALS_PATH"):
        if os.environ.get(var):
            paths.append(os.environ[var])
    return [os.path.realpath(p) for p in paths]


def load_guard():
    spec = importlib.util.spec_from_file_location("gauntlet_guard", os.path.join(KIT_HOOKS, "guard.py"))
    guard = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(guard)
    guard.HUMAN_OWNED = tuple(guard.HUMAN_OWNED) + tuple(p for p in EXTRA_OWNED if p not in guard.HUMAN_OWNED)
    kit_user_config = guard.user_config_violation

    def user_config_violation(path):
        reason = kit_user_config(path)
        if reason or not path:
            return reason
        expanded = os.path.expanduser(str(path))
        if not os.path.isabs(expanded):
            return None
        absolute = os.path.realpath(expanded)
        for owned in qwen_config_paths():
            if absolute == owned or absolute.startswith(owned + os.sep):
                return (f"{owned} is Qwen Code's own configuration (settings, hooks, hook approvals, agents, memory, "
                        f"start-up environment); it could switch the gauntlet off. Do not touch it.")
        return None

    guard.user_config_violation = user_config_violation
    kit_scope = guard.Context.role_scope

    def role_scope(self, agent):
        scope = kit_scope(self, agent)
        if scope is None and agent != "main":
            return ()        # a subagent outside the kit's writing roles only reads (core.md, rule 1.6)
        return scope

    guard.Context.role_scope = role_scope
    return guard


def shell_cwd(params, event, project):
    directory = params.get("directory")
    if isinstance(directory, str) and directory.strip():
        directory = os.path.expanduser(directory.strip())
        # the package documents an absolute path, the user docs a path relative to the project root: take both
        return directory if os.path.isabs(directory) else os.path.join(project, directory)
    return event.get("cwd") or project


def pre_tool(event):
    tool = event.get("tool_name") or ""
    params = event.get("tool_input") or {}
    if not isinstance(params, dict) or (tool not in WRITE_TOOLS and tool not in SHELL_TOOLS):
        return None
    project = project_of(event)
    guard = load_guard()
    agent = agent_of(event, project)
    ctx = guard.Context(project)
    if tool in WRITE_TOOLS:
        path = params.get("file_path") or params.get("notebook_path") or ""
        return guard.user_config_violation(path) or guard.path_violation(agent, ctx.relative(path), ctx)
    command = str(params.get("command") or "")
    if QWEN_HOOK_SWITCH.search(command):
        return ("Switching Qwen Code's hooks off (QWEN_CODE_SAFE_MODE, QWEN_CODE_SIMPLE, --safe-mode, --bare, the "
                "Stop hook cap) is reserved for the human.")
    return guard.bash_violation(agent, command, ctx, shell_cwd(params, event, project))


# ----------------------------------------------------------------------------- selftest

def selftest():
    """The names this script patches or calls in guard.py, so a kit update that renames one fails loudly here
    instead of silently allowing every call."""
    guard = load_guard()
    missing = [name for name in ("HUMAN_OWNED", "user_config_violation", "path_violation", "bash_violation", "Context")
               if not hasattr(guard, name)]
    if not missing and not hasattr(guard.Context, "role_scope"):
        missing.append("Context.role_scope")
    if missing:
        print("qwen_hooks selftest: guard.py no longer has " + ", ".join(missing))
        return 1
    print("qwen_hooks selftest: ok (" + ", ".join(EXTRA_OWNED) + " added to the human-owned paths)")
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))
```

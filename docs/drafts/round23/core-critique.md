# Критика ядра `core.md`: правило тщательности, приёмка отчётов, карточки сабагентов

Дата: 2026-11-24. Объект: `round23/core.md` (119 строк, в набор ещё не внесён). Сверено с:
`gauntlet-method-universal.md` ревизии 4.4 (раздел 1.1, пп. 1–26; разделы 3, 5, 6, 8.3; приложения D и E), набором
`work/kit` (`gauntlet/CLAUDE.md`, `.claude/agents/*.md`, `.claude/settings.json`, `gauntlet/hooks/guard.py`,
`stop_gate.py`, `session_start.sh`, `.github/workflows/gauntlet-kit.yml`, `gauntlet/README.md`, разделы 5–7 и 9) и
`docs/decisions.md` репозитория разработчика набора (раздел «Правило остановки»).

## 0. Вердикт

Цель верная, основа хорошая: доказательство у каждого утверждения, доказательство поиска у «ничего не найдено»,
обязательный раздел «Не проверено», опровергатель без вывода первого, пометки статуса в плане. Это стоит сохранить.
Но в нынешней редакции ядро не решает задачу владельца — поймать быстрого и экономного сабагента на подмене работы:

1. **Приёмка статистически беззуба** (блокер F1). Одна выборочная перепроверка «тем же способом» ловит одно
   подделанное утверждение из k с вероятностью 1/k: 0,07–0,12 при k = 8–15. Около 90 % подделок уходит в промпт
   сессии. «Тем же способом» подтверждает подлинность доказательства, но не его достаточность и не полноту поиска.
2. **«По умолчанию при неуверенности — «опровергнуто»»** (блокер F2) превращает отказ опровергателя работать в снятие
   риска и противоречит самой карточке 4.4, где «опровергнуто» требует контрпримера.
3. **Раздел 5 обещает защиту, которой нет** (блокер F3): guard и CI `gauntlet kit unchanged` знают только пути Claude.
   Файлы адаптера, то есть инструкции и определения агентов вендора, не охраняет ни то, ни другое.

Дальше идут 17 мажоров и 5 миноров. Главные: стоимость растёт в 2,0–3,3 раза по запускам сабагентов без шкалы риска;
конфликты с пп. 10, 17, 21 и приложением D; не хватает карточек (наблюдаемые поверхности, область гейтов, зависимости,
миграции, тестовые данные, оценка, проверка после мержа). Утекает Claude-специфика: форки контекста, лимиты ходов,
журналы вызовов сабагента, подключение набора через `CLAUDE_CODE_REMOTE`, хуки SessionStart и SubagentStop. И есть
места, которые модель прочтёт самым дешёвым способом.

Ни одно предложение не ослабляет принцип «судить результат». Каждое заменяет текстовое требование проверкой по
результату: механическая сверка, контрольные пункты, сверка diff с областью роли, журнал приёмки. Прототип механической
сверки (раздел 8) нашёл 3 подделки из 3 на настоящем репозитории и ничего в нём не изменил. Главный блокер
закрывается дёшево.

## 3. Стоимость и шкала риска

Модель расчёта: оценка, не замер. Базовая пред-проверка по п. 12: S карт кода, сверка фреймворка и критик, итого
B = S + 2 запусков. Ядро как есть добавляет:
- возвраты: вероятность r = 0,4 на отчёт, не больше двух, то есть r + r² на отчёт;
- опровергателя на каждое несущее утверждение: K = 1 / 4 / 8 на класс;
- повтор после расхождения: d = 0,1.

Предложение (F1, F12) иначе устроено:
- возврат только после проваленной механической сверки, m = 0,4;
- продолжение того же сабагента стоит 0,3 запуска (Claude, Kimi, Qwen); без продолжения — полный запуск;
- опровергателей 0 / 1 / 3 по группам;
- риск-карточки только для высокого класса.

| Класс задачи | База | Ядро как есть | Предложение (с продолжением / без) |
|---|---|---|---|
| низкий (S = 1) | 3 | 6,0 (×2,0) | 3,4–4,2 (×1,1–1,4) |
| средний (S = 2) | 4 | 10,6 (×2,7) | 5,5–6,6 (×1,4–1,6) |
| высокий (S = 3) | 5 | 16,3 (×3,3) | 10,1–11,5 (×2,0–2,3) |

Кроме запусков есть токены координатора, а координатор — самая дорогая модель на максимальном уровне (раздел 1.1,
п. 17). Ядро как есть тратит их на чтение и ручную перепроверку по одному утверждению на отчёт и на чтение K отчётов
опровергателей. По предложению координатор запускает одну механическую сверку на отчёт (вывод в 1–2 тыс. токенов),
читает только расхождения и 0–3 пакетных отчёта опровергателей.

Где масштабировать, а не гонять всегда:
- опровержение — только несущих гарантий и пакетом;
- риск-карточки (4.9–4.11) — по предмету задачи;
- полные гейты в пред-проверке не нужны: их гонят сессия задачи и CI.

Новые карточки 4.7 и 4.8 идут пунктами карты 4.1, а 4.12 — в работе критика, поэтому запусков в расчёте они не
добавляют. Состав п. 12 сохраняется в каждом классе.

Где экономить нельзя: механическая сверка всех цитат и дешёвых команд и перепроверка каждого утверждения об отсутствии.
Это дёшево и закрывает главные уловки.

Особенность сред. Форк дешевле: у Claude он делит кэш промпта с родителем, у Qwen обещана экономия «80%+». Но форк
ломает независимость. Поэтому форк допустим для 4.1, которая проверяется механически, и запрещён для 4.2 и 4.4.
Сабагенты Claude по умолчанию могут порождать своих до трёх уровней вглубь, что множит стоимость и запутывает след
доказательств. Карточка это запрещает (F6).

## 5. Утечки Claude-специфики

1. **Чистый контекст сабагента** ядро считает данностью. У Claude это верно только для не-форка, а режим форка включён
   по умолчанию с v2.1.302. Qwen сам выбирает форк для параллельного исследования. У Codex — не подтверждено.
2. **Возврат отчёта тому же сабагенту** («возвращается сабагенту»). Есть у Claude (`SendMessage`), Kimi (`resume`) и Qwen
   (`send_message`). У Codex и Gemini — не подтверждено. Без продолжения возврат — это новый полный запуск, то есть
   стоимость.
3. **Журнал вызовов сабагента** для сверки. Есть у Claude: `agent_transcript_path` в SubagentStop и
   `decision: "block"`, чтобы вернуть сабагента. У Kimi родитель видит только последнее сообщение; у остальных — не
   подтверждено.
4. **Отсутствие жёстких лимитов ходов и времени.** У Gemini 30 ходов и 10 минут по умолчанию; у Qwen есть `maxTurns`.
5. **Только чтение.** У Claude guard ограничивает лишь три роли. У Codex инструкция не создаёт песочницы только для
   чтения, а у Kimi explore только чтение держится на промпте.
6. **Охраняемые пути** — только пути Claude (F3).
7. **Подключение набора к сборке** через `CLAUDE_CODE_REMOTE` (F20).
8. **Хуки** SessionStart, Stop и SubagentStop и строка статуса `guard: on; stop hook: on` (F20).
9. **Подпись ответа** «Ответ Claude Code на комментарий» (п. 19, приложение D) — у агента другого вендора она ложная
   (F17).
10. **Форматы итога ролей** набора — договор основного агента Claude с ролями (F16).
11. **Вложенность сабагентов:** у Claude до трёх уровней по умолчанию, у Gemini запрещена (F6).

### F1. [блокер] Раздел 2, п. 2 (выборочная перепроверка) и п. 1.1
**Проблема.** «Минимум одно утверждение из каждого отчёта… тем же способом» ловит одно подделанное утверждение из k с

сигнатура не доказывает поведения. Полноту тоже: узкий grep повторяется тем же узким. «Открыл и прочитал в этом
сеансе» проверить нельзя. Проверить можно только совпадение цитаты с файлом на ревизии.
**Последствие.** Главные короткие пути быстрой модели — выдуманная цитата, выдуманный вывод, узкий поиск — уходят в
«Факты пред-проверки». Тщательность перенесена в приёмку, а приёмка её не ловит.
**Предлагаемый текст.**
П. 1.1, второй вид доказательства:
- `файл:строка` с дословной цитатой. «Открыл и прочитал» доказывается только совпадением цитаты с файлом на ревизии
  отчёта.

Раздел 2, пп. 2–4 и 7 вместо «Выборочной перепроверки»:
2. **Механическая сверка — всех доказательств, а не одного.**
   - Каждую цитату `файл:строка` координатор сверяет с файлом на ревизии из шапки отчёта: `git show <ревизия>:<путь>`,
     ±2 строки, пробелы не в счёт.
   - Каждую команду только для чтения (поиск, `git log`, `git show`, подсчёт) он перезапускает и сравнивает код выхода

   - Сверку делает скрипт набора, если он есть, иначе команды.
   - Если среда хранит журнал вызовов инструментов сабагента, каждая заявленная команда и её вывод сверяются с журналом.
   - Сборка, тесты и источники в сети проверяются выборочно, по п. 2.6.
   - Сдвиг строки при той же цитате — поправка, не расхождение.
3. **Достаточность и полнота — другим способом.** У несущего утверждения координатор проверяет, что доказательство его

4. **Контрольные пункты.** В карточку координатор вкладывает 1–2 пункта с заранее известным ему ответом: число

7. **Расхождение.** Отчёт не принят целиком, если есть расхождение по существу (цитаты нет на месте; другой вывод,
   число или код выхода) или ошибка в контрольном пункте. Повтор — новым сабагентом с той же карточкой и без прежнего
   отчёта, не больше одного раза. Если не принят и повтор, несущие утверждения координатор проверяет сам, остальные
   помечает «не проверено».

**Проблема.** «модель, которую учили экономить, сократит работу при любой формулировке» — первоисточники показывают

Ядро не говорит, каким сабагентом исполнять карточку. Требование тщательности стоит в промпте задачи, а у встроенного
исследователя системный промпт его перебивает.
**Последствие.** Координатор возьмёт встроенного «быстрого» исследователя: Kimi прямо советует `subagent_type="explore"`
и параллельный запуск. Отчёты будут тонкими по настройке, и приёмка будет без конца возвращать их — это дорого.
**Предлагаемый текст.**
### 0.1. Что делает сабагентов «быстрыми» и снимается настройкой
Часть краткости — не обучение модели, а настройка среды, и адаптер снимает её до приёмки. Это встроенный исследователь
с системным промптом «будь быстрым», лимит ходов или времени сабагента по умолчанию, совет вендора возвращать сводку
вместо вывода, модель или уровень рассуждений сабагента ниже рабочих. Поэтому:
1. Карточку исполняет определение сабагента набора с правилом тщательности в системном промпте, а не встроенный

2. Модель сабагента — не ниже рабочей модели сессий шага (раздел 1.1, п. 17), уровень рассуждений — там, где среда его
   задаёт. Выбор пишется в план вместе с рекомендацией.
3. Бюджет ходов и времени — по размеру карточки, а не по умолчанию среды. Если карточка не помещается, она делится.
4. Шапка отчёта называет модель, уровень и то, упёрся ли сабагент в лимит среды.

Приёмка по результату (раздел 2) остаётся обязательной: настройка снимает причину, приёмка ловит остаток.

### F5. [мажор] Раздел 1, нет п. 1.8: класс утверждения и бремя доказательства
**Проблема.** П. 1.1 требует доказательства от каждого утверждения, а иначе отправляет его в «Не проверено», а не в
выводы. Работа критика (4.3) и опровергателя — это гипотезы-риски («строка ломается при входе X»). По п. 1.1 они
уходят в «Не проверено» и теряются как выводы. Нет и правила, какое доказательство что доказывает.
**Последствие.** Риски, найденные критиком, оседают в остатке. Гарантии, «доказанные» доказательством не того класса
(сигнатурой, страницей без версии, именем теста), проходят.
**Предлагаемый текст.**
8. **Класс утверждения задаёт бремя доказательства.** Каждое утверждение помечено классом:
   - *гарантия* («безопасно», «вызовов больше нет», «фреймворк делает X», «свойство действует») — нужно доказательство по
     списку ниже, иначе «не проверено»;
   - *риск* («здесь гонка», «строка таблицы ломается», «миграция блокирует запись») — нужна конкретика: вход, путь в коде
     (`файл:строка`), что сломается и как это увидит приёмка. Доказательство нужно, чтобы риск снять, а не чтобы его
     назвать;
   - *несущее* — дополнительная пометка у утверждения, на котором держится решение плана или строка таблицы решений.

   Что доказывает что:
   - поведение фреймворка — документация версии сборки (правило 12), исходник того же тега или прогон;
   - сигнатура — javadoc или `javap`; сигнатура не доказывает поведения;
   - «вызовов нет» — команда поиска с числом совпадений по имени, по ссылке на метод и по строкам конфигурации;
   - «тест покрывает X» — имя теста и строка ассерта, который упал бы при неверном X;
   - «значение действует» — строка конфигурации, профиль и фактическое значение из прогона или из метаданных свойств.

  - каждый HTTP-ответ, сообщение (очередь, ключ маршрутизации, поля), сохранённая строка, поле события аудита, через
    которые проходит изменение (`файл:строка` записи или отправки);
  - для каждого — меняется ли значение, формат, порядок или наличие;
  - существующие фичи, которые это уже закрепляют (путь и сценарий).
- Вернуть: «поверхность → меняется / нет → доказательство»; вывод «со спецификацией» или «без» как несущее
  утверждение; неясные поверхности — рисками.

### 4.8. Область гейтов (раздел 1.1, п. 4)
Исполняется пунктами карты 4.1; прогон — одной командой в отдельной копии.
- Цель: заранее знать, не покраснеет ли гейт на старом коде файлов, которые задача изменит.
- Чек-лист:
  - файлы, которые задача изменит (из 4.1);
  - нарушения в них: прогон `./gradlew checkstyleGate pmdGate -Pgauntlet.scope=all --continue` в отдельной копии с
    фильтром вывода по этим файлам, а без прогона — строки файла против 300 и методы длиннее 25 строк (`файл:строка`);
  - строки allowlist'ов, которые их касаются.
- Вернуть: «файл → нарушение → доказательство»; рекомендация — отдельный шаг гигиены до поведенческого или «нарушений
  нет».

### 4.9. Зависимости и версии (раздел 1.1, п. 26; раздел 1.2)
- Цель: какие версии на деле в сборке и нужна ли задаче новая зависимость или обновление.
- Чек-лист:
  - фактически разрешённые версии библиотек, которых касается задача (`./gradlew dependencies` по нужной конфигурации,
    вывод), и `project.*` (`./gradlew gauntletInfo`);
  - нужна ли новая зависимость или плагин: координаты `group:artifact:version` и откуда (Maven Central или портал
    плагинов — плагина с портала в корпоративном реестре может не быть);
  - нужно ли обновление — тогда это отдельное решение владельца и отдельная задача;
  - конфликт с BOM.
- Запрещено: менять версии приложения ради гейта; обращаться к корпоративному реестру из сессии.
- Вернуть: «библиотека → разрешённая версия → доказательство → нужна новая / обновление → координаты для переноса»;
  вопросы владельцу.

### 4.10. Безопасность миграции (только если задача меняет схему или данные)
- Цель: миграция безопасна для данных и для работающей версии приложения.
- Чек-лист:
  - правится ли уже применённый changeSet (история файла в git; последствия для проверки контрольных сумм — по
    источнику версии Liquibase из сборки);
  - совместимость прежней версии приложения с новой схемой на время выката (добавить → перенести → удалить);
  - блокировки и длительность операций на больших таблицах (индекс, смена типа, NOT NULL на существующих строках) — по
    документации PostgreSQL версии из «Источников документации»;
  - откат;
  - прогон миграции на чистой базе и на базе со схемой предыдущей ревизии (Testcontainers, в отдельной копии);
  - миграция лежит в основном каталоге исходников (раздел 1.2); комментарии — по п. 20.
- Вернуть: «changeSet → риск → доказательство → тест или шаг выката»; решения владельцу (окно, порядок сервисов).

### 4.11. Тестовые данные и фикстуры
- Цель: данные тестов и сценариев, которые задача использует или меняет, детерминированы, независимы и без ПДн.
- Чек-лист:
  - реальные ПДн и секреты в фикстурах, сценариях и тестовых ресурсах — поиск по шаблонам (e-mail, телефон, ФИО-подобные
    строки, токены) с числом совпадений;
  - фиксированные даты и id против «сейчас» и случайных;
  - общие изменяемые фикстуры и состояние стенда, от которых зависят сценарии (будущие красные контроли `cN` и `zN` в
    `gherkinMutation`);
  - данные, которые задача делает неверными;
  - образы Testcontainers и их версии.
- Вернуть: «фикстура → проблема → доказательство → что поменять (тестовый код или вопрос к спецификации)».

### 4.12. Проверка оценки (раздел 1.1, пп. 2 и 12)
Входит в работу критика 4.3: по п. 12 проверку оценки сводит критик.
- Цель: оценка задачи для Jira соответствует найденному объёму.
- Чек-лист: число точек изменения, новых и меняемых сценариев, целей unit-тестов, шагов гигиены из 4.8; факт против
  оценки у прошлых сопоставимых шагов (раздел «Оценка» их PR, ход выполнения плана).
- Вернуть: «оценка подтверждена» или «поправка: на сколько и из-за чего», с доказательствами.

### 4.13. Проверка после мержа (раздел 1.1, п. 21)
- Цель: смерженный PR делает то, что написано в его описании.
- Чек-лист:
  - строки «Сверки по документации» отчёта PR — источник открывается и подтверждает утверждение для версии сборки
    (несущие — все, остальные — выборочно);
  - таблица гейтов отчёта против лога CI на голове PR;
  - «Перенос в контур» против diff: новые зависимости, удалённые и переименованные файлы;
  - остатки и отложенное — в план.
- Вернуть: «пункт отчёта PR → совпало / нет → доказательство»; остатки.

## 8. Прототип механической сверки (не часть набора)

Файл: `round23/critic-proto/report_check.py`, Python 3 без зависимостей. Запуск:

# Сравнение связок «координатор + исполнитель»

Черновик к ревизии 4.5. Эталон — Claude Code в обеих ролях. Кандидаты — Codex CLI, Antigravity CLI (Gemini 4
Carbon), Grok Build, Kimi Code CLI, Qwen Code. Все сведения о средах — по документации и исходникам версий на
2026-11-24 (черновики адаптеров — `../adapters/`, разбор по ролям — `rolefit.json` рядом); вживую ни одна среда
здесь не запускалась.

## 1. Что можно знать заранее, а что только из прогона

Документы и исходники показывают, насколько среда держит правила набора: хуки, права ролей, гейты, приёмку
отчётов. Насколько глубоко думает модель, они не показывают. Это меряется только прогоном на ваших задачах, с
одинаковыми входами и ключом ответов, поэтому ниже — порядок такого сравнения.

Уже есть и реальные данные: аудит ревью ревизии 4.3 (`docs/review-audit.md`). Там каждое замечание ревьюеров
воспроизведено прогоном. Точность ревью: Codex — 93–100 % подтверждённых по раундам, Grok — 17 из 17, Kimi — 11
из 15 (ещё 3 частично, одна посылка неверна, и исполнитель «починил» несуществующее поведение). Исполнителями тогда
были Qwen4 Max и Kimi 3.1 pro: закрыли 112 из 131, но сообщали цифры без стендов и публиковали ответы-ссылки на
файлы вместо текста. И важное для вопроса о глубине: семь раундов ревью спорили о редких формах команд, а обычную
многострочную команду хук не разбирал — это нашлось только сверкой с настоящим bash. Точность ревьюера не равна
глубине. Среды и версии моделей тогда были другие, а гейтов набора на том репозитории нет, поэтому это ориентир,
а не ответ.

## 2. Настройки, без которых сравнение нечестно

Часть «поверхностности» — умолчания сред, а не модель. Перед сравнением уровень рассуждений задаётся явно.

| Среда | Координатор | Исполнитель сессии шага | Выключить | Версия |
|---|---|---|---|---|
| Codex CLI | `gpt-6.2-astra`, `-c model_reasoning_effort=max`; не Ultra | `gpt-6.2-sol` high; тонкая семантика — `gpt-6.2-astra` xhigh | `/goal`, `--yolo`, `--approve-for-me`, Codex Cloud (хуки не подтверждены) | ≥ 0.172.0 |
| Antigravity CLI | Carbon, `--effort high` (максимум у Carbon) | Carbon High; простые шаги — Argon High | Orchestrator, `/swarm`, `/goal`, `--dangerously-skip-permissions` | ≥ 1.5.16 |
| Grok Build | `grok-4.7` xhigh (максимум) | `grok-4.7` high; тонкая семантика — xhigh | `/goal`, `/workflow`, `/deep-research`; без `--trust` хуки не грузятся | 1.0.92 |
| Kimi Code CLI | K3.1 Pro, `max`; `[secondary_model]` не задавать, чтобы карточки наследовали `max` | K3.1 Pro high; тонкая семантика — max | Highspeed-вариант для координатора и карточек | ≥ 2.7.0 (закреплена 2.7.3) |
| Qwen Code | `qwen4-max`, `/effort xhigh` (верх лестницы) | `qwen4-max` | `yolo`, `plan`, `tools.executionSandbox` (выключает хуки), встроенные агенты `codex`/`claude-code` | 0.28.4 |

Умолчания, которые режут глубину: у `gpt-6.2-astra` во встроенном каталоге Codex CLI 0.172.0 уровень low (сервер
может его переопределять — проверьте `/status` в своей сессии); у Carbon без `--effort` — Medium; Kimi Code при
входе ставит high, а не max; у Qwen4-Max и Grok 4.7 — high. Ваше впечатление «Астра копает вширь» стоит
перепроверить на явном max.

## 3. Этап 1 — координаторы, теневой режим

Исполнитель не участвует: сравнивается только пред-проверка и промпт сессии.

1. **Задачи.** Две-три уже сделанные задачи серии и одна предстоящая. Для сделанных — базовый коммит до задачи и
   ключ ответов: что нашла эталонная пред-проверка и что всплыло позже (замечания ревью, дефекты после мержа,
   правки спецификации). Ключ составляется до прогона кандидатов и им не показывается.
2. **Входы одинаковые:** выдержка плана, задача для Jira, базовый коммит, набор ревизии 4.5. Кандидат делает
   пред-проверку по `gauntlet/subagents.md` в отдельной копии (`git worktree`), ничего не пушит, пишет файл
   пред-проверки и черновик промпта сессии по приложению D.
3. **Контрольные пункты.** В карточки вкладываются 3–5 вопросов с известным ответом (ядро, приёмка): число вызовов,
   значение свойства, строка метода.
4. **Лист оценки** (по каждой задаче и каждому кандидату):
   - **полнота по ключу:** сколько ловушек найдено как факт или риск; глубокие — поведение во время работы через
     несколько компонентов: потоки и пулы, транзакции, колбэки брокера, порядок событий, повторы, фоновые задачи —
     считаются вдвое;
   - **ложные принятые факты:** `python3 gauntlet/tools/report_check.py` по каждому отчёту сабагента плюс выборочная
     проверка пяти фактов из файла пред-проверки;
   - **шум:** доля выводов о стиле, именах и локальных мелочах, которые ни на одно решение не влияют;
   - **честный остаток:** «не проверено» действительно не проверено, «доказано» действительно доказано;
   - **контрольные пункты:** верных из заданных;
   - **протокол:** нумерованные решения, план, ни строки продакшен-кода, отказы guard в журнале;
   - **стоимость:** время, запуски сабагентов, токены или кредиты, ваши ручные шаги.
5. **Судит ключ и механическая сверка, а не впечатление:** метод исходит из того, что человек код не читает.

## 4. Этап 2 — исполнители

Координатор — эталон, промпт сессии одинаковый для всех кандидатов. Две-три небольшие поведенческие задачи со
спецификацией и одна гигиеническая, на одной базе. Измерительный прибор — сам набор:

- CI `gauntlet` на первой голове PR: зелёный или красный;
- блокировки Stop-хука (попытки закончить с красным гейтом) и отказы guard;
- раунды ревью (не больше двух) и находки «дефект» уровня blocker и major от reviewer и внешних ревьюеров;
- мутанты: выжившие до и после hardener'а;
- дисциплина спецификации: остановка на утверждении, попытки править замороженные фичи;
- проверка после мержа (раздел 1.1, п. 21): описание PR совпадает с кодом;
- время, токены, ваши вмешательства.

Запуск — в локальном терминале: облачного режима с хуками нет у четырёх сред из пяти, у Codex Cloud хуки не
подтверждены.

## 5. Этап 3 — лучшая пара целиком

Лучший координатор из этапа 1 и лучший исполнитель из этапа 2 на одной-двух новых задачах против эталона.

## 6. Правило решения

Пара заменяет эталон, только если: полнота по ключу не ниже эталона (допустим пропуск одной мелкой ловушки), ложных
принятых фактов не больше, нарушений протокола нет, а выигрыш по стоимости или лимиту ощутим. Иначе вендор остаётся
внешним исполнителем карточек только для чтения при эталонном координаторе (маршрут сабагентов, `subagents.route`).

## 7. Что известно о ролях заранее (по документации и исходникам)

**Координатор.** Ни одна из пяти сред не создаёт сессию шага, не пишет в идущую сессию и не подписывается на
события PR. Владелец становится «транспортом»: 6–10 ручных шагов на задачу — запустить сессию шага с готовым
промптом, переносить решения и вопросы, сообщать о PR и CI, объявлять паузу по лимиту. Глубину пред-проверки
определяют настройки (уровень, порог сжатия, отказ от «быстрых» режимов), запуск карточек с чистым контекстом и
механическая приёмка. Подсказки среды к краткости есть у всех: «summarize routine verification» (Grok), «tools
only when necessary» и «summarize the findings» после 100 чтений (Qwen Code), быстрый `explore` и «do that work
yourself» (Kimi Code), «не запускай сабагентов без явной просьбы» вне Ultra (Codex). У Carbon два известных сбоя
бьют именно по координатору: в Orchestrator он сообщал о действиях без вызова инструмента (#1613), а после сжатия
около 256 тыс. токенов отчёт «дополнял» несуществующие SHA (#1245). Отсюда настройки пилота: High, Orchestrator
выключен, порог сжатия задан, карточки — отдельные запуски `agy -p` с явным уровнем.

**Исполнитель.** Ближе всего к эталону по охране — Codex CLI (хуки того же контракта, песочница ОС; нужна
прослойка, иначе правка через `apply_patch` из оболочки идёт мимо guard) и Qwen Code (Stop, SubagentStop и
SessionStart вызывают скрипты набора напрямую; хуки работают только после одобрения в каталоге сессии). У
Antigravity механизмы переносятся почти один к одному, но ключевые точки не проверены вживую: хуки роли у
сабагента, Stop при конце hardener'а, 30-минутный Gradle на переднем плане. Grok Build держит всё через прослойку
и `--trust`; Stop-гейт не срабатывает на оборванном ходе, а инструмент `monitor` выводит команды из-под guard. Kimi
Code слабее всех: в событиях хуков нет роли, поэтому области specifier, hardener и reviewer среда не исполняет,
гейта hardener'а нет, Stop держит один раз и не дольше 600 с — годится для шагов без тонкой семантики.

## 8. С чего начать

1. Координатор: эталон остаётся системой учёта (план), Carbon идёт теневым координатором на двух-трёх уже сделанных
   задачах с ключом — пакет пилота `carbon-coordinator.md`.
2. Исполнители: первыми — Codex CLI и Qwen Code, они лучше держат правила набора; Kimi — на простых шагах.
3. Внешние карточки только для чтения: по аудиту 4.3 выше всего точность ревью у Codex и Grok — с них и начать
   маршрут сабагентов; у Kimi — строже приёмка.

# Метод Gauntlet: разработка «не читая код»

Универсальная инструкция и протокол развёртывания для любого стека (Java, Python, JS/TS-фронтенд и Node,
другие) в Claude Code, облачные и локальные сессии. Ревизия 4.3, 2026-11-20 (ревизия 4.2 — 2026-11-19, ревизия 4.1 — 2026-10-06, ревизия 4 —
2026-10-05, ревизия 3 — 2026-10-04, ревизия 2.1 — 2026-09-30, ревизия 2 — 2026-09-29, ревизия 1 — 2026-09-26).
Источник: эталонный набор `gauntlet/` (Java 21, Gradle, Spring Boot 4), обкатанный на реальном проекте, и
бандл `gauntlet-kit-bundle.md` ревизии 4.3. Имён, пакетов и предметной области эталонного проекта здесь нет:
предметную область нового проекта `start` определяет по его репозиторию.

Термины. «Многоагентный прогон» — несколько сабагентов, запущенных координатором параллельно (инструмент
workflow, если он есть в сессии и владелец разрешил запуск; иначе те же роли последовательными сабагентами).
С CI-workflow он не связан.

Документ рассчитан на двух читателей: человека (разделы 1–7) и Claude (раздел 8, протокол).

  от specifier, каждая строка становится сценарием; граничные тесты рождаются до реализации, а не патчем
  после сдачи (раздел 1.1, п. 12; раздел 3, шаг 2; раздел 5, роль specifier; раздел 8.3; приложение D);
- дыра-чек перед заморозкой: каждое правило, которое код должен решать, закреплено сценарием или явно
  «Вне фичи» с принятым риском; критерий — наблюдаемость приёмкой (раздел 1.1, п. 5; раздел 3, шаг 3);
- остановка на неопределённом правиле в «Когда застрял» и в правилах сессии (раздел 4; приложение D);
- отчёт: раунды ревью и находки типа «правило» отдельным списком (раздел 3, шаблон отчёта).
Причина: правка одного случая неопределённого правила порождает следующий случай новым заворотом, а гейты его
не ловят — мутации закаляют тесты против спецификации, а не против ненаписанных правил. Синхронизировано с
бандлом ревизии 4.2.

**Как запустить в новом проекте.** Нужны два файла, оба самодостаточны, доступ к чужим репозиториям
не требуется:
- `gauntlet-method-universal.md` — эта инструкция (метод, правила, протокол);
- `gauntlet-kit-bundle.md` — бандл эталонного набора: файлы `gauntlet/`, `.claude/`, `CLAUDE.md`
  и CI-workflow эталона, очищенные от имён и примеров эталонного проекта, как текст между маркерами
  `===== BEGIN FILE … =====`, со скриптом распаковки в заголовке.

Инструкцию прикрепляют к каждой сессии протокола: `start`, `scan`, координатору и `contract`. Протоколов
нет в `gauntlet/CLAUDE.md` проекта, без файла сессия их не знает. Бандл нужен только для `start`.

1. Откройте новую облачную сессию Claude Code **на целевом репозитории** (том, куда ставится набор),
   режим Accept edits. Прикрепите оба файла и напишите одно слово: `start`. Ответьте на вопросы.
   Claude распакует бандл, адаптирует набор под ваш стек, установит его в той же ветке `gauntlet-setup`
   (первый прогон гейтов зелёный на текущем коде) и откроет PR.
2. После мержа PR откройте вторую сессию на том же репозитории, прикрепите инструкцию и напишите: `scan`.
   Claude соберёт контекст проекта и напишет инструкцию по настройке окружения (домены, переменные,
   Docker, админ-окружение, GitHub) и первую серию задач.
3. Серию задач ведёт координатор — отдельная долгоживущая сессия на том же репозитории с прикреплённой
   инструкцией и файлом плана (или отчётом `scan`), слово `coordinate` (разделы 1.1, п. 11, и 8.3): план,
   задача для Jira и пред-проверка перед каждым шагом, сессия на задачу. Перед выкатом серии в прод —
   сессия с инструкцией и словом `contract <ревизия прода>` (раздел 8.5).

Если приложение живёт в закрытом корпоративном контуре (раздел 1.2), набор туда не переносится. Оба файла
— обычные документы: их можно переслать тому, кто ставит набор в свой репозиторий. Если вся разработка
идёт внутри закрытой сети, файлы вносят туда так же, как любые документы.

Архив `gauntlet-<проект>-<дата>.tar.gz` — локальный бэкап владельца эталона, к сессии его не прикрепляют.
Бандл пересобирается из архива одной командой (раздел 8.4), когда эталон меняется.

## 1. Суть метода

Подход Роберта Мартина (Uncle Bob), переложенный на Claude Code, с дополнениями владельца проекта.

**Что делает человек.** Читает три вещи: спецификацию (Gherkin), отчёт о гейтах в PR и изменения самого
набора `gauntlet/`. Принимает три решения: «да» спецификации в чате, утверждение плана серии задач,
merge PR. Ставит задачи. Всё остальное делает агент.

**Что делает агент.** Из запроса пишет спецификацию (роль specifier), после «да» реализует по TDD (coder),
закаляет тесты мутациями (hardener), проходит адверсарное ревью (reviewer), гоняет гейты до зелёного,
пушит ветку, открывает PR с отчётом. Агент не может: править спецификацию после утверждения, править
набор `gauntlet/`, ослаблять проверки, переписывать историю, мержить.

**Почему это работает без чтения кода.** Гейты закрывают лазейки: маленькие функции (сложность и размер),
антипаттерны, архитектурные рёбра, покрытие через CRAP, дубли, мутационное тестирование с требованием
«ни один покрытый мутант не выживает», мутация значений спецификации (пустые step-определения видны),
проверка целостности (нет отключённых тестов и подавлений). Хуки Claude Code защищают набор и
спецификацию; CI повторяет гейты вне сессии; PR показывает diff.

**Оговорка Мартина (сентябрь 2026).** Он пересматривает тяжёлые оркестрации; здесь взята часть, которая от
оркестрации не зависит: гейты качества, один основной агент и три лёгкие роли.

### 1.1. Дополнения владельца

1. **Разбор перед серией.** Перед серией задач агент разбирает код относительно спецификации и плана:
   подтверждённые дефекты со ссылками файл:строка, предложения по каждому шагу, вопросы владельцу.
   Ключевые находки проверяются независимыми сабагентами-скептиками, утверждения об API сверяются с
   официальной документацией, критик ищет пробелы плана. Результат: план в ревизии N с разделами
   «решения владельца», «подтверждённые дефекты», «шаги», «нужно решение человека», «ход выполнения».
   План хранится у владельца (файл), обновляется после каждого шага.
2. **Задача для Jira перед каждой задачей.** Это задача владельца в его рабочем трекере, а не задание
   сессии: координатор пишет её в свой чат простым человеческим языком, без «нейрослопа» (тема, что и зачем,
   критерии приёмки, трудозатраты) до начала работы; после апрува владельца открывает сессию шага с отдельным
   описанием уже для сессии. Сессия, получившая задачу в промпте, заново её не пишет. Оценка сверяется по факту
   в отчёте PR.
3. **Одна задача = одна сессия = одна ветка = один PR.** Следующая задача начинается новой сессией от
   основной ветки; её открывает координатор (п. 11) с полным промптом либо владелец вручную.
   Ветка не переиспользуется после мержа.
4. **Порядок серии: гигиена → рефакторинг под гейты → поведенческие шаги.** Область гейтов — изменённые
   файлы целиком, поэтому большие файлы приводятся к лимитам до поведенческих правок, отдельными PR.
5. **Шаги помечаются «со спецификацией» и «без».** Без спецификации: рефакторинг, конфигурация,
   инфраструктура, логи. Со спецификацией: всё, что меняет наблюдаемое поведение, включая новые события
   аудита и таблицы. Критерий: меняется хоть одно свойство, которое может наблюдать приёмка, — ответ API,
   сообщение, сохранённая строка, поле события аудита. Новое поле в существующем событии тоже требует
   спецификации. В эталонном проекте шаг «сквозной идентификатор в логах» сначала был помечен «без
   спецификации»; пред-проверка заметила, что идентификатор попадает и в сохранённые события, и шаг пошёл
   через specifier. Правило, которое код должен решать, но которое не закреплено ни сценарием, ни явным
   «Вне фичи» с принятым риском, — дыра спецификации: вопрос владельцу до заморозки (раздел 3, шаг 3), а не
   место для решения кодом.
6. **Отчёт по шаблону в PR и в чат**: гейты со статусами, max CRAP, мутанты (убито / выжило / без
   покрытия), Gherkin-мутанты, спецификация (файлы и сценарии), ревьюер (вердикт, что исправлено), сверка
   по документации (утверждение, источник, версия), перенос в контур (новые зависимости, удалённые и
   переименованные файлы), нужно решение человека, остаточные риски.
7. **Решения владельца фиксируются письменно** (в плане и в описании PR), включая «не делать» с причиной.
8. **Бэкап набора.** После каждого изменения `gauntlet/` владелец сохраняет архив у себя (git archive
   основной ветки: `gauntlet/`, `.claude/`, `CLAUDE.md`, CI-workflow).
9. **Вне кода** ведётся список операционных задач (ротация ключей, политики хранилищ, доступы), они
   не входят в план правок, но перечисляются в нём.
10. **Ревью в два раунда.** Blocker и major типа «дефект» исправляются всегда; minor, отложенные по согласованию,
    записываются в «нужно решение человека» с причиной. Каждая поведенческая находка помечается типом:
    **«дефект»** — поведение противоречит утверждённой спецификации или решению владельца, правится в коде;
    **«правило»** — спецификация не определяет поведение, которое код решает (выбор версии, порядок строк,
    судьба отказа, явная очистка поля против его отсутствия). Находка типа «правило» не уходит в новый раунд
    правок: она идёт владельцу нумерованным списком «ответьте здесь», работа над ней останавливается до
    ответа; после ответа правило закрепляется в спецификации (п. 23), затем один проход реализации против
    всего правила, а накопленные регрессионные случаи становятся приёмочным набором. Счёт раундов механический:
    координатор ведёт его в плане, сессия без координатора — в описании PR; после второго CHANGES REQUESTED с
    непогашенными находками новые замечания не выдаются — остаток выносится владельцу, работа не считается
    сделанной. Замечание, воспроизводящееся на базе до задачи, — отдельная задача бэклога, а не основание
    заворачивать PR.
11. **Координатор серии.** Одна сессия-координатор ведёт план и не пишет продакшен-код. Перед каждой задачей
    она пишет задачу для Jira, делает пред-проверку (п. 12), открывает для задачи новую сессию с полным
    промптом (приложение D), передаёт в неё решения владельца и обновляет план после мержа. Сессия задачи
    работает по процессу раздела 3 и отчитывается в PR. Сессии открываются только по команде владельца.
12. **Пред-проверка перед каждой задачей.** Многоагентный прогон координатора: несколько агентов строят
    карты кода по срезам задачи (точки изменения, потоки, конфигурация, тестовый каркас), отдельный агент
    сверяет каждое утверждение о фреймворке по официальной документации или по байткоду подключённой версии,
    критик сводит варианты дизайна, черновик сценариев, цели unit-тестов, проверку оценки, блокеры и
    вопросы владельцу. Для задачи, которая выбирает значение или версию из нескольких (история строк, эхо,
    повтор, отказ, удаление, очистка поля), пред-проверка дополнительно даёт таблицу решений: тип события ×
    наблюдаемый исход (отправленное сообщение, сохранённое состояние); критик атакует её граничными случаями,
    а цели граничных тестов идут в промпт сессии до реализации. Таблицу утверждает владелец до заморозки
    спецификации; каждая её строка становится сценарием со значениями в Examples. Малый размер задачи не
    освобождает от таблицы: правило выбора с несколькими исходами наблюдаемо приёмкой (п. 5). Выводы и
    решения попадают в промпт сессии и в план. В эталонном проекте пред-проверка каждый
    раз находила то, что сломало бы задачу: пул планировщика, на котором не наследуется контекст логов;
    колбэк подтверждения брокера на I/O-потоке клиента; фоновые тики, перехватывающие строки в приёмке.
13. **Решения владельца — нумерованным списком.** Любой запрос решений у владельца идёт пронумерованным
    списком с рекомендацией в каждом пункте: утверждение спецификации, вопросы координатора после
    пред-проверки, раздел «Нужно решение человека» в отчёте PR, отчёт `contract`. Владелец отвечает коротко:
    «1) да 2) да 3) нет, потому что …». Сессия задачи записывает ответ в описание PR, координатор переносит
    его в план.
14. **Лимит токенов.** Порог — 99 % пятичасового или недельного лимита, 100 % не ждать. Процент агент сам
    не видит: паузу объявляет предупреждение, пришедшее в сессию, либо владелец или координатор сообщением
    «пауза по лимиту». На паузе сессия коммитит и пушит свою ветку и пишет статус: что сделано, что красное,
    что дальше. Stop-хук после такого коммита может вернуть красный гейт — на паузе его не чинят, а отвечают
    одной строкой «пауза по лимиту, работа не сделана»; хук отпускает после третьей попытки. После сброса
    работу возобновляет владелец или координатор сообщением в ту же сессию. Правило входит в промпт каждой
    новой сессии.
15. **Структурные миграции — через переходную политику архитектуры.** Большой перенос кода (например, из
    слоёв в пакеты по фичам) идёт серией PR. Владелец заранее утверждает переходную редакцию политики
    архитектуры: целевые компоненты плюс объединение рёбер всех промежуточных состояний, с пометкой, какие
    рёбра временные. Финальная редакция снимает временные рёбра после последнего PR серии. Исключения для
    тонких наследников библиотек задаются масками в конфиге модуля и тоже утверждаются владельцем.
16. **Сверка контракта с продом.** Перед выкатом серии, а также по запросу владельца, отдельная сессия
    `contract <ревизия прода>` сравнивает ревизию прода с основной веткой по всем внешним поверхностям
    (раздел 8.5). Открывает её владелец или координатор по его команде; отчёт координатор переносит в план.
17. **Модель и уровень рассуждений — рекомендация при каждом старте сессии.** Перед созданием сессии шага
    координатор пишет в чат, какую модель и какой уровень рассуждений он рекомендует под эту задачу и почему;
    решает владелец. Умолчания эталона: координатор — старшая модель на максимальном уровне, без многоагентных
    воркфлоу (adversarial-проверка PR, параллельная сверка плана — только по явному запросу владельца); сессия
    шага — рабочая модель на высоком уровне, без многоагентных воркфлоу: процесс gauntlet уже многоагентный
    (specifier, hardener, reviewer, хуки), и воркфлоу поверх него — главный расход лимита; шаги с тонкой
    семантикой фреймворка (транзакции, ORM, брокер, таймауты) — старшая модель на высоком уровне. Инструмент
    создания сессии задаёт только модель; уровень рассуждений и воркфлоу владелец выставляет в настройках
    сессии сам. Конкретные имена моделей живут в `gauntlet/CLAUDE.md` проекта («Правила владельца»).
18. **Адресация вопросов сессии шага.** Сессия решает только свою задачу. К каждому пункту списка решений она
    ставит пометку «ответьте здесь» или «переслать координатору»; владелец пересылает вопрос в чат
    координатора, а сессия до ответа работает там, где от него не зависит. Координатору: всё, что меняет план
    за пределами шага (состав, оценки, порядок других шагов, новый шаг, перенос остатка); правки набора и его
    файлов (политика архитектуры, allowlist'ы, исключения из мутаций, эквивалентные мутанты); контракты с
    соседними сервисами и внешними системами и вопросы к их разработчикам; дефекты и долг вне файлов шага;
    модель, уровень рассуждений и лимиты; всё, что затрагивает другую идущую сессию. Владелец отвечает сам: выбор
    варианта спецификации и критериев приёмки шага, бизнес-правила из ТЗ в объёме шага, утверждение
    спецификации, допустимые остаточные риски шага, замечания внешнего ревьюера, противоречащие спецификации.
    Вопрос вне обоих списков — «переслать координатору».
19. **Независимый ревьюер.** Внешний ИИ-ревьюер (в эталоне — Grok AI) читает каждый PR и оставляет
    комментарии в GitHub, сам ничего не правит. Его комментарий — не истина и не шум: автор PR (сессия шага на
    своём PR, координатор на своём) проверяет каждое замечание по коду и источникам; прав — исправить и
    запушить; не прав — ответить в том же треде, почему, со ссылкой на код или документацию. Молчать нельзя.
    Каждый ответ начинается строкой «Ответ Claude Code на комментарий <ревьюер>» с номером или датой
    комментария, чтобы в треде было видно, кто кому отвечает. Замечание против утверждённой спецификации или
    решения владельца — вопрос владельцу, а не правка.
20. **Комментарии и Javadoc простым языком.** Читатель комментария — человек в рабочем контуре, у которого нет
    плана, ТЗ и gauntlet: первое предложение — что это и для чего; слова предметной области вместо кодов
    документов и шагов плана; полные предложения, без телеграфных цепочек через тире, без «см. раздел … в
    CLAUDE.md», без пересказа кода и без истории правок. Переход постепенный: новый код по правилу, старые
    комментарии приводятся в файлах, которые задача меняет (файл целиком); шапки фич спецификации правило не
    затрагивает. Javadoc — контракт, а не рассуждение: у класса резюме одной фразой и ещё 2–6 строк того, чего не
    видно из кода (больше 10 строк — сигнал вынести объяснение в документ), у метода 1–3 строки, подробнее — только
    при неочевидном контракте (исключения, транзакция, потокобезопасность, крайние случаи); без Javadoc у геттеров,
    DTO и очевидных методов, без пересказа кода и разбора альтернатив. **Комментарии в конфигурации** (настройки
    приложения, `Dockerfile`, `docker-compose.yml`, миграции, скрипты сборки — всё, что уходит в контур) — по тем же
    правилам: одна-две фразы о том, зачем это значение и что сломается без него, без пересказа ключа и кодов
    документов, длинное объяснение — в документ эксплуатации. Правка только комментариев не меняет ни значений, ни
    ключей, ни инструкций и доказывается сравнением до и после: дерево YAML или JSON, `docker compose config`, строки
    Dockerfile без комментариев. Комментарии файлов, которые владелец оставил за собой (переключатель реестров,
    Dockerfile, compose), меняются только его решением. Проверяет reviewer.
21. **Проверка после мержа.** Координатор сверяет код смерженного PR с его описанием и спецификацией, гоняет
    гейты на основной ветке, разбирает остатки (что не вошло, что отложено), записывает итог в план и
    архивирует сессию шага. Полная adversarial-проверка многоагентным прогоном — по запросу владельца, на PR с
    тонкой семантикой. Контрольный прогон гейтов на основной ветке идёт в режиме набора по умолчанию (область —
    изменения относительно базовой ветки, тесты целиком): прогон со `scope=all` покажет нарушения в файлах шагов,
    которые ещё не пройдены, и это не дефект смерженного PR.
22. **hardener при пустой области PIT.** Если мутировать нечего (правка только конфигурации или вне продакшен-кода),
    hardener предлагает ручные мутанты списком (`файл: что изменить → какой тест должен упасть`), а применяет,
    гоняет тесты и откатывает их основная сессия; перед коммитом она проверяет, что продакшен-каталог чист.
    Роли запрещено править продакшен-файлы «временно», в том числе скриптом, патчем или stash: guard по типу
    агента — растяжка, а не сейф, и оставленный мутант уехал бы в коммит. В эталоне такое случилось один раз;
    правки откатили, правило внесли в роль.
23. **Замороженную спецификацию меняет только человек.** Хук закрывает фичи для всех агентов после коммита
    `spec:`. Если по ходу реализации спецификацию нужно поправить (в эталоне — Gherkin-мутант выживал, потому что
    ожидания повторяли столбцы входа), сессия шага останавливается с пунктом «ответьте здесь»; после «да» правку
    вносит владелец сам или координатор как его делегат: отдельный коммит `spec:` в ветку шага с пометкой, чьё
    решение, приёмка прогоняется до пуша, сессия подтягивает ветку (`git pull`, без rebase). Смысл сценария при
    этом не меняется; изменение смысла — новая спецификация через specifier.
24. **Allowlist RUN_ERROR — через PR владельца набора.** Строку вносит не сессия шага: координатор (или владелец)
    сам гоняет `mutationGate` на ветке шага, читает тест и называет ассерт, который упал бы ровно на этой
    мутации, затем вносит строки своим PR; сессия после его мержа сливает основную ветку. Строка живёт ровно
    столько, сколько метод: если ревью переписало код и метод исчез, строка стала мёртвой и убирается следующим
    PR владельца набора (в эталоне — в тот же день).
25. **Никаких следов разработки вне рабочего контура.** Официально приложение разрабатывается только внутри
    контура, поэтому в коде, комментариях, Javadoc, фикстурах, примерах и документах, которые уходят в контур
    (описание API для соседних команд), не упоминаются PR и их номера, GitHub, ветки, gauntlet и гейты, сессии
    и роли, «решение владельца», номера шагов и решений плана, открытые вопросы. Причина правила пишется словами.
    Правило действует на каждый файл, который задача меняет; старые файлы вычищает отдельный шаг гигиены
    (замер — grep по этим словам, он же проверка). Документы плана и журнала решений в контур не переносятся, на
    них правило не распространяется.
26. **Зависимости и версии приложения не меняются ради гейтов.** `start` определяет их по файлам проекта и
    фактическому разрешению, а инструменты Gauntlet выбирает и фиксирует отдельно после реального прогона.
    Обновление языка, сборщика, фреймворка или любой зависимости приложения — отдельное решение владельца и
    отдельная задача/PR, даже если оно нужно для совместимости гейта. JVM инструментов — независимая настройка
    (`gate.java.version`); локальный путь — `GAUNTLET_GATE_JAVA_HOME`/`-Pgauntlet.gateJavaHome` вне git,
    не повод менять Java приложения или его toolchain. Toolchain разрешается только при выполнении гейта:
    обычные `help`/`classes` не требуют gate-JDK.

### 1.2. Закрытый рабочий контур

Частый случай: разработка идёт в облачных сессиях на GitHub, а приложение живёт в корпоративной сети.
Метод различает два контура:

- **Внешний контур** — где владелец пишет запросы Claude и работает с GitHub: облачные сессии, CI, PR.
  Зависимости здесь публичные и берутся напрямую из Maven Central, PyPI, npm, а не через корпоративный
  реестр. Здесь работают набор, приёмка и все гейты.
- **Рабочий контур** — сеть внутри организации. В ней нет доступа ни к GitHub, ни к Claude, нет интернета,
  зависимости и образы берутся только из корпоративного реестра (Nexus, Artifactory). Здесь приложение
  собирают, прогоняют в рабочем окружении и эксплуатируют.
- **Поток правок:** задача, затем PR в GitHub, затем merge владельцем. После этого владелец вручную забирает
  файлы проекта из GitHub, переносит их в рабочий контур и прогоняет там. Обратного канала нет:
  результат прогона в рабочем контуре владелец пересказывает в чате.

Сборка обязана проходить в обоих режимах. Ничто из того, что проверяется только во внешнем контуре
(приёмка, гейты), не должно быть нужно приложению в рабочем. Метод это учитывает так:

- **Набор не переезжает в контур.** `gauntlet/`, `.claude/`, `CLAUDE.md` и CI-workflow живут только в
  GitHub: это контекст агентов и гейты. Сборка модулей обязана работать и без них. В эталоне набор
  подключается к сборке, только если каталог `gauntlet/` лежит рядом и сборка идёт по публичным
  репозиториям; в корпоративной сборке он выключен по умолчанию (приложение E).
- **Приёмочные тесты тоже остаются в GitHub.** Каталог приёмки (в Java — `src/acceptanceTest`) в контур
  не переносится, а в облаке остаётся рабочим инструментом всех сессий. Поэтому продакшен-код и unit-тесты
  не зависят от классов и ресурсов приёмки, а всё, что нужно приложению в контуре (конфигурация,
  миграции), лежит в основном каталоге исходников. В эталоне source set приёмки создаёт сам набор, так что
  без `gauntlet/` сборка его просто не видит.
- **Два режима репозиториев в одной сборке.** Переключатель по переменной окружения облака и CI:
  публичные репозитории в облачной сессии и в GitHub Actions, корпоративный реестр во всех остальных
  случаях. Флаг можно задать явно свойством сборки.
- **Образы контейнеров тестов** — через префикс реестра (в Java: `hub.image.name.prefix` Testcontainers),
  в облаке — Docker Hub. Префикс кладут рядом с тестами, которые его используют: для тестов, которые
  переносятся в контур, — в сборку или основной каталог тестовых ресурсов, не в каталог приёмки.
- **Каждая новая зависимость и плагин** указываются в отчёте PR с координатами и версией, чтобы владелец
  проверил их наличие в корпоративном реестре до переноса. Плагины, опубликованные только на портале
  плагинов, в корпоративном реестре может не оказаться.
- **Ручной перенос дорог.** Переносы и переименования файлов умножают работу владельца. Отчёт PR перечисляет
  удалённые и переименованные файлы отдельно: при ручном переносе старые файлы нужно удалить, иначе
  останутся дубли классов и бинов.
- **Внутренняя библиотека** из того же репозитория в облаке собирается из исходников (composite build), а
  в контуре берётся из реестра. Её правка требует новой публикации в реестр контура.

## 2. Гейты

Пороги Мартина и их источники: CRAP > 8 (crap4java), «ни один покрытый мутант не выживает»
(mutate4java), структурная схожесть ≥ 0.82 при ≥ 4 строках как дубль (dry4java), цикломатическая
сложность «ниже 4». Остальное — значения эталонного набора, проверенные в работе.

| Гейт | Что проверяет | Порог по умолчанию | Java | Python | JS/TS |
|---|---|---|---|---|---|
| integrity | нет отключённых тестов, подавлений, скрытия кода от покрытия, порчи сборки | 0 находок вне allowlist | свой сканер (IntegrityCheck) | свой сканер | свой сканер |
| style / size | метод ≤ 25 строк, ≤ 4 параметров, CC ≤ 3, NPath ≤ 20, файл ≤ 300 строк, вложенность if ≤ 2, fan-out ≤ 20, магические числа, скобки | 0 нарушений | Checkstyle | ruff: C901 (max-complexity 3), PLR0913 (max-args 4), PLR0904 и PLR1702 (preview); pylint: C0302 (max-module-lines 300), R0904; когнитивная сложность — отдельный инструмент (например, complexipy, порог 9); длина функции ≤ 25 строк кода, NPath и fan-out — свой `tools/size_gate.py` или отказ по решению владельца, записанному в gauntlet.properties | ESLint: complexity 3, max-params 4, max-lines-per-function {max: 25, skipBlankLines: true, skipComments: true}, max-lines 300, max-depth 2, no-magic-numbers; sonarjs/cognitive-complexity 9; число методов класса, NPath и fan-out — свой `tools/size_gate.mjs` или отказ по решению владельца |

| unit | проект как есть | зелёный | JUnit | pytest | vitest / jest |
| architecture | разрешённые рёбра между компонентами, без циклов, домен без фреймворка | конфиг | ArchUnit | import-linter (layers, forbidden, independence) | dependency-cruiser (allowed, no-circular, forbidden) |
| acceptance | сценарии Gherkin, ни одного skipped | зелёный, 0 skipped | Cucumber-JVM | pytest-bdd или behave | cucumber-js (+ Playwright для UI) |
| CRAP | CC² × (1 − покрытие)³ + CC на метод | ≤ 8 | JaCoCo XML + CrapGate | coverage.py XML + radon json + crap_gate.py | istanbul coverage-final.json + CC каждой функции: отдельный прогон ESLint с `complexity: ["error", 0]` и JSON-форматтером (в отчёт попадает каждая функция со своей сложностью) или `typhonjs-escomplex` + crap_gate.mjs (пакет `escomplex` не ставить: без `esprima` он не загружается) |
| DRY | дубли ≥ 60 токенов, имена и литералы игнорируются | 0 в области | PMD CPD | jscpd или pylint duplicate-code | jscpd |
| mutation | каждый покрытый мутант убит; покрытие мутируемых модулей ≥ 80 %; мутант, на котором упал сам прогон тестов (в PIT — RUN_ERROR), убитым не считается | test strength 100 % | PIT + `PitSummary.java` (RUN_ERROR → `UNVERIFIED`, allowlist `config/pit-runerror-allowlist.txt`) | mutmut (или cosmic-ray) + verdict-скрипт | Stryker + verdict по `mutationScoreBasedOnCoveredCode` |
| gherkin mutation | каждое значение Examples мутируется по очереди, сценарий обязан упасть в шаге (сбой хука или фикстуры — ошибка, не kill); контроль — та же строка без изменений в том же прогоне — обязан пройти | 0 выживших, все контроли прошли | GherkinMutator | порт на Python | порт на JS или Python |

**Область проверки** (`scope=changed`, по умолчанию): diff относительно базовой ветки плюс незакоммиченные
файлы; изменённый файл проверяется целиком. `scope=all` для ночного CI и новых проектов.

**Мутант, на котором упал прогон тестов** (PIT: RUN_ERROR — JVM тестов упала на `redefineClasses`, обычно на
record; PIT считает его обнаруженным). Ничто не доказало, что тест его заметил бы, поэтому гейт печатает его
`UNVERIFIED` и красный, пока человек не впишет строку `Class#method Mutator # тест, который убивает` в
`config/pit-runerror-allowlist.txt`, прочитав тесты. Ключ — метод и мутатор, не строка: RUN_ERROR
недетерминирован, а номера строк устаревают с каждой правкой. Агент на таком мутанте останавливается и называет
ассерт, который упал бы ровно на этой мутации; нет такого — это слабый тест, агент пишет тест, а не просит
строку. Исключение класса из мутаций или метка медленного теста падение JVM не чинят. В других стеках аналог —
статус «ошибка прогона» мутатора (mutmut `suspicious`, Stryker `RuntimeError`): verdict-скрипт считает его так же.

**Приёмка судит только свой прогон.** Результаты прошлого прогона стираются перед запуском; если фичи есть, а ни
один сценарий не исполнен — красный. Фича без значений в «Примерах» для мутации значений бесполезна: гейт
`gherkinMutation` помечает её как пустую (`VACUOUS`) и падает. Мутант убит, только когда сценарий упал в шаге:
падение до шага (хук, фикстура, контекст) — ошибка прогона, а не обнаружение. Вместе с мутантами судится контроль —
каждая мутируемая строка «Примеров» без изменений в том же прогоне: если контроль не прошёл, стенд мутантов сломан
(фикстура недоступна, сценарий зависит от соседнего или от своего имени), и упавшие мутанты ничего не доказывают.
Два прогона гейтов в одном каталоге сборки
(фоновый прогон агента, Stop-хук, сабагент) бьют отчёты тестов: раннер держит блокировку на каталог сборки,
второй прогон ждёт первого (в эталоне до 1500 с).

**Четыре команды** (имена задач одинаковые в любом стеке, реализация через раннер стека):

| Команда | Состав |
|---|---|
| `gauntletFast` | integrity → style → anti-patterns → unit → architecture → acceptance (+ no-skipped) → CRAP → DRY |
| `mutationGate` | мутации изменённых модулей |
| `gherkinMutation` | мутация значений Examples |
| `gauntlet` | всё вместе |

Раннер: в эталоне Java/Gradle хуки и CI вызывают `./gradlew <задача>` напрямую, а область проверки, оверлеи
модулей и маски исключений считает `gauntlet.gradle`. В новом стеке единственная точка входа — `gauntlet/run.sh
<задача>` (контракт — раздел 8.1, шаг 2, п. 2); `make gauntlet`, `nox -s gauntlet` и `npm run gauntlet` только
вызывают `run.sh`. Java/Maven — профиль `./mvnw -P gauntlet verify` за той же обёрткой.

**Исключения из покрытия и мутаций**: только тонкие IO-адаптеры, до которых дотягиваются лишь
интеграционные тесты (репозитории с native SQL, конфигурационные классы, bootstrap). Логика в них
запрещена. HTTP-клиенты не исключаются: у них есть моки/WireMock/MSW/responses.

Исключения задаются масками имён, и у масок четыре ловушки (все встречены в эталонном проекте):
1. Ключ в конфиге модуля заменяет значение общего файла целиком, поэтому маски по умолчанию в нём
   повторяются.
2. Маска прячет класс, который позже получил логику. Тогда маску сужают в той же задаче, решением
   владельца. В эталоне так случилось дважды: одну маску убрали, другую сузили до имён оставшихся тонких
   классов.
3. Новый класс с логикой, чьё имя случайно попало под маску (`*Config`, `*Properties`), молча выпадает из
   мутаций и CRAP. Имена таким классам дают так, чтобы маски их не задевали.
4. Комментарий к маскам перечисляет ровно то, что исключено сейчас, и правится вместе с ними.

«Тонкие наследники» внутренней библиотеки (1–4 строки, сложность 1, только вызов родителя)
приравниваются к тонким IO-адаптерам: маски для них ставит владелец.

**Архитектурный конфиг при миграции.** Компонент — прямой подпакет корневого пакета; вложенные пакеты
входят в родителя, тестовые пакеты в анализ не входят. Компонент объявляется до появления кода, иначе гейт
падает. Переходная редакция и временные рёбра — раздел 1.1, п. 15; каждое новое ребро — решение
владельца, обычно отдельным пунктом на утверждении спецификации.

## 3. Процесс задачи

Триггер — сообщение владельца: фича, багфикс, изменение контракта или сообщения. Для правок без изменения
поведения шаги 2–4 пропускаются.

0. **Задача для Jira** в чат: тема, описание, трудозатраты (дополнение владельца). Её пишет координатор до
   пред-проверки (раздел 8.3); сессия задачи получает её в промпте и заново не пишет. Если сессию открыл
   владелец без координатора, задачу для Jira пишет сама сессия первым сообщением и ждёт согласия.
1. **Контекст.** Прочитать `gauntlet/config/gauntlet.properties`, `architecture.properties`, существующие
   фичи по теме.
2. **Спецификация.** Сабагент `specifier`: запрос дословно, релевантные фичи, ограничения. Возвращает
   изменённые файлы, по строке на сценарий, открытые вопросы. Все значимые значения — в таблицах
   Examples (иначе мутация их не проверит). Если задача выбирает значение или версию из нескольких (история
   строк, эхо, повтор, отказ, удаление, очистка поля), specifier дополнительно возвращает таблицу решений:
   тип события × наблюдаемый исход; каждая строка таблицы — сценарий со значениями в Examples. Правило
   выбора, не закреплённое ни сценарием, ни явным «Вне фичи», — открытый вопрос владельцу до заморозки, а не
   место для решения кодом.
3. **Утверждение — остановиться.** Показать пути, сценарии, вопросы и нумерованный список решений,
   нужных от владельца; у каждого пункта — пометка «ответьте здесь» или «переслать координатору» (раздел 1.1,
   п. 18). Дыра-чек перед заморозкой: каждое правило, которое код должен решать (выбор версии, порядок строк,
   судьба отказа, явная очистка поля против его отсутствия), закреплено сценарием или явно вынесено
   «Вне фичи» с принятым риском; критерий — наблюдаемость приёмкой (раздел 1.1, п. 5). Дыра — вопрос
   владельцу до заморозки; после заморозки она стоит уже правки спецификации человеком (п. 23). Ждать «да».
   До ответа — никакого кода и коммитов. В облаке Stop-хук платформы
   (`~/.claude/stop-hook-git-check.sh`, не gauntlet) один раз заблокирует остановку и попросит закоммитить
   и запушить изменения: черновик фич не коммитить (коммит заморозит неутверждённую спецификацию), а
   ответить одной строкой и остановиться повторно — вторая остановка проходит. `spec.approval=pr` — не
   останавливаться, человек читает Gherkin в PR.
4. **Заморозка.** Коммит только фич `spec: <что описано>` и push. С этого момента хук замораживает фичи
   для всех агентов. Противоречивая спецификация → остановиться и описать, не подгонять.
5. **Реализация.** TDD маленькими шагами: падающий unit-тест, минимум кода, рефакторинг. Step-классы
   в приёмочном source set. `gauntletFast --continue` до зелёного.
6. **Закалка.** Сабагент `hardener`: убивает выживших мутантов и пустые step-определения, правит только
   тестовый код; предложения по продакшен-коду применяет coder. Мутант, на котором упал прогон тестов, — либо
   строка allowlist для человека с именем убивающего теста, либо новый тест (раздел 2).
7. **Ревью.** Сабагент `reviewer` (база, фичи, список файлов). Каждая находка помечается типом: «дефект» —
   поведение противоречит утверждённой спецификации или решению владельца, правится в коде; «правило» —
   спецификация не определяет поведение, которое код решает. Находки типа «правило» не уходят в новый раунд
   правок: они идут владельцу нумерованным списком «ответьте здесь», работа над ними останавливается до
   ответа; после ответа правило закрепляется в спецификации (раздел 1.1, п. 23), затем один проход реализации
   против всего правила. Исправить blocker/major типа «дефект», повторить прогон, вернуть результат. Не
   больше двух раундов (раздел 1.1, п. 10): после второго CHANGES REQUESTED с непогашенными находками
   остановиться и описать остаток, а не начинать третий круг. Рекомендация против утверждённой спецификации —
   вопрос человеку.
8. **Финал.** `gauntlet --continue` зелёный → коммит → push своей ветки → PR с отчётом → тот же отчёт в чат.
   Никогда не мержить и не просить мержить.
9. **Комментарии внешнего ревьюера на PR** (раздел 1.1, п. 19): каждый проверить; прав — правка и push; не прав
   — ответ в треде со ссылкой на код или документацию, начиная строкой «Ответ Claude Code на комментарий
   <ревьюер>». Молчать нельзя.

### Шаблон отчёта (PR и чат)

```
## Гейты          таблица: каждый гейт со статусом; max CRAP; мутанты убито/выжило/без покрытия/не проверено
                  (RUN_ERROR); Gherkin-мутанты; что не прогнано и почему
```

## 4. Жёсткие правила (стек-нейтрально)

1. **Не трогать набор.** `gauntlet/`, `.claude/`, `CLAUDE.md`, CI-workflow принадлежат человеку; хук
   блокирует правки. Проверка выглядит неверной — остановиться и объяснить.
2. **Никогда не ослаблять проверку ради зелёного**: отключённые/условные тесты, assumptions, аннотации и
   прагмы, скрывающие код от покрытия и мутаций, inline-подавления, фильтры тестов, `enabled=false`,
   переконфигурация гейтов в сборке, удалённые или ослабленные assert'ы. Integrity это ловит, человек
   видит каждую попытку в diff.
3. **Фичи — это спецификация.** Пишет только specifier, утверждает только человек. Код удовлетворяет
   спецификации, а не наоборот.
4. **TDD.** На каждое поведение сфокусированный падающий unit-тест, который упал бы на правдоподобной
   неверной реализации → минимум кода → рефакторинг. Приёмочные тесты не заменяют unit-тесты.
5. **Маленькие функции.** CC ≤ 3, NPath ≤ 20, CRAP ≤ 8; метод ≤ 25 строк, ≤ 4 параметров, файл ≤ 300 строк,
   ≤ 12 методов в классе/модуле, когнитивная сложность < 10. Извлечённый метод сам владеет своими
   входами: не передавать boolean, который вызывающий уже знал.
6. **Зависимости направлены к политике**: без циклов, домен свободен от фреймворка, персистентности и
   транспорта. Адаптеры вызывают домен и не дублируют доменное правило.
7. **Step-определения используют каждый параметр** и проверяют наблюдаемое поведение (ответ, сохранённое
   состояние, отправленное сообщение).
8. Пометка «медленный тест» (`no-mutate` / маркер стека) только для тестов с полным контекстом или
   контейнерами; код, покрытый только ими, считается непокрытым.
9. **Секретам, персональным и другим чувствительным данным не место** в логах, фикстурах и текстах
   исключений.
10. **Git.** Коммиты говорят, что изменилось и зачем, заканчиваются `By <role>.`. Только новые коммиты в
    своей ветке: никаких `--amend`, `rebase`, `revert`, `reset` на другую ревизию, `checkout -B`,
    `push --force`, push в базовую ветку, `--no-verify`.
11. **SOLID по каждому принципу.** SRP: одна причина меняться. OCP: новый случай — новый класс/стратегия,
    не ещё одна ветка `if`. LSP: реализация не ужесточает предусловия. ISP: узкие интерфейсы. DIP:
    зависимость от абстракции, конкретику выбирает конфигурация.
12. **Сверяться с официальной документацией, а не с памятью — строго и на каждом шаге.** Правило
    действует для всех ролей: specifier сверяет семантику протоколов и фреймворка, на которую опираются
    сценарии; coder — каждый API, опцию, свойство конфигурации, поведение потоков, транзакций и таймаутов
    до того, как написать код; hardener — тестовые библиотеки; reviewer — что сверка была и источник
    подходит к версии. Документация берётся той же версии, что в сборке, а не «latest». Источники — только
    из раздела «Источники документации» в `gauntlet/CLAUDE.md` (раздел 4а этого документа). Никогда не
    выдумывать имя свойства, атрибут, метод, опцию или поведение: нет подтверждения ни в одном источнике —
    не использовать, остановиться и описать. Порядок источников строгий:
    (1) официальные сайты из списка разрешённых доменов облачного окружения (раздел 4а, приложение B);
    (2) только если нужный сайт недоступен или его нет в списке — запасные пути раздела 4а по порядку:
    артефакт нужной версии в реестре (javadoc-jar и sources-jar, sdist, tarball), затем исходники
    документации по тегу версии, затем установленный пакет (jar и `javap`, site-packages, `node_modules` и
    `.d.ts`); (3) только если недоступно и это — память модели, и то лишь когда утверждение подтверждает
    тест в том же изменении (тест фиксирует поведение фреймворка или библиотеки). Каждый случай (2) и (3)
    идёт в отчёт, случай (3) — с пометкой «память + тест». Reviewer считает решение без официального
    источника нужной версии и без такого теста находкой уровня major.
13. **Антипаттерны запрещены** не только те, что ловит статический анализ: god class, логика в
    листенере/контроллере/планировщике вместо домена, магические строки и числа, boolean-параметр-
    переключатель, `null` вместо Optional/пустой коллекции, проглоченное исключение, catch-all вне
    границы системы или без решения, мутабельное статическое состояние, самописный механизм там, где у
    платформы есть стандартный (retry, транзакции, валидация, конвертация, планирование, кэш).
14. **Оптимальный, безопасный и отказоустойчивый путь.** Перед реализацией назвать 2–3 варианта и выбрать с
    обоснованием. Для каждого нового пути: идемпотентность обработчика, границы транзакций (транзакция не
    пересекает вызов внешней системы), таймауты и ограниченные ретраи внешних вызовов, судьба отказа
    (dead letter, outbox, компенсация), потокобезопасность, валидация входа на границе, наблюдаемость
    (структурный лог без ПДн, метрика, correlation id). Кэширование там, где данные читаются многократно и
    меняются редко, только стандартным механизмом платформы с явными ключом, TTL, пределом и инвалидацией.
15. **Читаемый код.** Имена из предметной области; метод делает ровно то, что говорит имя, один уровень
    абстракции; guard clause вместо вложенности; комментарий, объясняющий плохой код, — повод переписать;
    документация на языке команды для публичных классов и неочевидных методов.

### Когда застрял
Выживший мутант, который считается эквивалентным; `switch`, который должен остаться выше лимита CRAP;
легитимная находка integrity; спецификация противоречит тесту или коду — **остановиться и описать**.
Человек добавляет исключение в allowlist или меняет спецификацию. Ревью или координатор нашёл поведение,
которое спецификация не определяет (находка типа «правило»), — остановиться и описать: какое правило решает
код, какие исходы видны приёмке, варианты с рекомендацией. Не подбирать правило по одному случаю за раунд:
следующее проявление того же пробела придёт новым заворотом, и гейты его не поймают — мутации закаляют тесты
против спецификации, а не против ненаписанных правил. Решение владельца закрепляется в спецификации, затем
один проход реализации против всего правила; накопленные регрессионные случаи становятся приёмочным набором.
Гейт красный после 3 попыток — Stop-хук
отпускает с предупреждением; работа при этом не сделана, так и писать в отчёте.

## 4а. Источники документации по стекам

Это шаблон раздела «Источники документации» в `gauntlet/CLAUDE.md` набора: единственный перечень
допустимых источников для правила 12. При `start` Claude оставляет строки, которые соответствуют
зависимостям проекта, добавляет источники владельца и проверяет каждый адрес запросом из сессии.
Адреса собраны и проверены 2026-09-29, дополнены 2026-09-30, ревизия Java-строк по фактической доступности из
облачной сессии эталона — 2026-10-05. Если домен был закрыт сетевой политикой, официальность подтверждена по
метаданным пакета: `<url>` в POM на Maven Central, `project_urls` на PyPI, `homepage` в реестре npm. Ревизию
стоит повторять раз в несколько недель: сайты открываются и закрываются (RabbitMQ и JUnit открылись, Liquibase
закрылся за неделю), репозитории документации архивируются, адрес с версией в пути может начать перенаправлять на
страницу без версии. Способ — `curl -sS -o /dev/null -L -w '%{http_code} %{url_effective}'` по каждому адресу
таблицы и запасному пути, затем сверка версий стека с кэшем зависимостей.

**Правила для всех стеков.**
- `<версия>` — версия из манифеста проекта: `./gradlew dependencies` или `mvn dependency:tree`, lock-файл
  Python, `package-lock.json`, `pnpm-lock.yaml` или `yarn.lock`. Документация берётся той же major.minor.
- Адрес без версии показывает последнюю ветку, а не вашу. Пример: docs.spring.io без версии в пути
  2026-09-29 открывал Spring Boot 4.1 при 4.0 в проекте. Версию в пути нужно проверять по самой странице
  (у сайтов на Antora — метатег `version`).
- Первоисточник API — артефакт нужной версии: javadoc-jar и sources-jar на Maven Central, sdist на PyPI,
  tarball в npm. Агрегаторы (javadoc.io, unpkg, jsDelivr) — зеркала для удобства.
- `stable` и `latest` в адресе заменять на `<версия>`, где сайт её публикует (Read the Docs:
  `/en/<версия>/`). Сайт без версий (например, FastAPI, react.dev, vitest.dev, testing-library.com) считается
  источником, только если страница не расходится с исходниками документации по тегу нужной версии; в
  отчёт идёт ссылка на тег (`raw.githubusercontent.com/<org>/<repo>/<тег>/docs/…`), её достаточно и
  reviewer.
- Сайт закрыт — запасные пути по порядку: артефакт нужной версии в реестре, затем исходники той же
  документации по тегу версии на raw.githubusercontent.com (формат тега у каждого проекта свой, его нужно
  проверить), затем установленный артефакт.
- Веб-страницы github.com чужих репозиториев из облачной сессии закрыты: прокси отвечает HTTP 403 «GitHub
  access to this repository is not enabled for this session». Чужие репозитории ради документации не
  подключать. Файлы — `raw.githubusercontent.com/<owner>/<repo>/<тег>/…`, вики —
  `raw.githubusercontent.com/wiki/<owner>/<repo>/<Страница>.md`; страницу, которой нет и там, открывает
  человек.
- Приоритет — разрешённые домены окружения. В разделе набора есть строка «Разрешённые домены
  окружения»: ровно тот список, который владелец внёс в Network access (приложение B). Источник вне списка
  не вызывается: для него сразу берётся запасной путь, а в отчёт идёт строка, какой домен стоит открыть.
- Не источник: блоги, Stack Overflow, статьи, ответы ИИ, код других проектов. Память модели допустима
  только последним рубежом и только вместе с тестом, который фиксирует это поведение (правило 12).
- В рабочем контуре доступны только артефакты из корпоративного реестра (раздел 1.2). Сверка по
  документации идёт во внешнем контуре.

## 5. Роли

Роли живут в `.claude/agents/*.md` репозитория: только они доходят до облачной сессии, пользовательские
`~/.claude/agents/` остаются на машине. Хук ограничивает роли по `agent_type`.

| Роль | Пишет | Что делает | Итог |
|---|---|---|---|
| **specifier** | только каталог фич | из запроса пишет Gherkin на границе сервиса: запросы/ответы, сообщения, наблюдаемое состояние; никаких классов и таблиц; фиксированные даты и id; значимые значения в Examples; лишние столбцы убраны; переиспользует формулировки шагов; для правил выбора — таблица решений (тип события × наблюдаемый исход) и самопроверка полноты: каждое правило закреплено сценарием или явно «Вне фичи», иначе открытый вопрос владельцу; семантику протоколов и фреймворка сверяет по источникам раздела 4а | файлы, по строке на сценарий, вопросы и допущения с источниками, таблица решений для правил выбора (или «нет правил выбора») |
| **coder** (основной агент) | продакшен и тестовый код | TDD, гейты, отчёт; каждый API, опцию и свойство сверяет по источникам раздела 4а до того, как пишет код | PR |
| **hardener** | только тестовый код | убивает SURVIVED и NO_COVERAGE мутантов, чинит пустые step-определения; для мутанта, на котором упал прогон тестов (RUN_ERROR), называет убивающий тест и строку allowlist для человека либо пишет тест; не ослабляет assert'ы, не прячет за маркерами; эквивалентных описывает человеку; правки продакшен-кода предлагает, не делает — в том числе ручные мутанты при пустой области PIT (список `файл: что изменить → какой тест должен упасть`; применяет и откатывает кодер); API тестовых библиотек сверяет по источникам раздела 4а; закончить может только с зелёным `mutationGate` (SubagentStop-хук) | числа до/после (убито / выжило / без покрытия / RUN_ERROR), добавленные тесты, что не убито и почему, список ручных мутантов |
| **reviewer** | ничего | ищет то, чего не видят метрики: поведение против спецификации (каждая поведенческая находка — «дефект» или «правило», раздел 3, шаг 7), безопасность и ПДн, транзакции и конкурентность, дизайн и SOLID по принципу, API против официальной документации (решение без источника нужной версии — major), перенос в контур (зависимости без координат, зависимость продакшен-кода от приёмки или набора), антипаттерны, комментарии и Javadoc простым языком в затронутых файлах (раздел 1.1, п. 20), gate gaming | `VERDICT: APPROVED \| CHANGES REQUESTED`, нумерованный список `[blocker\|major\|minor] [дефект\|правило] file:line — проблема — риск — исправление` (у «правило» исправление — решение владельца по спецификации, не правка кода), остаточные риски |

Полные тексты ролей для Java — в бандле (`.claude/agents/`). Для другого стека Claude при `start`
переписывает всё стек-зависимое: пути, раннер, инструменты, фреймворк и его версии, офлайн-источники
(site-packages, `node_modules`, `.d.ts` вместо jar и `javap`), примеры исключений. Во фронтенде граница для
specifier — то, что видит и делает пользователь (маршрут, экран, текст, состояние формы), и запросы к API на
моках (MSW, `page.route`). Смысл ролей, права и формат итога не меняются.

## 6. Защита и что может только человек

**Хуки Claude Code** (`.claude/settings.json`):
- `SessionStart` — `session_start.sh`: в облаке добывает базовую ветку (single-branch и shallow-клоны),
  фиксирует снимок рабочего дерева, в облачной VM поднимает демон Docker (`dockerd` напрямую: `service docker
  start` там падает на ulimit; процессы в снимок окружения не попадают, поэтому в каждой сессии заново) и
  печатает статус в контекст агента, включая `docker: up`.
- `PreToolUse` — `guard.py`: запрещает правки набора, `~/.claude`, спецификации (кроме specifier до
  заморозки), выход роли за область, `--amend`/`rebase`/`revert`/`reset`/`checkout -B`/`branch -f`/
  `push --force`/push в базовую ветку/`--no-verify`, `gh pr merge` и merge через API, выключение хуков.
  Shell-команды проверяются эвристически (cd, `git -C`, глобы, редиректы, heredoc-тела как данные; команда
  после `do`, `then`, `else`, `{`, `!` разбирается так же, как после `&&`); `gauntlet` как задача Gradle или
  путь под `build/` — не набор, ложных срабатываний на `./gradlew gauntlet > …` нет.
- `Stop` — `stop_gate.py`: основной агент не может закончить ход с красным `gauntletFast`; хук гоняет его,
  только когда дерево изменилось и это состояние не проверялось; ход только со спецификацией не гоняет;
  пока фичи не закоммичены, приёмочные тесты в прогон не входят: агент должен иметь возможность
  остановиться и задать вопрос; после 3 попыток отпускает с предупреждением; возвращает агенту строки
  RUN_ERROR и `mutationGate: …`, чтобы он видел, что именно красное. Хук hardener'а — `SubagentStop` в
  `.claude/settings.json` (matcher `^hardener$`), он гоняет `mutationGate` перед концом работы сабагента;
  в облачной сессии хуки из frontmatter роли не срабатывают, поэтому во frontmatter их нет. Specifier и
  reviewer хуком остановки не проверяются: их правки ловит Stop основного агента.
- У облачной платформы свой Stop-хук (`~/.claude/stop-hook-git-check.sh`, не часть набора). Он один раз
  блокирует остановку при незакоммиченных, неотслеживаемых или незапушенных изменениях и просит
  закоммитить и запушить; вторая остановка проходит. На остановке для утверждения спецификации черновик
  фич не коммитят (раздел 3, шаг 3); правило входит в промпт сессии (приложение D).
- Переменные окружения `GAUNTLET_GUARD=off`, `GAUNTLET_STOP_HOOK=off` — только в отдельном **админ-окружении**
  cloud (для правок набора человеком через агента). Переменные читаются при старте сессии, а сессия,
  созданная другой сессией без явного окружения, наследует окружение создавшей. Поэтому координатор
  создаёт сессии задач с явным идентификатором охраняемого окружения, а сессия первым сообщением
  приводит строку статуса хуков из SessionStart (`guard: on; stop hook: on`). Если SessionStart напечатал
  предупреждение без поля `guard`, сессия выполняет `printenv GAUNTLET_GUARD`: пусто или любое значение,
  кроме `off`, — защита включена. Окружение самого координатора выбирает владелец и записывает в план.
  Правки набора, утверждённые владельцем, вносит своим PR координатор, если он в админ-окружении, иначе
  отдельная сессия в админ-окружении; сессия задачи с `guard: on` их не сможет. В эталонном проекте однажды выяснилось, что окружение по умолчанию, где работали и координатор,
  и сессии задач, несёт `GAUNTLET_GUARD=off`: защита набора держалась на дисциплине агентов, CI и diff, а не
  на хуке.
- Единичное отступление от жёсткого правила (например, переписать авторство коммитов в своей ветке)
  допускается только явным решением владельца в чате, для одного случая, и записывается в план с датой и
  PR. Правило от этого не меняется.

**Заморозка спецификации**: «заморожено, если в ветке есть коммит с фичами, отличающийся от базовой ветки».
Снимается сама после мержа. Изменить утверждённую спецификацию может только человек: на GitHub в ветке
сессии либо в админ-окружении.

**Integrity** (правила T1–T5 тесты, M1–M3 main, F1 фичи, B1–B5 сборка, P1 тестовые свойства): находки
принимает только человек в `config/integrity-allowlist.txt` с причиной.

**CI**: workflow гоняет `gauntlet` на каждый PR с полной историей; в монорепо — во всех охраняемых
модулях. Защита ветки: не мержить красный PR (правило человека, если платформа не даёт защиту).

**Только человек**: «да» спецификации; merge; пороги, allowlist'ы, архитектура, роли, `CLAUDE.md`;
исключения для эквивалентных мутантов; строки `pit-runerror-allowlist.txt` (после чтения тестов); выключение
хуков.

**Ограничения**: метрики не ловят уязвимости и ошибки бизнес-логики, которых нет в спецификации (для
регулируемых контуров добавить SAST и проверку зависимостей); хуки работают только в сессии с одним
репозиторием; облачная VM ограничена (мутации медленные: `scope=changed`, инкрементальный анализ,
маркер медленных тестов); внутренние зависимости из корпоративных реестров в облаке недоступны
(библиотека в репозитории или composite build), а публичные сайты и GitHub недоступны в корпоративном
контуре (раздел 1.2); сайты документации из облака открываются только из списка сетевой политики
окружения (раздел 8.2).

## 8. Протокол для Claude

Этот раздел выполняет Claude Code. Он читает документ целиком (бандл целиком не читает: распаковывает и
читает нужные файлы), затем действует по ключевому слову: `start` (раздел 8.1), `scan` (раздел 8.2),
`coordinate` (раздел 8.3) или `contract <ревизия прода>` (раздел 8.5).

### 8.1. `start` — сгенерировать набор под стек

**Шаг 1. Версии проекта и опрос владельца.** Сначала без вопросов прочитать файлы целого проекта:
манифесты и скрипты сборки, версии toolchain/source/target, version catalogs, lock-файлы, wrapper
(`gradle/wrapper/gradle-wrapper.properties`, `maven-wrapper.properties`), `package.json`/engines,
`pyproject.toml`/`uv.lock`, существующий CI. Определить язык и его версию, сборщик, фреймворки и тестовые
библиотеки; если файлы задают диапазон, получить фактически разрешённую версию штатной read-only командой
сборки (`dependencies`/`dependency:list`, `npm ls`, `uv tree`). Для каждой версии сохранить доказательство
(файл:строка или команда и её вывод). Не копировать версии эталона и не менять проект ради разведки.

Затем задать владельцу один список вопросов (отвечать можно кратко); обнаруженную таблицу версий показать
для подтверждения, спрашивать только о пробелах, конфликтах и необходимых решениях:

1. Репозиторий: owner/repo, основная ветка, монорепо или одна сборка (если монорепо — какие каталоги
   охранять: сервисы с логикой, не библиотеки и не тестовые стенды).
2. Стек: подтвердить обнаруженные язык/версию, сборку/раннер (Gradle, Maven, Poetry/uv/pip,
   npm/pnpm/yarn), фреймворки и тестовые библиотеки с версиями; дополнить только то, что не удалось
   определить по файлам и фактическому разрешению зависимостей, и подтвердить BDD-инструмент.
3. Инфраструктура тестов: контейнеры (Docker/Testcontainers), базы, брокеры, моки внешних систем.

текст в чат, по выбору владельца; каталог `gauntlet/` агенту закрыт хуком), разделы:

1. **Облачное окружение Claude Code**:

     галка «Also include default list of common package managers» — без неё пропадут публичные реестры
     пакетов из уровня Trusted. Git-операции с репозиториями сессии идут через отдельный прокси, вносить
     github.com не нужно; веб-страницы github.com чужих репозиториев всё равно закрыты (раздел 4а);

     полагаться на это не стоит — проверить запросом;

     зависимостей, загрузка образов контейнеров тестов. Результат кэшируется снимком файлов, если скрипт
     укладывается примерно в 5 минут; дольше — кэша нет, и скрипт идёт в каждой новой сессии. Независимые
     установки запускать параллельно (`&` и `wait`), долгую загрузку переносить в SessionStart-хук в фоне.

     2 минуты по умолчанию и до 10 минут по запросу, затем уходит в фон (лимиты меняются переменными
     `BASH_DEFAULT_TIMEOUT_MS` и `BASH_MAX_TIMEOUT_MS`). Отсюда `scope=changed` для мутаций и прогон полного
     `gauntlet` в фоне — но не одновременно с прогоном Stop-хука в том же каталоге сборки.
2. **Админ-окружение** `gauntlet-admin`: то же плюс `GAUNTLET_GUARD=off` (и при желании
   `GAUNTLET_STOP_HOOK=off`). Только для правок набора и утверждённой спецификации по решению владельца:
   сам владелец через агента или координатор, если владелец поставил его сюда (раздел 6).
3. **GitHub / GitLab**: приложение Claude установлено на репозиторий; workflow гейта включён; защита ветки
   (обязательный зелёный `gauntlet`, запрет push в основную) или правило «красное не мержить»;
   CODEOWNERS на `gauntlet/`, `.claude/`, `CLAUDE.md` при наличии.
4. **Закладки с промптами**: `https://claude.ai/code?repositories=<owner>/<repo>&prompt=<текст>` для
   типовых запусков (новая задача от основной ветки, разбор инцидента, продолжение шага плана).
5. **Проверка установки**: новая сессия от основной ветки печатает `guard: on; stop hook: on`, гейты
   `gauntletFast` зелёные на текущем коде.
6. **Известные ловушки контура** (из скана и из опыта): окончания строк (CRLF в репозитории против LF у
   инструментов записи), rate limit реестров (повторы с паузой), single-branch/shallow клоны и
   merge-base, вложенные классы и глобы исключений, мутанты на логирующих методах, тесты с ожиданиями без
   таймаута, корпоративные зеркала недоступные из облака, кодировки.
7. **План адаптации старого кода**: `scope=changed` включает набор без разбора истории; список файлов
   выше лимитов и порядок их приведения к лимитам отдельными PR до поведенческих правок; кандидаты в
   `exclude` с обоснованием; рёбра архитектуры против направления как отдельные задачи.
8. **Операционные задачи вне кода**: ротация секретов, найденных в репозитории; политики хранилищ; доступы.
9. **Перенос в рабочий контур** (если контур закрыт, раздел 1.2): что переносится и что нет; какие
   зависимости и плагины проекта проверить в корпоративном реестре (список с координатами из скана);
   как собрать и прогнать тесты в контуре без набора; способ переноса правок (git-зеркало, `git bundle`,
   архив с манифестом удалённых файлов) и порядок: PR за PR, в порядке мержа.

**Шаг 3. Предложить первую серию задач** в формате плана (раздел 1.1, п. 1): гигиена → рефакторинг под
гейты → поведенческие шаги, каждый с пометкой «со спецификацией / без», зависимостями и оценкой, и
задачу для Jira на первый шаг.

### 8.3. `coordinate` — координатор серии и передача контекста (одна задача = одна сессия)

Серию ведёт координатор (раздел 1.1, п. 11). Старт по слову `coordinate`: прочитать план (прикреплённый файл
или отчёт `scan`), найти охраняемое окружение (список окружений), привести строку статуса хуков из
SessionStart, записать в план окружение координатора и охраняемое окружение для сессий задач и ждать
команды владельца на первую задачу. Цикл одной задачи:

1. Владелец пишет, что предыдущий шаг закрыт (PR смержен). Координатор проверяет merge, подтягивает
   основную ветку и записывает итог шага в план: PR, что вошло, открытые вопросы из отчёта.
2. Задача для Jira в чат, затем пред-проверка (многоагентный прогон: карты кода по срезам задачи,
   сверка по документации и байткоду, критик). Результат — в файл рядом с планом. Для задачи выбора значения
   или версии пред-проверка даёт таблицу решений (тип события × наблюдаемый исход), атакованную критиком
   граничными случаями, и цели граничных тестов до реализации; таблицу утверждает владелец до заморозки
   (раздел 1.1, п. 12).
3. Если пред-проверка меняет объём или оценку, координатор пишет дополнение к задаче и вопросы владельцу.
   Сессию открывает только по команде владельца.
4. Перед созданием сессии координатор пишет в чат рекомендацию модели и уровня рассуждений под эту задачу с
   обоснованием (раздел 1.1, п. 17); владелец решает. Затем координатор создаёт сессию задачи (инструмент
   создания сессий облака; если его нет — готовый промпт владельцу) по шаблону приложения D: база и ветка,
   правила сессии (лимит токенов, контур, git, ПДн, Docker, адресация вопросов, внешний ревьюер, комментарии
   простым языком, остановка на находке «правило»), задача, факты пред-проверки, черновик сценариев, таблица
   решений для правил выбора, цели unit-тестов (включая граничные случаи таблицы), решения, которые сессия
   соберёт на остановке, объём «вне задачи». Окружение задаётся явно — охраняемое, без `GAUNTLET_GUARD=off`
   (раздел 6); модель — параметром инструмента; уровень рассуждений и воркфлоу владелец выставляет в настройках
   сессии сам; заголовок «Шаг N: …», теги проекта, модуля и шага. ID сессии записывается в план.
5. Решения владельца, пришедшие, пока сессия работает, координатор передаёт в неё сам. Если прямой отправки
   сообщения в другую сессию нет, работает Routine: создать одноразовый триггер с привязкой к ID сессии,
   запустить его с текстом решения и удалить. Вопросы, которые сессия пометила «переслать координатору»,
   владелец пересылает в чат координатора; ответ координатор отправляет в сессию тем же способом и записывает
   в план.
6. Когда сессия открыла PR, координатор подписывается на его события (CI, комментарии, в том числе внешнего
   ревьюера) и ставит себе периодическую проверку. Комментарии внешнего ревьюера на PR шага разбирает сессия
   шага (раздел 1.1, п. 19); координатор следит, что ни один не остался без ответа, и отвечает сам только на
   своих PR. Координатор не мержит и не просит мержить; вопросы из отчёта заносит в план до решения. Приёмка
   реализации — не больше двух раундов замечаний (раздел 1.1, п. 10): каждое замечание координатора помечается
   типом «дефект» (правится исполнителем) или «правило» (вопрос владельцу нумерованным списком «ответьте
   здесь», без нового раунда правок); счёт раундов координатор ведёт в плане. После второго круга с
   непогашенными находками координатор прекращает выдавать новые и выносит остаток владельцу; PR не считается
   готовым — в чате и описании пишется, что работа не сделана. Если PR
   шага открылся и был смержен между проверками без подписки, события не придут: напоминание сессии ответить
   внешнему ревьюеру и проверка после мержа делаются вручную.
7. После мержа — проверка результата (раздел 1.1, п. 21): код против описания PR и спецификации, гейты на
   основной ветке в режиме набора по умолчанию (копия рабочего дерева через `git worktree`, Docker поднят),
   остатки — в план; сессия шага архивируется. Ветка координатора после мержа его собственного
   PR пересоздаётся от основной ветки (GitHub удаляет смерженную ветку, и push в неё отвечает «stale info»:
   обычный `git push -u origin <ветка>` создаёт её заново).
8. Две правки, которые сессия шага сделать не может и которые координатор делает сам по решению владельца
   (раздел 1.1, п. 23 и 24): правка замороженной спецификации — отдельный коммит `spec:` в ветку шага после
   прогона приёмки, с пометкой о решении; при гонке с пушем сессии — `git merge` её головы, не rebase; строки
   allowlist RUN_ERROR — собственный прогон `mutationGate` на ветке шага (worktree), чтение тестов, строки в PR
   координатора, сессии сообщается, что после мержа нужно слить основную ветку. Оба сообщения в сессию идут тем же
   способом, что решения владельца (п. 5).
9. Документы для соседних команд (описание API, уведомления разработчикам) координатор пишет языком контура
   (раздел 1.1, п. 25): без шагов, PR, набора, веток, репозитория и ролей. Файл передаётся владельцу в чат, в
   репозиторий не кладётся, если владелец не решил иначе; перевыпускается после каждого шага, меняющего контракт.

Новая сессия начинается с `git fetch` базовой ветки. Дочерняя сессия по умолчанию наследует модель от
сессии, которая её создала; параметр `model` инструмента создания её меняет. Параметра уровня рассуждений у
инструмента нет: его выставляет владелец в настройках сессии (в самой сессии — команда `/effort <уровень>`).

### 8.4. Как пересобрать бандл из эталона (владелец эталона)

Когда набор в эталонном репозитории меняется, бандл пересобирается. Работа идёт во временном каталоге, а
не в корне эталона: там остались бы неотслеживаемые файлы, которые легко закоммитить.

**Снимок набора.** В каталог положить прежний бандл `gauntlet-kit-bundle.md` и снять набор нужной
ревизии:
```bash
REPO=<путь к эталону>; REV=origin/main
rm -rf kit-src && mkdir kit-src
git -C "$REPO" archive "$REV" --format=tar gauntlet .claude CLAUDE.md .github/workflows/gauntlet.yml | tar -x -C kit-src
```

Тот же `git archive` в формате `tar.gz` — локальный бэкап владельца (`gauntlet-<проект>-<дата>.tar.gz`).

**Очистка перед раздачей.** Бандл отдают посторонним, поэтому из копии набора (`kit-src` → `kit-clean`) убирают всё, что
называет эталонный проект и его предметную область: оверлеи модулей эталона (`config/<module>/`) —
удалить; корневой `CLAUDE.md` — заменить шаблоном (`# <проект>`, описание модулей, `@gauntlet/CLAUDE.md`);
имена пакетов, модулей и внутренних библиотек — на нейтральные (`com.example.service`, `adapter`,
`shared-lib`); примеры и термины предметной области в правилах, ролях (`.claude/agents/`), README,
комментариях конфигов и allowlist'ов, шаблонах фич и тестовых данных хуков (имена классов, методов, фич и
коммитов) — на нейтральные. Список запрещённых слов — на обоих языках набора: название проекта и
организации, смежные системы, отраслевые термины по-русски и по-английски, имена пакетов, модулей и классов
эталона (список классов — `git -C "$REPO" ls-files '*.java'`). Скрипт очистки начинает с `rm -rf kit-clean &&
cp -r kit-src kit-clean` и правит только `kit-clean`. Список замен и запрещённых слов владелец эталона ведёт
в своём скрипте очистки рядом с этой командой; результат проверяется grep по запрещённым словам (пусто) и
`selftest.py` (0 failed).

С ревизии 3 очистка — скрипт `clean_kit.py`, который лежит у владельца рядом с бандлом: `python3 clean_kit.py
kit-src kit-old kit-clean`, где `kit-old` — распакованный прежний бандл. Из него берутся обобщённые
`README.md`, `INSTALL.md`, `gauntlet.properties`, `architecture.properties` и корневой `CLAUDE.md` (в эталоне эти
файлы после установки стали проектными), и в них переносятся правки новой ревизии; остальные файлы берутся из
`kit-src` и правятся заменами. Каждая замена обязана найтись ровно один раз, иначе скрипт останавливается:
так устаревшая замена не проходит молча, когда набор изменился. После правок набора в эталоне скрипт
правится вместе с ним.

Бандл снимают с ревизии, где смержены все правки набора. Если правка набора ещё в открытом PR, до его мержа
`REV` — ветка этого PR, иначе пересборка из `origin/main` молча её потеряет.

**Сборка.** Скрипт ниже пишет манифест и файлы и вкладывает в заголовок **канонический распаковщик этой
версии**. Распаковщик поставляется вместе со сборщиком одного формата (F12): брать его из прежнего бандла
нельзя — старый формат добавлял завершающий LF, который новый сборщик уже сохраняет, и каждый файл расходился
бы с манифестом на байт. Из прежнего бандла берутся только описание и список изменений; первую строку
(`ревизия N от <дата>`) и список изменений владелец правит руками. Сборщик сам распаковывает результат своим
распаковщиком и сверяет побайтно (round-trip), поэтому рассинхрон формата, пустой файл или лишний/недостающий
завершающий LF не уйдут в бандл молча:
```bash
python3 - kit-clean gauntlet-kit-bundle.md gauntlet-kit-bundle.new.md "# Бандл эталонного набора gauntlet (ревизия N от <дата>)" <<'PY'
import os, sys, subprocess, tempfile
src, old_bundle, new_bundle, revision = sys.argv[1:5]
if not os.path.isdir(src) or not any(os.scandir(src)):
    sys.exit(f"{src}: нет очищенной копии набора — сначала очистка")
# Канонический распаковщик побайтного формата этого сборщика (тело пишется verbatim, без rstrip и без добавления
# LF). Меняется ВМЕСТЕ со сборщиком: новый формат + старый распаковщик = каждый файл на байт длиннее манифеста.
FENCE = chr(96) * 3
EXTRACTOR = r'''import re, os, sys
bundle = open(sys.argv[1], encoding="utf-8").read()
for m in re.finditer(r"^===== BEGIN FILE (.+?) =====\n(.*?)\n===== END FILE \1 =====$", bundle, re.S | re.M):
    path, body = m.group(1), m.group(2)
    os.makedirs(os.path.dirname(path) or ".", exist_ok=True)
    with open(path, "w", encoding="utf-8", newline="\n") as f:
        f.write(body)
    print("wrote", path)
'''
UNPACK = (
    "## Как распаковать (Claude выполняет это на шаге 2 протокола `start`)\n\n"
    "Каждый файл лежит между строками `===== BEGIN FILE <путь> =====` и `===== END FILE <путь> =====`.\n"
    "Скрипт ниже пишет их на диск в текущий каталог, сохраняя пути. При `start` запускайте его во временном\n"
    "каталоге вне репозитория: набор попадает в проект только после адаптации под стек.\n\n"
    + FENCE + "python\n" + EXTRACTOR + FENCE + "\n\n"
    "Запуск: `python3 extract_bundle.py gauntlet-kit-bundle.md`. После распаковки: `chmod +x gauntlet/hooks/*.sh\n"
    "gauntlet/hooks/*.py gauntlet/install.sh`. Файлы `.claude/*`, `CLAUDE.md` и `.github/workflows/gauntlet.yml`\n"
    "в эталоне уже установлены (`install.sh` их когда-то перенёс из `gauntlet/claude` и `gauntlet/ci`); для новой\n"
    "установки положите их обратно в `gauntlet/claude/` и `gauntlet/ci/`: их переносит `install.sh` последним шагом\n"
    "установки (раздел 8.1, шаг 3 инструкции). Корневой `CLAUDE.md` в бандле — шаблон: описание модулей заполняется по репозиторию.\n"
)
old = open(old_bundle, encoding="utf-8").read()
header = old.split("\n## Как распаковать", 1)[0].split("\n")   # описание + список изменений прежнего бандла
header[0] = revision
files = sorted(os.path.relpath(os.path.join(d, n), src).replace(os.sep, "/")
               for d, _, names in os.walk(src) for n in names)
with open(new_bundle, "w", encoding="utf-8", newline="\n") as out:
    out.write("\n".join(header).rstrip("\n") + "\n\n" + UNPACK + "\n## Манифест\n\n")
    out.writelines(f"- `{p}` ({os.path.getsize(os.path.join(src, p))} байт)\n" for p in files)
    out.write("\n## Файлы\n\n")
    for p in files:
        raw = open(os.path.join(src, p), "rb").read()
        if b"\r\n" in raw:
            sys.exit(f"CRLF in {p}: заголовок бандла читается с universal newlines (CRLF→LF), побайтного совпадения не будет")
        body = raw.decode("utf-8")          # без rstrip: тело == содержимое файла побайтно, распаковка пишет его как есть
        out.write(f"===== BEGIN FILE {p} =====\n{body}\n===== END FILE {p} =====\n\n")
# Round-trip тем же распаковщиком, что уйдёт в заголовке: ловит рассинхрон формата, пустые файлы и 0/1/2 LF.
with tempfile.TemporaryDirectory() as td:
    ext = os.path.join(td, "extract_bundle.py")
    open(ext, "w", encoding="utf-8", newline="\n").write(EXTRACTOR)
    outdir = os.path.join(td, "out"); os.makedirs(outdir)
    subprocess.run([sys.executable, ext, os.path.abspath(new_bundle)], cwd=outdir, check=True, stdout=subprocess.DEVNULL)
    for p in files:
        a = open(os.path.join(src, p), "rb").read()
        b = open(os.path.join(outdir, p), "rb").read()
        if a != b:
            sys.exit(f"round-trip расходится в {p}: {len(a)} -> {len(b)} байт — распаковщик не соответствует формату сборщика")
print(len(files), "files ->", new_bundle, "(round-trip побайтно совпал)")
PY
```

**Проверка.** Сборщик уже сверил round-trip побайтно своим распаковщиком. Дополнительно распаковать новый бандл
во временный каталог скриптом из его заголовка: `diff -r` с `kit-clean` — пусто (тело файла пишется побайтно, без
снятия или добавления переноса строки); `python3 gauntlet/hooks/selftest.py` из распакованной копии — `0 failed`;
grep по запрещённым словам — пусто. После проверки новый бандл заменяет старый.

### 8.5. `contract <ревизия прода>` — сверка контракта с продом

Выполняется в сессии на целевом репозитории по запросу владельца, перед выкатом серии и всегда, когда
владелец спрашивает, не задевают ли изменения прод. Только чтение: ничего не меняет и не коммитит.

**Шаг 1. Базы сравнения.** Облачный клон бывает single-branch и shallow, поэтому сначала добыть историю и
ссылки: `git fetch --unshallow origin` (если клон shallow), затем `git fetch origin
'+refs/heads/*:refs/remotes/origin/*' '+refs/tags/*:refs/tags/*'`. Ревизия прода — коммит, тег или ветка,
которую назвал владелец. Если он не уверен, предложить кандидатов: `git tag --sort=-creatordate`,
`git branch -r --list 'origin/release/*'`, последний мерж перед серией; выбор за владельцем. В закрытом
контуре (раздел 1.2) ревизия прода — коммит GitHub, до которого правки перенесены в контур; его называет
владелец по своему журналу переноса. Правки, сделанные прямо в контуре, в GitHub не видны: сверка их не
покрывает, и отчёт пишет это в «не проверено». Вторая ревизия — основная ветка. Обе раскрыть отдельными
`git worktree add <tmp>/<имя> <ревизия>` во временном каталоге. Сначала `git diff --stat` по областям: какие модули, библиотеки, миграции БД, ресурсы и файлы
сборки не менялись вовсе — это сразу «идентично», дальше их не разбирать.

**Шаг 2. Сравнение по поверхностям** — многоагентный прогон, по агенту на поверхность и скептик на
каждого. Набор поверхностей выбирается по типу проекта: пункты 1–5 — для сервиса с интеграциями, 6 — для
любого сервиса со своим API, 7 — для клиентского приложения. Пакеты и классы могли переехать, поэтому сравнивается поведение и байты на проводе, а не пути.
1. Брокеры сообщений: состав и формат тела, свойства сообщения, exchange и routing key, объявляемая
   топология и её аргументы (изменённый аргумент существующей очереди ломает объявление), что принимается
   на входе и что отвергается, подтверждения, повторы, dead letter.
2. HTTP и иные протоколы с внешними системами: запрос побайтно по смыслу (путь, метод, заголовки,
   кодировка, тело, идентификаторы сообщений, таймауты, повторы) и разбор ответа — что раньше принималось,
   а теперь отвергается или трактуется иначе.
3. Прочие клиенты и хранилища: объектное хранилище (ключи, метаданные, таймауты), сторонние API.
4. БД и эксплуатация: схема и миграции, значения в колонках (статусы, форматы идентификаторов), события
   аудита и ключи их деталей, метрики, health и служебные эндпоинты, свойства конфигурации и переменные
   окружения (переименования, новые обязательные, смена умолчаний), строки логов, на которые может быть
   настроен алертинг.
5. Бизнес-поведение, видимое смежным системам: число, порядок и тайминги вызовов и сообщений; случаи,
   где раньше сообщение уходило, а теперь нет, и наоборот.
6. Собственный API сервиса: маршруты и методы, схемы запросов и ответов, коды ошибок, аутентификация,
   CORS, лимиты, версия API. Для сервиса с генерацией OpenAPI — сравнить спецификации обеих ревизий
   (например, `app.openapi()` у FastAPI).
7. Клиентское приложение: вызовы API (пути, параметры, тела, обработка ошибок и статусов), маршруты и
   deep links, ключи localStorage, sessionStorage и cookies, переменные сборки (например, `VITE_*`),
   базовый путь ассетов, поддерживаемые браузеры.

**Шаг 3. Классификация** каждой находки: «идентично» (проверено), «добавлено» (старые потребители не
ломаются), «поведение» (намеренное изменение, видимое смежной системе или эксплуатации), «ломает»
(система, работающая по старому контракту, сломается без своей правки). Скептик подтверждает «ломает»
только при конкретном входе от реальной внешней системы, на котором поведение отличается. Утверждение о
поведении фреймворка или библиотеки (значение по умолчанию, кодировка, сжатие, таймаут) проверяется по
правилу 12 — источник нужной версии или байткод; без источника находку не классифицируют, она идёт в «не
проверено». Пример из эталонного проекта: после перехода на новый HTTP-клиент фреймворк по умолчанию
добавил заголовок `Accept-Encoding: gzip, deflate` во все исходящие запросы — это нашлось только по
байткоду фабрики клиента.

**Шаг 4. Отчёт владельцу:** сначала «ломает» с действиями до выката, затем «поведение» с тем, кто его
заметит, затем добавленное, затем подтверждённо идентичное по поверхностям; отдельно — что не проверено и
почему. Решения, нужные от владельца, — нумерованным списком. В закрытом контуре (раздел 1.2) — новые переменные окружения и значения по умолчанию, а также
удалённые и переименованные файлы для ручного переноса.

Ожидания — своими столбцами; правка замороженной спецификации — только человеком или его делегатом (раздел 1.1, п. 23) | параметризованные тесты любого стека |
| строка allowlist устарела за день | метод, под который человек внёс строку RUN_ERROR, исчез после второго раунда ревью (расчёт переписан); строка стала мёртвой — убирать в следующем PR владельца набора, иначе allowlist врёт о коде | любые исключения из мутаций и линтеров |
| hardener правит продакшен «на минутку» | при пустой области PIT роль через скрипт правила main-файлы ради ручных мутантов и откатывала их; guard по типу агента не ловит правку через скрипт. Правило роли: предлагает список, применяет кодер (раздел 1.1, п. 22) | любые ограничения ролей по инструментам |
| контрольный прогон после мержа со `scope=all` | показывает старые нарушения в файлах непройденных шагов (Checkstyle в мапперах, которые чинят следующие шаги) и выглядит как красный main; контроль идёт в режиме набора по умолчанию | любые гейты с областью «изменённое» |
| сессия ждёт правку, которую сделать не может | хук закрыл замороженную фичу для агентов, и сессия шага ждала «правку на GitHub»; координатор увидел это по сводке состояния сессии (`needs_action`) и внёс правку сам как делегат владельца | то же |
| внутренние термины в документах для соседей | описание API содержало номера шагов, PR, «владелец», ветку и ревизию репозитория — для разработчиков контура, которые не должны знать о внешней разработке; документ переписан, правило закреплено (раздел 1.1, п. 25) | любые документы, уходящие за пределы команды |
| raw-вики недоступна для одного репозитория | raw.githubusercontent.com/wiki/… отдаёт вики Spring Framework, но 404 для вики Spring Boot при любом имени страницы; гид миграции открывает человек | проверять каждую вики запросом, не по аналогии |
| адрес с версией перенаправляет на страницу без версии | docs.spring.io/spring-framework/reference/7.0/ стал текущей веткой и ушёл на адрес без версии с метатегом 7.0.9 при 7.0.8 в сборке | сверять метатег `version` и `url_effective` после редиректа |
| репозиторий документации заархивирован | liquibase/liquibase-docs заархивирован, веток под версии нет, а сайт закрыт политикой: остаются javadoc-jar и исходники библиотеки по тегу | любые проекты, перенёсшие документацию на закрытую платформу |

## Приложение E. Встраивание набора в сборку для закрытого контура (эталон, Gradle)

Три сокращённых фрагмента из модулей эталона. Адрес корпоративного реестра заменён на `nexus.example.corp`,
имя внутренней библиотеки — на `shared-lib`. Для
других стеков принцип тот же: переключатель источника пакетов по переменной окружения облака и CI,
набор и приёмка подключаются только при наличии каталога набора и публичных репозиториях, образы
контейнеров тестов — через префикс реестра.

**`settings.gradle` модуля** — переключатель репозиториев и условие подключения набора:

```groovy
pluginManagement {
    // публичные репозитории в облачной сессии (CLAUDE_CODE_REMOTE) и в GitHub Actions (GITHUB_ACTIONS),
    // корпоративный реестр во всех остальных случаях; принудительно: -PpublicRepositories=true|false
    gradle.ext.publicRepositories = providers.gradleProperty('publicRepositories').map { it.toBoolean() }
            .getOrElse(System.getenv('CLAUDE_CODE_REMOTE') == 'true' || System.getenv('GITHUB_ACTIONS') == 'true')
    repositories {
        if (gradle.ext.publicRepositories) {
            gradlePluginPortal()
            mavenCentral()
        } else {
            maven { url = uri(NEXUS_MAVEN_CENTRAL_URL) }   // gradle.properties: https://nexus.example.corp/repository/maven-group/
        }
    }
}

// набор подключается, когда он лежит рядом и его артефакты достижимы: по умолчанию там же, где публичные
// репозитории; в корпоративной сети — только явным -Pgauntlet=true (плагин PIT есть лишь на портале плагинов)
gradle.ext.gauntletEnabled = file('../gauntlet/gauntlet.gradle').isFile() &&
        providers.gradleProperty('gauntlet').map { it.isEmpty() || it.toBoolean() }.getOrElse(gradle.ext.publicRepositories)

// внутренняя библиотека из того же репозитория: в облаке — из исходников, в контуре — снапшот из реестра
if (gradle.ext.publicRepositories && file('../shared-lib').isDirectory()) {
    includeBuild('../shared-lib')
}
```

**`build.gradle` модуля** — набор, плагин мутаций и зависимости приёмки только при включённом наборе:

```groovy
buildscript {
    repositories {
        if (gradle.ext.publicRepositories) { gradlePluginPortal() } else { maven { url = uri(NEXUS_MAVEN_CENTRAL_URL) } }
    }
    dependencies {
        if (gradle.ext.gauntletEnabled) { classpath 'info.solidsoft.gradle.pitest:gradle-pitest-plugin:1.19.0' }
    }
}

repositories {
    if (gradle.ext.publicRepositories) { mavenCentral() } else { maven { url = NEXUS_MAVEN_CENTRAL_URL } }
}

if (gradle.ext.gauntletEnabled) {
    apply plugin: 'info.solidsoft.pitest'
    apply from: '../gauntlet/gauntlet.gradle'          // он же создаёт source set acceptanceTest
    dependencies {
        acceptanceTestImplementation 'org.testcontainers:testcontainers-postgresql'
        acceptanceTestImplementation 'org.testcontainers:testcontainers-rabbitmq'
    }
    // образы контейнеров: вне корпоративной сети — Docker Hub; -Phub.image.name.prefix=… переопределяет
    def imagesPrefix = findProperty('hub.image.name.prefix')
    if (imagesPrefix == null && gradle.ext.publicRepositories) { imagesPrefix = '' }
    if (imagesPrefix != null) {
        imagesPrefix = imagesPrefix ? (imagesPrefix.endsWith('/') ? imagesPrefix : imagesPrefix + '/') : 'docker.io/'
        tasks.withType(Test).configureEach { environment 'TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX', imagesPrefix }
    }
}
```

**`src/acceptanceTest/resources/testcontainers.properties`** — реестр образов по умолчанию:

```properties
# приоритет Testcontainers: переменная TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX > ~/.testcontainers.properties > этот файл
hub.image.name.prefix=nexus.example.corp/
```

Префикс кладут рядом с тестами, которые его используют. В эталоне контейнеры есть только в приёмке, поэтому
префикс лежит там. Для тестов, которые переносятся в контур, его кладут в сборку или в основной каталог
тестовых ресурсов: файл в каталоге приёмки в контур не попадает.

Что это даёт: в контуре `gradle build` не видит ни набора, ни приёмки, ни плагина мутаций и берёт всё из
корпоративного реестра; Docker-образ модуля собирается как раньше. В облаке и CI включается всё.

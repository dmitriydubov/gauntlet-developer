# Регрессионный набор дистрибутива

Проверки самого набора Gauntlet. В бандл не входят: это тесты для того, кто меняет набор, а не для проекта,
в который набор ставят.

```bash
python3 tests/run.py              # всё, чему достаточно python3, git, bash и JDK 21+ (около двух минут)
python3 tests/run.py --fast       # без самопроверки хуков (самая долгая часть)
python3 tests/run.py --gradle     # плюс сценарии на настоящем Gradle (Gradle 8.14+, Maven Central; несколько минут)
python3 tests/run.py -k crap      # только тесты, в идентификаторе которых есть «crap»
```

Код возврата: 0 — всё зелёное; 1 — есть падение или `-k` не выбрал ни одного теста; 2 — `--gradle` без `gradle`
в `PATH`. Прогон, который ничего не проверил, зелёным не считается.

Набор никогда не проверяет рабочую копию. `run.py` распаковывает `gauntlet-kit-bundle.md` скриптом из шапки
самого бандла, компилирует single-file инструменты и гоняет тесты по этой копии: зелёный прогон относится
к тому, что получит пользователь бандла. Поэтому порядок правки набора такой: изменить файлы в распакованной
копии, пересобрать бандл сборщиком из раздела 8.4 инструкции, запустить `python3 tests/run.py`.

| Модуль | Что проверяет |
|---|---|
| `test_bundle.py` | манифест равен распакованным файлам; сборщик из раздела 8.4 воспроизводит бандл побайтно; файлы синтаксически целы; ревизия одна во всех документах; таблица размеров в CHANGELOG равна манифесту |
| `test_hooks_selftest.py` | `gauntlet/hooks/selftest.py` из распакованной копии: 0 падений, счётчик в README набора совпадает с фактическим |
| `test_guard_reader.py` | чтение командной строки хуком `guard.py` против настоящего bash: 127 команд с маркерами «исполнится» и «данные» (комментарии, heredoc, here-string, перенос строки, `case`, подстановки, ANSI-C строки `$'…'`); всё, что bash исполнил, хук обязан увидеть, а данные не должен принять за команду |
| `test_ci_workflow.py` | shell-шаги `.github/workflows/gauntlet.yml`, выполненные как на раннере (`bash -e`) со стабами JDK и wrapper: версии по модулям, отсутствующий модуль, `PATH`, красный модуль |
| `test_install.py` | `install.sh`: чистая установка, слияние с существующими настройками, обновление, пользовательские хуки |
| `test_crap_gate.py` | `CrapGate` на синтетических отчётах JaCoCo: порог, allowlist, область `changed` с debug-информацией и без |
| `test_integrity_check.py` | `IntegrityCheck`: каждое правило, освобождение packaging-задач (матрица «свободно»/B1), кодировки |
| `test_gherkin_mutator.py` | `GherkinMutator`: генерация мутантов и контрольных сценариев, вердикт по JUnit XML в формате Gradle (стадия падения, контроли), `no-skipped` |
| `test_gradle_e2e.py` | только с `--gradle`: настоящий проект на Gradle — полный `gauntlet` на примере из набора и сценарии, найденные ревью (вердикт Gherkin-мутаций, область `changed` и удалённый glue-файл, JVM гейтов: полная версия, `GAUNTLET_GATE_JAVA_HOME`, launcher, прочитанный init-скриптом) |

В GitHub Actions набор гоняет `.github/workflows/kit-tests.yml` этого репозитория: на каждый pull request и
push в `main` — `python3 tests/run.py --gradle` на ubuntu-24.04 с Python 3.13, Temurin 21 (по умолчанию) и 25,
Gradle 8.14.3.

Workflow самого набора (`.github/workflows/gauntlet.yml` в бандле) здесь не исполняется: его шаги проверяются
как shell-скрипты, сам workflow — только настоящим прогоном в репозитории, куда набор установлен.
